Enemy 스크립트의 [Serializable] 에 대한 설명 주석 추가

-  Serializable 이란? (정의)
   1. 정의: C# 클래스(Class)나 구조체(Struct) 위에 붙이는 특별한 속성(Attribute). System 네임스페이스에 속해있어
   2. 핵심 역할: 유니티 엔진에게 "이 클래스를 직렬화(Serialization) 가능한 데이터 구조로 취급해 주세욥" 라고 공식적으로 요청하는 허가증 역할이야

- Enemy 스크립트에 Serializable이 필요한 이유 (문제 해결)
   1. 일반적으로 유니티는 MonoBehaviour를 상속받은 스크립트의 public 변수만 인스펙터에 표시하고 저장할 수 있어,
      하지만 EnemyStats처럼 MonoBehaviour를 상속받지 않은 일반 C# 클래스를 사용하려면 이 허가증이 필수야
   2. Serializable이 없을 때 발생하는 문제:
      2-1. 인스펙터 미노출: public EnemyStats NormalStats; 같은 변수가 유니티 인스펙터에 아예 표시되지 않아
      2-3. 데이터 미저장: 인스펙터에서 값을 수정하려고 해도 유니티가 그 데이터를 저장하지 못해, 프로젝트를 껐다 켜거나 다시 실행하면 코드가 정의한 기본값으로 초기화돼

- Serializable 사용의 이점 (EnemyStats 적용 사례)
   1. 시각적 그룹화 및 편리한 편집: NormalStats, StrongStats 변수 아래에 MoveSpeed, AttackDamage 등의 필드들이 논리적인 그룹으로 묶여서 인스펙터 가독성이 극대화되고, 기획자가 밸런싱 작업을 하기 쉬워져
   2. 데이터 영구 저장: 인스펙터에서 수정한 모든 값들이 프리팹 파일에 안전하게 기록(직렬화) 되어 영구적으로 유지돼
   3. 높은 재사용성: EnemyStats라는 스탯 템플릿(설계도) 을 단 한 번만 정의하고, 이 템플릿을 NormalStats, StrongStats라는 여러 인스턴스로 만들어서 재사용함으로써 코드의 중복을 제거하고 확장성을 확보할 수 있어

**결론 (Serializable의 가치): Serializable은 데이터와 코드를 분리하는 유니티의 핵심 원칙이자, 협업 환경에서 기획자와 개발자 모두의 생산성을 극대화하는 가장 기초적인 설계 도구야**

Enemy 스크립트의 스탯 시스템의 '데이터 직렬화' 메커니즘 완벽 이해 (배경: Enemy스크립트의 [Serializable] 클래스와 switch 분기 로직에 대한 근본적인 이해 부족 해결)

- [Serializable]의 역할 재정립
   1. EnemyStats와 같은 MonoBehaviour를 상속받지 않은 일반 C# 클래스를 유니티 인스펙터에 노출시키고 **프리팹 파일에 영구적으로 저장(직렬화)**하기 위한 필수 태그임을 확인. (데이터 영속성 확보)
   2. 비유하면 MonoBehaviour의 하청업체 역할을 수행하며, Enemy 클래스에 포함되어야만 저장 권한을 얻어

- 데이터 설정 흐름 파악
   1. Editor 단계: [Serializable] 덕분에 NormalStats, StrongStats, EliteStats 에 수정한 값이 프리팹에 저장돼
   2. Runtime 단계 (핵심!): Start()에서 호출되는 SetEnmeyStats() 함수가 실행됨
   3. 세부 프로세스 (SetEnmeyStats 내부 로직):
      3-1. 타입 선택: switch(enemyType)를 통해 인스펙터에서 설정된 타입에 맞는 스탯 덩어리(NormalStats 등)를 selectedStats에 할당 (데이터 선택) 
      3-2. 난이도 및 최종 적용: EnemyDifficulty.Instance를 통해 난이도 보정을 거친 후, 그 결과값을 currentMoveSpeed, currentAttackDamage 등 실제 게임 로직에서 사용될 내부 변수에 최종적으로 담는다 (데이터 가공 및 할당)

- switch 문의 정확한 역할 이해:
   1. 기능: 인스펙터에서 설정한 EnemyType (Normal, Strong 등) 명찰을 확인하여, 프리팹에 저장된 세 가지 스탯 덩어리(NormalStats, StrongStats, EliteStats) 중 하나를 통째로 선택해서 selectedStats에 할당
   2. 결론: switch 문은 기획 데이터 중 어떤 것을 쓸지 결정하는 최종 분기점이며, 이후 로직은 selectedStats만 참조하여 코드를 간결하게 유지


- 예시) 인스펙터 값 → 게임 적용 6단계 흐름 정리 (인스펙터에서 수정한 값이 게임에 적용되는 과정(데이터 파이프라인)을 명확히 정리)
   1. 데이터 저장: 인스펙터에서 Normal몬스터의 스탯 값 수정 → [Serializable]을 통해 프리팹 파일에 영구 저장
   2. 메모리 로드: 게임 시작 시, 유니티가 프리팹 파일을 읽어 NormalStats 변수(메모리)에 수정된 값을 로드
   3. 함수 호출: 몬스터 오브젝트의 Start() 함수 실행 → SetEnmeyStats() 호출
   4. 타입 선택: SetEnmeyStats() 안의 switch (enemyType) 문이 실행되어 NormalStats를 selectedStats에 할당
   5. 난이도 보정: selectedStats의 값을 EnemyDifficulty를 거쳐 난이도 보정 처리
   6. 최종 적용: 보정된 최종 값이 currentMoveSpeed 등 실제 게임 로직 변수에 할당되어 몬스터 움직임에 반영

Enemy 스크립트의 불필요한 로직 최종 수정
코드가 한 줄만 있는 함수 간략화

- DealDamageToPlayer() 함수에 있던 playerShield = playerGameObject.GetComponent<PlayerShield>(); , playerHealth = playerGameObject.GetComponent<PlayerHealth>();를 Start() 함수로 옮겼어.
- 내부 컴포넌트는 Awake()에, 외부 스크립트는 Start() 함수에. GetComponent는 비용이 비싼 작업이므로, 매 프레임이나 공격 때마다 호출하는 것을 방지하고, 게임 시작 시 한 번만 호출하여 변수에 저장(캐싱)함으로써 런타임 성능을 극대화함.
   1. Awake()의 내부 컴포넌트 = 가장 먼저 호출. 스크립트가 붙은 같은 오브젝트의 컴포넌트는 항상 준비가 보장되므로, 가장 빠르게 캐싱해서 사용할 준비를 마침
   2. Start()의 외부 스크립트 = Awake가 모두 끝난 후 호출. 씬의 다른 오브젝트들이 자기 자신의 Awake를 통해 준비를 마칠 때까지 기다려서 널 에러를 방지하는 안전 장치 역할
   3. 요약: Awake: 나 자신이 준비하는 시간, Start: 모두가 준비를 마칠 때까지 기다렸다가, 다른 오브젝트와 연결하는 시간


- ApplyTouchDamage()와 OnAttackFinished() 함수는 내부에 코드가 한줄만 있었어. 그래서 간결하게 =>를 쓰는 '표현식 본문 멤버'로 수정했어
   1. void ApplyTouchDamage() => DealDamageToPlayer();//통합 함수 호출
   2. public void OnAttackFinished() => animator.SetBool("Attack", false);//몬스터의 Animation에서 이 함수를 호출해 공격 종료.


- 로직 안정성 강화: DealDamageToPlayer()에 최후의 IsDead 체크 추가.
- 데미지를 적용하는 결정적인 순간에 playerScript.IsDead를 체크해서 플레이어가 죽은 후에도 애니메이션 이벤트로 인해 몬스터의 공격 함수가 실행되는 잠재적 버그를 방지. (방어적 프로그래밍)

Player 스크립트 수정.

- 코드 실행 순서(Awake → Start)를 활용하여 안정성을 확보.
   1. GetComponent<>()로 찾는 내부 컴포넌트 (rb, animator, playerHealth 등) 및 [SerializeField]로 연결된 외부 참조 (gameOverManager, walkingaudioSource, ScoreTextUI)의 모든 Null 체크를 Awake() 함수로 이동
   2. Start() 최소화: Start()는 이제 UI 초기값 설정 (ScoreTextUI.text = ...) 등 컴포넌트가 모두 준비된 후에 실행할 최초 동작만 담당하도록 분리


- GameOverManager 스크립트 참조 방식 최적화 (캡슐화(private)를 유지하며 인스펙터 연결의 편리성을 사용)
   1. 변수를 [SerializeField] private GameOverManager gameOverManager; 로 선언하여, public의 불안정성 없이 인스펙터 연결을 허용
   2. FindAnyObjectByType()을 제거하여 게임 시작 시 성능 부하를 줄임 (씬에 오브젝트가 많아질수록 검색 시간이 선형적으로 늘어나 **프레임 저하**의 가능성이 있어)
  	

- 플레이어 사망 시 메인 루프 (Update/FixedUpdate) 효율 극대화.
   1. 목표: 플레이어가 사망(IsDead = true)했을 때 불필요한 연산을 즉시 중단
   2. Update() 최상단 체크: Update() 함수의 가장 첫 줄에 if (IsDead) return;을 배치시켜 플레이어가 사망 시 입력 처리, 사운드, 애니메이션 로직 전체를 즉시 건너뛰도록 수정했어
   3. FixedUpdate() 간결화: PlayerDie() 함수에서 rb.simulated = false;를 실행하므로, FixedUpdate()의 중복된 if (IsDead) 블록을 제거하고 순수 이동 로직 한 줄만 남겼어


- PlayerDie() 함수 로직 명확화 및 버그 수정
   1. 플레이어 사망 처리 함수가 자신의 핵심 책임 (상태 변경 및 모든 활동 중단) 에만 집중하도록 정리했어
   2. 불필요 코드 제거: horizontalInput = 0; 등 Update() 함수에서 이미 처리되는 입력 변수 초기화 코드를 삭제
   3. 버그 수정: 사망 직후 걷기 사운드가 멈추지 않는 버그를 확인했어. PlayerDie() 함수 내부에 if(walkingaudioSource != null && walkingaudioSource.isPlaying) walkingaudioSource.Stop(); 로직을 추가해서,
   사망 즉시 이동 시 사운드를 중단 하도록 조치했어
