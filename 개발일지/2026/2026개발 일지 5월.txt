플레이어의 이동 속도, 무적 지속 시간, 사운드 클립 등을 PlayerStatsSO를 추가해 하나로 관리하도록 구조 개선

- 하드코딩된 이동속도, 무적시간 등을 SO를 추가해 하드코딩을 지양하는 방식으로 바꿨어.

- 왜 이렇게 했어? 하드코딩이라 해도 작동 잘 되잖아.
- 단순히 GetComponent나 문자열로 다 때려 박는 '하드코딩'도 당장은 잘 작동해. 하지만 내가 이번에 구조를 분리하고 SO와 옵저버 패턴을 쓴 이유는 명확해.
   1. 유연한 데이터 관리 (ScriptableObject):
      1-1. 하드코딩의 문제: 몬스터 스탯이나 플레이어의 스킬 쿨타임을 수정하려면 매번 스크립트를 열어서 숫자를 고쳐야 해
      1-2. 해결: PlayerStatsSO를 사용하면 게임을 실행 중인 상태에서도 인스펙터에서 숫자를 딸깍 고치는 것만으로 밸런스를 바로 수정할 수 있어
   2. 오디오 제어의 정교함 (자식 오브젝트 분리):
      2-1. 하드코딩의 문제: 플레이어 하나에 오디오 소스를 다 넣으면 "어떤 게 발소리고 어떤 게 무적 소리인지" 코드에서 구분하기 힘들어
      2-2. 해결: SND_Invincibility처럼 사운드에 맞는 이름의 자식 오브젝트로 나누고 이 안에 각자 오디오 소스를 넣어서 유니티 Audio Mixer에서 "효과음 볼륨만 줄이기" 같은 기능을 만들 때 훨씬 편하고, 이름으로 찾으니까 헷갈릴 일이 없지
   3. 코드 간의 의존성 제거 (옵저버 패턴):
      3-1. 하드코딩의 문제: 플레이어가 죽었을 때 UI 매니저를 직접 불러서 "야, 창 띄워!"라고 시키면, 나중에 UI가 바뀌었을 때 플레이어 코드도 같이 고쳐야 해, 한번이면 끝나는걸 두 세번을 작업 해야해
      3-2. 해결: 플레이어는 그냥 "나 죽었어!" 라고 방송(Invoke)만 하고, 필요한 놈들이 알아서 듣게 만들었어. 이렇게 하면 나중에 UI를 새로 만들어도 플레이어 코드는 손댈 필요가 없지

   1. 강화 시스템: 아이템 획득 시 currentEnhanceStacks를 올리고, maxEnhanceStacks(3스택) 도달 여부에 따라 isEnhanced 판정을 내림

SwordWeapon 스크립트의 하드코딩된 데이터를 PlayerStatsSO로 이전

- 데이터 소스 단일화:
   1. 어제 했던 활 스크립트와 동일하게 기존 스크립트에 있던 데미지, 쿨타임, 프리팹 참조 변수 삭제
   2. 모든 데이터를 PlayerStatsSO에서 가져오도록 수정해서 에디터에서 관리 용이성 확보

- 안전한 참조 로직 (왜 함수마다 var stats = player.Stats; 를 썻어?):
   1. 최신성: 활 스크립트에도 동일한 방식이야. 신성: 게임 중 버프를 받거나 아이템을 장착해 Stats 데이터가 바뀌더라도, 함수 호출 시점에 즉시 반영된 값을 가져올 수 있어
   2. 안전성: 클래스 멤버 변수로 두지 않고 지역 변수로 사용함으로써, 다른 함수에서 실수로 이 참조를 수정하는 사고를 방지할 수 있어
   3. 주석을 적어, 해당 방식이 왜 데이터 오염을 방지하고 안전한지 명시

- 검 강화 및 쿨타임 로직 최적화:
   1. 검 아이템 3회 획득 시 쿨타임 감소 로직을 UpgradeSword() 함수로 일원화
   2. 공격 함수(SwordAttack())에서는 이미 계산된 결과값만 사용하도록 하여 불필요한 조건 검사 삭제

- 밸런싱:
   1. 어제 화살의 발사속도가 하드코딩에서 SO로 이전되서 똑같은 값이지만 느려진것과 같이 검기 에너지도 동일한 문제 발생
   2. 검기 발사 속도가 느려진 현상을 SO 수치 수정을 통해 해결. 기존 속도 15에서 22로 상향 (인스펙터에는 기본적으로 15로 되어 있지만 인스펙터에서 수정해서 22로 적용된 상태야)

- 물리 및 시각적 최적화:
   1. 검기 프리팹의 Rigidbody2D에서 Interpolate 설정을 None에서 Interpolate로 변경하여 프레임 간 움직임을 부드럽게 개선
   2. 물리 보간(Interpolate)의 중요성: 빠른 속도로 이동하는 투사체는 물리 연산 주기에 따라 끊겨 보일 수 있는데, 이 설정을 통해 시각적 퀄리티를 높임
   3. Rigidbody2D Interpolate 설정의 의미:
      3-1. None: 물리 연산 결과가 나오는 프레임에만 위치를 갱신해. 모니터 주사율과 물리 프레임이 맞지 않으면 물체가 떨려 보일 수 있어
      3-2. Interpolate (보간): 이전 프레임과 현재 프레임 사이의 위치를 부드럽게 이어줘서, 검기 에너지처럼 빠르게 움직이는 물체가 아주 매끄럽게 보이게 만들어 줘

- 오늘 어땟어?
   1. 객체지향적 설계: 데이터를 코드와 분리(SO)하고, 각 함수의 역할을 명확히 나누는 것이 유지보수에 얼마나 유리한지 체감
   2. 하드코딩은 초보자? 들이 하는거야. 물론 작동하는것엔 문제는 없지만 지금처럼 혹은 방대한 데이더를 다룰때 스크립트를 일일히 뒤져보는게 아닌 하나의 SO만으로 데이터만 보고 수정작업을 이어갈 수 있어
   3. "내가 할 수 있을까"라는 불안함이 항상 있었지만, 에러를 하나씩 지워가며 결국 코드를 깨끗하게 정리했을 때 큰 성취감을 느꼇어


- To-do 리스트에 있던 **플레이어의 활, 검 공격, 무적, 이동속도도 각스크립트가 아닌 SO를 만들어서 관리해보자, 하드코딩 방식은 지양하는 구조로 만들어보자** 해결!

132회 헌혈. 하루 휴식

- 132회 헌혈을 하고 왔어. 요즘은 헌혈한 날에도 뭐라도 조금 하곤 했지만 오늘은 쉬고 싶어. 물론 쉬어도 똑같이 의자에 앉아있는거겠지만.....
- 1년동안 개발일지 매일 적고 헌혈도 하고 작품도 만들고 계속 업데이트, 학습을 하는 내가 결국은 해피앤딩으로 끝날거라고 난 확신해.(그래야만 버틸 수 있겠지)

- 어제 작업 복습:
- 검기 에너지 프리팹의 Rigidbody2D Interpolate:
   1. 원리: 유니티의 물리 연산 주기(FixedUpdate)와 렌더링 주기(Update) 사이의 오차를 메워주는 기술이야
   2. 적용: 검기(SwordEnergy) 프리팹에 적용해서 빠른 이동 시 발생하는 떨림 현상을 시각적으로 해결했어
- ScriptableObject(SO) 기반 설계:
   1. 핵심: 데이터(Stats)를 로직(활, 검 스크립트)에서 분리하여 독립적인 에셋으로 관리하는 방식이야
   2. 이점: var stats = player.Stats; 처럼 각 함수 내에 지역 변수를 활용해 최신 데이터를 안전하게 참조하며, 하드코딩을 제거해 유지보수성을 극대화했어
- 왜 각 함수마다 var stats = player.Stats; 지역 변수를 넣어?:
   1. 함수마다 불러오는 방식은 '데이터의 최신성'을 보장하고, 실수로 인한 '데이터 오염'을 방지하는 방어적 프로그래밍 기법이야
   2. 매 프레임 실행되는 Update 함수 등에서 과도하게 호출할 경우 성능에 미세한 영향이 있을 수 있으나, 현재와 같은 이벤트 기반이나 일반 함수 호출 구조에서는 무시해도 될 수준이야. 하지만 이 문제를 알고 있어야 하기에 지금처럼 유지했어
   3. 참조 오염 방지: 만약 멤버 변수로 선언해두면, 실수로 어떤 함수에서 stats = null;이라고 적었을 때 스크립트 전체가 마비돼. 하지만 지역 변수(var stats)는 해당 함수가 종료되면 메모리에서 사라지므로 다른 함수에 영향을 주지 않아 안전해
   4. 데이터의 최신성: 게임 도중 강화 아이템을 먹거나 상태가 변해서 player.Stats가 가리키는 SO 자체가 바뀌더라도, 함수를 실행할 때마다 새로 가져오기 때문에 항상 최신 수치를 반영해.
**함수마다 적는 번거로움은 있지만, 이는 "나중에 발생할 수도 있는 치명적인 버그를 미리 예방하는 보험"이라고 생각하자. 어제 작성한 SwordWeapon 스크립트의 주석에 이 내용을 잘 정리해두었으니, 나중에 봐도 금방 이해할 수 있을 거야**

노션 포트폴리오의 '핵심 로직 구현 & 기술적 문제 해결'에 플레이어 SO를 적용한 내용을 기재

- `ScriptableObject를 활용한 데이터 중심 무기 시스템 설계 및 유연한 리팩토링(PlayerStatsSO.cs)`.
- 지금껏 플레이어의 SO를 만든 이유와 플레이어 스크립트 한곳에서만 SO를 연결한것에 대한 이유와 설명을 적었어.

   2. 의존성 구조 리팩토링: 각 무기의 스크립트에서 데이터를 직접 들고 있던 하드코딩 방식에서, 본체인 Player 스크립트만 SO를 연결하고 SO에 각 무기, 무적의 값을 넣어 해당 스크립트에 GetComponent<Player>()로 데이터를 가져오도록 단일화함
   3. 방어적 참조 설계 적용: 공격 함수가 실행될 때마다 var stats = player.Stats; 와 같이 지역 변수로 참조하여 데이터의 최신성을 보장하고 런타임 오류를 방지

- 작업 중 마주한 고민과 해결.
   1. 고민: 무기가 늘어날 때마다 인스펙터에서 SO를 일일이 연결하는 게 번거롭고 실수할 확률이 높다고 판단. 내가 싫어하는 하나하나 드래그 앤 드롭 방식을 지양하기 위함
   2. 해결: 그래서 단 하나의 SO를 만들어서 이 안에 활, 검, 무적의 데이터를 넣고, Player 스크립트에 프로퍼티(Stats => stats)를 만들어 통로를 단일화하고, 무기들은 플레이어 스크립트만 참조하게 함으로써 세팅 효율을 기대 이상으로 높임
   3. 시각적 확인: 인스펙터에서 플레이어 오브젝트 하나만 관리하면 되는 구조를 직접 확인하고 스크린샷으로 기록

- 적으면서 스스로 느낀 점?
   1. 단순히 "기능이 돌아가게 만드는 것"보다 "나중에 수정하기 편하게 만드는 아키텍처"가 얼마나 중요한지 계속 깨달아. 실무에선 나 혼자 개발하는게 아니니까!
   2. 기획 수치를 바꿀 때 코드를 안 열고 SO의 인스펙터에서 바로 수정할 수 있게 되어 워크플로우가 훨씬 빨라지지

플레이어 체력, 방어력 시스템 리팩토링. SO 적용

- PlayerHealth 및 PlayerShield 스크립트의 하드코딩된 데이터를 PlayerStatsSO로 통합 관리하도록 구조 변경.
- 데이터 보호 및 캡슐화: 현재 체력과 방어력 변수에 public float ... { get; private set; } 프로퍼티를 적용해서 외부의 불필요한 접근을 차단.

- 캡슐화와 프로퍼티 ({ get; private set; })
   1. 객체지향 설계: 체력과 방어력은 게임 내 플레이어의 생존과 직결된 민감한 데이터야, 더욱 함부로 건드려선 안돼!
   2. 보호막 형성: 그래서 외부 스크립트에서는 값을 읽을 수만 있게 하되(get), 수정은 반드시 해당 클래스 내부의 로직(set)을 통해서만 가능하게 제한했어. 이렇게 바꿔서 의도치 않은 수치 조작으로 인한 버그를 원천 차단했지

- 수치 연산의 안정성 (Mathf 함수)
   1. 하한선과 상한선: Mathf.Max(CurrentHealth, 0)을 통해 체력(방어력도 동일)이 음수가 되는 논리적 오류를 막았고, Mathf.Min(CurrentHealth + amount, maxHealth)을 통해 최대치를 넘어서는 오버플로우 상황을 방지했어
   2. 수학적 방어: 이런 세세한 처리가 모여서 플레이어가 게임 중 "에? 체력이 왜 마이너스가 되지?" 같은 어색함을 느끼지 않게 해주는 거야

- 핵심 학습 내용.
   1. Mathf 함수 활용:
      1-1. Mathf.Min: 회복 시 최대 체력을 초과하지 않도록 제한
      1-2. Mathf.Max: 받은 데미지 계산 시 수치가 0 미만으로 떨어지지 않도록 하한선 고정
   2. 유니티 직렬화(Serialization) 우선순위:
      2-1. So 스크립트에서 기본값을 수정해도, 이미 생성된 ScriptableObject 에셋이나 인스펙터에 저장된 값이 있다면 그 값이 우선 적용된다는 점을 파악
      2-2. 그래서 처음 So에 체력 값을 100 넣은 후 저장. 그 상태에서 다시 스크립트에서 값을 20으로 수정해도 이미 초기 값을 저장했기에 인스펙터에선 100인 상태야
   3. 업계 표준 용어 사용:
      3-1. 무적 기술 재사용 대기시간을 의미하는 용어로 **CoolTime** 보다 글로벌 표준인 **Cooldown** 을 사용하는 것이 적절함을 배움
   4. 코드 개선 사항:
      4-1. 방어적 프로그래밍: 무기 스크립트와 같이 체력, 방어력 스크립트 내 함수 호출 시점에 var stats = playerScript.Stats;와 같이 지역 변수로 최신 데이터를 가져와 데이터의 일관성을 유지함(가장 최신화된 능력치(SO)를 안전하게 가져옴)
      4-2. 옵저버 패턴 유지: 직접적인 UI 참조 (인스펙터에 UI를 드래그&드롭 방식, 싱글톤 패턴으로 참조 등) 없이 이벤트를 통해 상태 변화를 방송하여 객체 간 결합도를 낮춤

Dictionary, Mathf.SmoothStep의 재이해

- SceneName 스크립트에서 쓰인 Dictionary, Mathf.SmoothStep가 아직 이해가 안가서 복습했어.
- SmoothStep과 Lerp의 관계를 머릿속에 그릴 때 이렇게 떠올려보자. 일반 Lerp는 대각선 직선(/)이지만, SmoothStep은 부드러운 곡선(~)이라는 점. 이 차이가 자연스러운 연출의 차이를 만든 거야.

- Dictionary. 딕셔너리는 '열쇠(Key)'를 주면 그에 맞는 '값(Value)' Dictionary<TKey, TValue>:을 바로 꺼내주는 보관함이야.
    //씬 파일 이름과 표시될 이름을 매핑
    private Dictionary<string, string> sceneNames = new Dictionary<string, string>()
    {
    { "GameScene1", "Stage 1" },
    { "GameScene2", "Stage 2" },
    { "GameScene3", "Stage 3 Challenge" },
    { "MainMenuScene", "메인 메뉴" }//이건 사용은 안하지만 일단 씬이 있으니 넣어둔거야
    };
   1. 왜 썼어?: 유니티의 실제 씬 이름은 GameScene1처럼 개발용 이름으로 되어 있어. 하지만 화면에는 유저에게 "Stage 1"이라는 이름을  보여주고 싶지. 이때 딕셔너리가 "GameScene1"이라는 키를 받아 "Stage 1"이라는 값을 연결해 주는 다리 역할을 해
   2. { "GameScene1", "Stage 1" }//{열쇠, 값}
   3. 유니티가 "지금 씬 이름이 뭐야?"라고 물어서 GameScene1을 가져오면, 딕셔너리에서 그 열쇠를 찾아 "아, 화면엔 'Stage 1'이라고 띄울게!" 하고 값을 가져오는 거야
   4. 왜 썼어? (확장성): 만약 if (sceneName == "GameScene1")처럼 조건문을 썼다면, 스테이지가 50개일 때 if문도 50개가 되어야 해. 하지만 딕셔너리는 데이터만 한 줄 추가하면 로직을 건드릴 필요가 없어

- 핵심 메서드: TryGetValue. **딕셔너리와 한세트**
- 보통 딕셔너리에서 값을 꺼낼 때는 "있어?"라고 물어보고(1번), "있으면 가져와!"라고 명령(2번)해야 해. 하지만 TryGetValue는 "있으면 바로 꺼내와!"라고 한 번에 말하는 것과 같아.
   1. 성능: 딕셔너리 안을 한 번만 뒤지니까 컴퓨터가 훨씬 편해해
   2. 안전: 찾으려는 이름이 없어도 에러(빨간 줄)를 내뱉으며 게임이 멈추지 않고, 그냥 "없어!"라고 false만 알려줘
- 내가 쓴 sceneNames.TryGetValue(currentSceneFile, out string displayName); 코드를 사람의 대화로 풀면?
   1. 나: "야, Dictionary! 지금 씬 이름인 GameScene1이라는 글자가 네 주머니에(Key)에 들어있어?"
   2. 딕셔너리:
      2-1. 있으면?: "웅, 있어! 그 짝꿍 이름은 Stage 1이야. 여기 displayName이라는 변수에(지역변수) 담아줄게! (결과는 true)"
      2-2. 없으면!: "아니, 그런 이름은 내 주머니에 없어. 대신 에러는 안 낼게. displayName(지역변수)은 비워둘게. (결과는 false)"
 - 왜 out이라는 글자가 붙을까?: TryGetValue는 원래 "성공했나? 실패했나?"라는 결과값(true/false)만 뱉어내는 함수야.
   1. 그런데 우리는 "성공했다면 그 내용물(Value)도 같이 받고 싶어!"라고 생각하잖아? 그때 쓰는 게 out이야. "결과값은 함수가 가지고, 실제 내용물은 이 displayName 변수로 밖으로(out) 내보내줘!"라는 뜻이지.

- Mathf.SmoothStep: 부드러운 가감속 연출.
   1. 개념: 일반 Lerp는 등속(일정한 속도)으로 움직이지만, SmoothStep은 시작과 끝에 가감속(Ease-in/out)을 자동으로 더해줘
   2. 원리: 0에서 1까지 직선으로 흐르는 시간값을 S자 곡선으로 비틀어주는 필터 역할
      2-1. 시작(t=0 근처): 변화율이 완만해서 천천히 가속해 (Ease-in)
      2-2. 중간(t=0.5 근처): 속도가 가장 빨라져
      2-3. 끝(t=1 근처): 다시 변화율이 줄어들며 부드럽게 안착해 (Ease-out)
   3. 기존에 썻던 방식의 t = t * t * (3f - 2f * t); 코드는 "이게 뭐 하는 수학 공식이지?"라고 한참 함수를 찾아봐야 해
      3-1. 현재로 수정의 Mathf.SmoothStep(0, 1, t); 는 함수 이름을 보는 순간 "아, 부드럽게(Smooth) 움직이게 하려는 거구나!" 하고 의도를 바로 알 수 있어
- 그럼 내 코드에선?:
   1. float t = timer / moveDuration; (0에서 1까지 일정하게 증가하는 값)
   2. float smoothT = Mathf.SmoothStep(0f, 1f, t); (일정한 속도를 부드러운 S자 속도로 변환)
   3. 이 smoothT를 Lerp에 넣어서 위치를 이동시킴

- Lerp: "비율에 따른 위치 배달":
- textRectTransform.anchoredPosition = Vector2.Lerp(startPosition, endPosition, smoothT);//위치 이동
- textRectTransform.localScale = Vector3.Lerp(Vector3.one * startScale, Vector3.one * endScale, smoothT);//크기 조절	
   1. 정의: 두 지점(A, B) 사이의 특정 지점을 비율(t)에 맞춰 계산하는 기능
   2. 역할 분담:
      2-1. SmoothStep: "얼마나 빨리 갈까?" (속도/비율 결정)
      2-2. Lerp: "그래서 지금 정확히 어디야?" (실제 좌표 계산)
   3. 작동 원리:
      3-1. smoothT가 0이면 startPosition(화면 중앙)
      3-2. smoothT가 1이면 endPosition(화면 구석)
      3-3. smoothT가 0.5이면 두 지점의 정중앙 좌표 반환
   4. 효과: 매 프레임(yield return null)마다 변하는 smoothT 값을 Lerp에 넣음으로써, 끊김 없이 미끄러지듯 이동하는 텍스트 이동 완성

- 로직의 흐름: AnimateSceneName() 코루틴은 이 세 단계의 합작품이야.
   1. 기다림: 게임 시작 후(카운트다운 종료 후) delayBeforeStart 변수에 설정된 시간 동안 유저가 스테이지를 인지할 시간 확보
   2. 계산: 매 프레임(yield return null)마다 시간이 흐른 비율(t)을 구함

- 자료구조의 선택 (List vs HashSet):?
- HashSet이란?:
   1. HashSet은 중복을 허용하지 않는 '집합' 개념의 자료구조야
   2. 리스트처럼 순서대로 줄을 세우는 게 아니라, 데이터의 값 자체가 주소가 되는 특수한 방식(해싱)을 사용해
- List와의 결정적 차이 (검색 속도):
   1. List(출석부): 데이터가 많아질수록 Contains로 하나하나 대조하는 시간이 늘어나 (데이터가 N개면 최대 N번 확인)
   2. HashSet (지문 인식기): 데이터가 아무리 많아도 지문을 찍듯? 단 한 번에 해당 데이터가 있는지 찾아내
- 그럼 왜 지금은 List를 썼어? (내 판단 기록)
   1. 데이터 규모: 현재 화살이 관통하는 적은 많아야 20마리 내외로 매우 적어, 계속 Normal 몬스터를 잡지 않고 모으기만 하면 늘어나겠지만 굳이?...인거지. List로도 충분히 빨라
   2. 수명(LifeTime): 강화화살, 검기 투사체는 생성 후 몇 초 안에 파괴되므로, 무거운 HashSet을 생성하는 비용보다 가벼운 List를 쓰고 버리는 게 효율적이라 판단
   3. 디버깅: 개발 단계에서 [SerializeField]로 이 리스트가 담긴 private 변수를 인스펙터에 보이게 해서 통해 실시간으로 피격 대상을 모니터링하며 로직의 정확성을 검증할 수 있었기 때문에 List를 활용
   4. 그럼 언제 HashSet을 쓸거야?
      4-1. 지금 프로젝트 등 화면에 수백 마리의 적이 등장하고, 광역 공격이나 초고속 연사 시스템을 만들 때
      4-2. 중복 체크를 해야 할 대상이 너무 많아서 리스트의 검색 속도가 게임의 프레임(FPS)을 깎아먹기 시작할 때 성능 최적화 카드로 사용 예정

SceneName 스크립트의 딕셔너리 방식 제거 (Dictionary -> Switch)

- 기존의 딕셔너리(Dictionary)와 TryGetValue를 사용해 씬 이름을 매핑했었지만, 씬이 3~4개인 현재 프로젝트 규모에 비해 코드가 복잡하고 직관적이지 않다고 생각해.
- 특히 out 키워드나  string currentSceneFile = SceneManager.GetActiveScene().name; 같은 딕셔너리의 작동 원리를 완벽히 이해하지 못한 채 사용하는 것이 '내 실력'이 아닌 느낌이 들었어...
- 또, 씬 이름이 딕셔너리에 없을 경우, 조용히 파일 이름을 출력하는 대신 확실하게 에러를 띄우고 작동을 멈추는(Fail-fast 원칙) 기능이 필요해. 안되면 안된다고 명확하게 알 필요가 있으니까. 
   1. "안 되면 안 된다고 명확하게 알리는 것"을 프로그래밍 용어로 Fail-fast(조기 실패)라고 한대, 문제가 생겼을 때 뒤로 숨기지 않고 즉시 터뜨려서 개발자가 바로 고칠 수 있게 만드는 아주 좋은 습관이야!

- 해결 방법 (Dictionary에서 Switch 방식으로 변경).
   1. default 케이스를 활용해 등록되지 않은 씬이나 잘못 적은 씬일 경우 Debug.LogError를 호출하고 return으로 이후 로직(위치/크기 애니메이션)을 차단함(명확하게 문제가 있다고 시작적으로 보일 수 있게)
   2. 기존에 적었던 딕셔너리 코드는 주석으로 남겨두어, 추후 프로젝트 규모가 커졌을 때 다시 딕셔너리로 전환할 수 있는 '고민의 흔적'을 보존

- 왜 지금 방식이 최선이야?
   1. 규모의 적정성: 현재 씬은 4개뿐이므로(메인씬은 제외되니 사실상 3개) 딕셔너리의 탐색 성능 이점보다 switch문의 가독성 이점이 훨씬 큼
   2. 확실한 제어: TryGetValue의 bool 반환값을 체크하는 것보다 switch-default 구조가 예외 상황을 시각적으로 더 명확하게 보여줌
   3. 자기 주도적 개발: 'AI딸깍, AI가 이게 좋다고 해서, 무조건 어려운걸로 로직을 짜야 한다는 생각' 이 아니라 '내가 완벽히 이해하고 설명할 수 있는 방식' 을 선택함으로써 내 코드에 대한 책임감을 가짐
	
- 무조건 복잡하고 어려운 문법을 쓰는 게 실력이 아니라, 현재 내 상황에 가장 적합한 도구를 선택하는 것이 실력이라고 생각해. **이해도 제대로 안되는걸 무작정 쓰고 넘어가면 그게 AI 딸깍충인거잖아?**
- 오류가 생겨도 숨기거나 그래도 실행이 되게 하는 것보단 빨간 로그를 띄워 즉시 발견하게 만드는 것이 유지보수에 훨씬 유리해. 그래야 내가 문제를 바로 확인하고 수정 할 수 있겠지.

- 사고의 전환?: 서버는 '만드는 것'이 아니라 '대화하는 것'.
   1. 클라이언트의 역할: 서버 자체를 구축하는 것이 아니라, 서버 개발자가 만들어둔 창구(API)에 데이터를 보내고(Send) 답장을 받는(Receive) 흐름을 설계하는 것, 나는 그 통로를 만드는 역할인거야
   2. 네트워크 매니저(NetworkManager)의 필요성: 아직 만들지는 않았지만....모든 스크립트에서 통신을 처리하는 것이 아니라, 단일 책임 원칙(SRP)에 따라 통신 전담 창구를 만들어 로직을 집중화하는 구조의 중요성은 이미 알고 있어

- 다음을 위한 프로젝트에 적용할 '실전 서버' 로드맵.
   1. 데이터 가공 (JSON): 내가 이미 잘 사용하고 있는 ScriptableObject나 변수 데이터를 서버가 읽을 수 있는 텍스트 형식으로 변환하는 법 익혀보기
   2. 통신 도구 활용: 유니티 내장 기능인 UnityWebRequest를 무전기처럼 사용하는 법 배우기
   3. 백엔드 서비스 활용 (Firebase/SDK): 직접 서버를 짜지 않아도 구글 등이 제공하는 서비스를 활용해 '로그인', '점수 저장' 등을 구현하여 실무적인 서버 연동 경험 쌓기 (만들어보란게 아니야, 뭔지 알고만 있는걸로도 충분할거야)

NetworkManager 서버 통신 스크립트의 안정성 강화

- 오늘 달성한 목표.
   1. 상용 서버가 없어도 HTTP 통신을 테스트할 수 있는 가짜 온라인 서버(JSONPlaceholder) 연동 성공
   2. 인게임 데이터(점수, 이동 레벨, 플레이 시간)를 웹 표준 규격인 JSON 문자열로 변환하는 직렬화(Serialization) 구현
   3. 예측 불가능한 네트워크 환경에 대응하는 실무형 방어 코드 및 예외 처리 시스템 구축

- 현실적인 네트워크 환경을 고려해서(또 내가 서버에 대해 많이 약하기에) **방어 코드 및 예외 처리 로직**을 추가 도입.
   1. request.timeout = 5; : 서버가 응답이 없을 때 무한 대기에 빠져 게임이 멈추는 현상을 방지 (5초 제한)
   2. UnityWebRequest.Result.ConnectionError: 유저의 인터넷 연결이 끊겼을 때의 예외 로그 처리
   3. responseCode == 404: 서버 주소(URL)가 잘못되었을 때 발생하는 에러 분기 처리

- 새롭게 배운 점:
- 함수 내부의 `using` 문법.
   1. 스크립트 맨 위에 쓰는 `using`과 달리, 함수 안에서 `using(오브젝트) { ... }` 형태로 사용하면 괄호가 끝나는 순간 해당 오브젝트를 메모리에서 자동으로 해제(`Dispose`)해 준다는 것을 배움
   2. 네트워크 통신처럼 외부 자원을 당겨쓸 때 메모리 누수(Memory Leak)를 막기 위한 필수적인 실무 장치임을 이해
- 실무 개발의 효율성: 실무에서는 모든 통신 스크립트나 그 외 다른 대부분의 스크립트를 바닥부터 새로 짜는 것이 아닌, 이미 검증된 안정적인 템플릿(프레임워크)을 재활용하고,
   데이터 구조(DTO)에 변수를 추가하는 방식으로 협업한다는 것을 파악. 구조를 통제하는 눈을 기르는 것이 진짜 실력임을 깨달......이건 아직 내가 부족해서 깨닫기에는 많이 부족할거야

- 굳이 using 문으로 감싸서 강제 해제해야 하는 이유? (보충 내용) "통신을 안 하거나 함수가 끝나면 알아서 해제되는 게 아닌가?"에 대한 의문과 해답:
   1. C#에는 자동으로 메모리를 청소해 주는 가비지 컬렉터(GC)가 있지만, **'네트워크 통신'은 유니티 내부가 아닌 컴퓨터 시스템의 물리적인 네트워크 자원(소켓)을 직접 대여해서 쓰는 영역이야**
   2. 이 영역은 C#의 자동 청소부가 손을 대지 못하는 구역이기 때문에, `using` 문을 쓰지 않고 방치하면 통신이 끝난 후에도 컴퓨터 시스템은 해당 자원을 계속 '사용 중'인 것으로 오해
   3. 그러니 결국 데이터 전송이 끝났음에도 메모리 문이 계속 열려 있게 되어 유저의 컴퓨터 자원이 낭비되는 메모리 누수가 발생!
   4. 따라서 데이터 송신 여부와 상관없이, 네트워크 객체를 생성하는 순간 반드시 `using`으로 감싸서 괄호가 끝날 때 시스템 자원의 문을 강제로 닫아주는(`Dispose`) 안전장치가 필수적이야
- 한 줄 요약: 클라이언트 비유로 완벽 이해하기.
   1. 함수 안에 using 없이 UnityWebRequest를 쓰는 것은, Update() 함수 안에 GetComponent()를 넣고 무한 대기시키는 것과 똑같다
   2. Update 내 GetComponent: 매 프레임마다 창고 뒤져보느라 'CPU'를 괴롭힘
   3. using 없는 WebRequest: 통신이 끝났는데도 문을 안 닫아서 '메모리'를 좀먹음

      1-1. currentIndex++를 통해 다음 목표를 즉시 교체하는 로직의 흐름을 이해
      1-2. Index(currentIndex)의 메커니즘(중요!): 인스펙터에 연결된 각 waypoints 오브젝트 리스트의 번호표를 0번부터 하나씩 올리며 다음 목적지를 갱신하는 '순차 이동'의 원리
   2. 벡터 정규화 (dir.normalized): 목표까지의 거리가 멀든 가깝든 상관없이 화살표의 길이를 '1'로 고정
      2-1. 이를 통해 speed 변수 값에 의존한 일정한 직선 속도를 유지하도록 구현
   3. 오차 범위 기반의 도착 판정
      3-1. 컴퓨터의 부동 소수점 오차를 고려해 Distance <= 0.1f 조건을 사용, 목표 지점 근처에 도달했을 때 자연스럽게 다음 경로로 넘어가도록 설정

- 유니티나 C#에서 리스트(List)나 배열(Array)은 첫 번째 칸을 0번이라고 불러. 그래서 네가 인스펙터 창에서 Waypoints 리스트에 오브젝트들을 드래그해서 넣은 그 위쪽 순서부터 차례대로 방문하게 돼.
   1. 시작 (currentIndex = 0):
      1-1. 몬스터는 waypoints[0](리스트의 첫 번째 항목)을 목표로 잡고 움직여
   2. 첫 번째 지점 도착 (Distance <= 0.1f):
      2-1. 0번 지점에 도착하면 currentIndex++를 실행해, 이제 currentIndex는 1이 돼
   3. 두 번째 지점 추적 (currentIndex = 1):
      3-1. 다음 Update 프레임부터 몬스터는 waypoints[1]을 보고 방향을 틀어 (normalized라서 일직선으로만 이동)
   4. 반복:
      4-1. 이런 식으로 0번 → 1번 → 2번 → 3번 → 4번 순서대로 리스트의 끝까지 여행을 떠나는 거야. 완전히 다 도착하면 (현재까진) 마지막 waypoints 오브젝트에서 멈춰
