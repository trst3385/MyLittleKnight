
09/1 
메인화면 씬에서 배경이미지의 원근감을 주기 위해 패럴랙스(Parallax) 스크롤 방식 사용.
메인 메뉴 컷씬 구상: 오락실 게임처럼 메인 화면에 단순한 배경 스크롤뿐만 아니라, 캐릭터와 몬스터가 등장하는 컷씬을 만들기로 결정했어.
MainMenuCutsceneManager 스크립트 생성: 이 스크립트는 컷씬의 전체적인 흐름을 관리하는 역할을 해. 컷씬의 상태를 정의하고, 각 상태에 따라 캐릭터와 몬스터의 행동을 제어할 거야.

- 패럴랙스(Parallax) 스크롤이란?
   1. 패럴랙스 스크롤은 게임에서 원근감과 깊이감을 주기 위해 사용하는 시각 효과를 말해. 화면의 배경 레이어들을 각각 다른 속도로 움직여서, 가까이 있는 물체는 빠르게, 멀리 있는 물체는 느리게 움직이는 것처럼 보이게 만드는 원리
   2. 이 효과는 사람이 현실에서 움직일 때 느끼는 원근감과 동일해. 예를 들어, 내가 차를 타고 갈 때 창밖을 보면 가까이 있는 가로수나 건물은 빠르게 지나가지만, 
   멀리 있는 산이나 구름은 아주 천천히 움직이는 것처럼 보이잖아. 패럴랙스 스크롤은 이 현상을 게임에 그대로 적용한 거지

- 패럴랙스 스크롤의 구현 방법. (오늘 직접 구현한 방법이 바로 패럴랙스 스크롤을 만드는 가장 대표적인 방법이야)
- 배경 레이어 나누기: 배경 이미지를 여러 개의 레이어(예: 하늘, 먼 산, 가까운 숲 등)로 분리해.
- 각 레이어에 스크립트 적용: 각 배경 레이어 오브젝트에 BackgroundScroller 스크립트를 연결해. 이 스크립트는 이미지를 계속 스크롤하는 역할을 해.
- 속도(Speed) 설정: 
   1. 스크립트의 scrollSpeed 변수에 각기 다른 값을 할당해
   2. 가장 멀리 있는 sky, mount는 0.01
   3. 중간에 있는 back은 0.015, mid는 0.03
   4. 앞에 있는 forest는 0.1, 바로 뒤에 있는 forest.short는 0.07
- 이런 방식으로 각 레이어의 속도 차이를 주면, 2D 게임 화면도 마치 겹겹이 쌓인 3D 공간처럼 보이게 돼.


- 이 메인화면에 플레이어와 몬스터를 추가했어. 따로 조작 하진 않고 오락실 게임의 데모화면 처럼 서로 움직이게 만들려고.
- 처음에는 오브젝트가 배경 뒤에 가려져 안 보였는데, Canvas 오브젝트의 Render Mode를 **Screen Space - Overlay**에서 **Screen Space - Camera**로 바꿔서 UI와 게임 오브젝트의 렌더링 순서 문제를 해결했어.
   이렇게 하면 Canvas 컴포넌트에 Sorting Layer와 Order in Layer가 생겨서 렌더링 문제를 해결했지.
- 각 플레이어, 몬스터의 기존에 있던 스크립트는 전부 지웠어. 메인화면에서 쓸꺼니까 기존의 스크립트들은 필요가 없어
- 플레이어, 몬스터에게 각각 MainMenuPlayer, MainMenuEnemy 스크립트를 만들었어. 내부 로직은 똑같은 상태고 생성 후 서로 연결해줬어.
   일단은 두 오브젝트가 움직이게만 만들었어. moveSpeed = 2f; , animator.SetBool("Move", true); , transform.Translate(Vector3.right * moveSpeed * Time.deltaTime);


- MainMenuCutsceneManager. 이 스크립트는 내가 구상한 메인 화면 컷씬의 모든 흐름을 총괄하는 역할을 해.
- 이 스크립트의 가장 중요한 역할은 **enum**을 사용한 상태 머신으로 컷씬의 흐름을 제어하는 거야.

- enum CutsceneState (상태 정의):
   enum은 ChasePlayer, PlayerAttack, ChasePlayer2처럼 컷씬의 각 단계를 이름으로 정의해줘. 이렇게 하면 숫자가 아닌 의미 있는 이름으로 컷씬의 상태를 관리할 수 있어 코드가 훨씬 깔끔해지고 읽기 쉬워져
- Update() 함수 (상태 감시 및 전환):
   1. Update()는 게임이 실행되는 동안 매 프레임마다 실행되잖아? 이 안에 있는 switch 문은 현재 상태(currentState)를 계속 확인하는 역할을 해
   2. case의 역할: 각 case는 현재 상태에 따라 플레이어와 몬스터의 MoveSpeed를 조절해서 누가 더 빠르게 움직일지 결정해. 예를 들어, ChasePlayer 상태에서는 몬스터의 moveSpeed를 플레이어보다 크게 설정해서 추격전을 연출하지
   3. 전환 조건: 각 case 안에는 if (monster.transform.position.x > changeStateX) 와 같은 조건문이 있어. 이 조건이 충족되면 currentState를 다음 상태로 바꿔서 컷씬을 다음 단계로 넘어가게 만들어
- SetState() 함수 (상태 변경 시 설정):
   1. 이 함수는 currentState가 바뀔 때 딱 한 번 호출돼. Update()처럼 매 프레임마다 실행되지 않아
   2. 주요 역할: 바뀐 상태에 맞춰 애니메이션을 바꿔주거나, 숨겨져 있던 오브젝트를 활성화하는 등 한 번만 실행하면 되는 초기 설정 작업을 담당해. 예를 들어, PlayerAttack(스크립트가 아니야!) 상태로 전환될 때 플레이어의 공격 애니메이션 파라미터를 true로 설정하는 역할을 하지

- 결론적으로, MainMenuCutsceneManager 스크립트는 Update()로 컷씬의 흐름을 감시하고, SetState()로 상태에 맞는 설정을 한 번만 적용하며 시나리오를 체계적으로 관리하는 거야!



09/2
지그재그 컷씬 구현. 플레이어와 몬스터가 왼쪽에서 오른쪽, 오른쪽에서 왼쪽, 다시 왼쪽에서 오른쪽으로 이동하는 3단계 컷씬을 완성.
지그재그 컷씬 구현 과정. 플레이어와 몬스터가 쫓고 쫓기는 방향이 꼬여서 제대로 된 컷씬이 나오지 않는 문제.
몬스터 오브젝트 관리 문제: 특정 컷씬에서 몬스터가 보이지 않거나, 여러 몬스터가 함께 나오지 않는 문제.

- MainMenuCutsceneManager 스크립트에서 SetState() 함수를 개선.
   1. 각 컷씬(ChasePlayer, PlayerAttack, ChasePlayer2)이 시작될 때마다 캐릭터들의 시작 위치, 이동 방향, 애니메이션 상태, 활성화 여부를 명확하게 설정하도록 코드를 개선했어
   2. 오브젝트 분리: monster와 EliteMonster 변수를 별도로 만들어, 컷씬에 따라 다른 몬스터를 활성화/비활성화하도록 로직을 분리했어
   3. 불필요한 코드 제거: 초기 문제점의 원인이었던 ResetCutscene() 함수를 삭제하여 코드를 더 깔끔하게 만들었어
- 이 스크립트가 몬스터, 플레이어의 이동속도, 이동 방향, 화면 너머까지 닿으면 다른 컷으로 넘어가는걸 담당해.

- MainMenuEnemy 스크립트 수정
   1. 스크립트 통합: 엘리트 몬스터를 위해 MainMenuEliteEnemy 라는 별도의 스크립트를 만들 필요 없이, MainMenuEnemy 스크립트 하나로 모든 몬스터를 관리하도록 개선했어
   2. 크기(Scale) 변수 추가: 몬스터의 크기를 스크립트에서 직접 제어할 수 있도록 public Vector3 enemyScale = new Vector3(8, 8, 1); 변수를 추가했어. 이제 유니티 인스펙터 창에서 몬스터별로 크기를 다르게 설정할 수 있게 수정했어
   3. 오브젝트 연결 방식 개선: 게임 폴더에 있는 프리팹을 스크립트에 바로 연결하는 대신, 씬에 있는 오브젝트를 연결하는 올바른 방법을 배웠어,
   Elite 몬스터는 3번째 컷씬에서 등장해야 하니까 등장 전까지는 오브젝트를 비활성화 시켰지

- 오브젝트가 왼쪽에서 오른쪽, 오른쪽에서 왼쪽으로 생성되야 하는데 화면 밖을 나가도 왼쪽으로 재생성 되던 문제가 있었어.
- 방향과 위치 통일: 각 컷씬의 시작점과 이동 방향을 SetState() 함수에 통일시켰어. 몬스터, 플레이어 둘 다 같은 방향으로 움직여야 하니까.
   1. ChasePlayer: 왼쪽 (returnPositionX) → 오른쪽 (changeStateX)
   2. PlayerAttack: 오른쪽 (changeStateX) → 왼쪽 (returnPositionX)
   3. ChasePlayer2: 왼쪽 (returnPositionX) → 오른쪽 (changeStateX)
- 몬스터 활성화/비활성화: 몬스터가 컷씬이 끝난 뒤에도 화면에 계속 남아있는 문제를 해결했어.
   각 컷씬이 시작될 때마다 이전에 사용했던 몬스터는 SetActive(false)로 비활성화하고, 새로 사용할 몬스터는 SetActive(true)로 활성화하는 코드를 추가했어.

- SetActive(true, false)란? 게임 오브젝트를 켜거나 끄는 기능.
   1. 쉽게 말하면, 무대 위에 배우가 있는데 조명을 비추면 보이고(SetActive(true)), 조명을 끄면 안 보이게(SetActive(false)) 만드는 것과 같아
   2. gameObject.SetActive(true): 오브젝트를 활성화해서 화면에 보이게 하고, 스크립트가 작동하게 해
   3. gameObject.SetActive(false): 오브젝트를 비활성화해서 화면에서 사라지게 하고, 모든 스크립트와 컴포넌트의 작동을 멈추게 해
- 오늘 만든 컷씬에서 SetActive를 사용했던 이유가 바로 이거야, SetState() 함수에서 컷씬이 바뀔 때마다, 필요 없는 몬스터는 SetActive(false)로 꺼버리고, 새로 등장할 몬스터는 SetActive(true)로 켜서 화면에 보이게 만든 거지.
- monster.gameObject.SetActive()나 EliteMonster.gameObject.SetActive()를 컷 씬마다 얘는 활성화하고 비활성화 하잖아?
   1. 1, 2번째 컷씬에는 일반 몬스터만 쓰니까 monster.gameObject.SetActive(true)를, 대형 몬스터는 안쓰니 EliteMonster.gameObject.SetActive(false)
   2. 3번째 컷씬에는 반대로 일반 몬스터는 안쓰고 대형 몬스터만 쓰니 monster.gameObject.SetActive(false), EliteMonster.gameObject.SetActive(true)를 쓰는거야

- 오늘의 최종 성과
   1. 지그재그 컷씬 구현: 플레이어와 몬스터가 쫓고 쫓기는 3단계 컷씬이 정상적으로 작동해
   2. 코드 최적화: 코드의 중복을 줄이고, SetState() 함수의 가독성을 높였어
   3. 오브젝트 관리 능력 향상: 유니티 씬의 오브젝트와 코드 간의 관계를 더 명확하게 이해하게 됐지!

  
**하지만 MainMenuCutsceneManager스크립트에는 각 오브젝트의 공격 모션이 있지만 작동이 안됐어, 몬스터와 케릭터의 간격이 너무 좁아서 쫒고 쫒기는 느낌이 들지 않아, 메인화면 씬의 배경음악도 못넣었어....
  이건 내일 해결해보자. 오늘도 수고했어**

메인화면 씬의 배경음악 추가.

- 플레이어의 Animator에서 SetBool을 사용했는데도 애니메이션이 계속 반복되는 문제가 있었어, 걷는 모션이 멈추고 계속 공격 모션만 반복되는 문제. 1, 3번째 컷씬은 그냥 좌 우로 걸어가는 모션만 넣으면 됐지만 2번은 공격하는 모션도 넣어야 했어.
- Walk에서 Attack으로 가는 트랜지션과 Attack에서 Walk로 가는 트랜지션의 조건으로 모두 Attack (Bool)이 true일 때로 설정했어. 그리고 Attack에서 Walk로 돌아가는 트랜지션에 **Has Exit Time**을 켜두어, 
  공격 애니메이션이 끝난 후 자동으로 걷는 모션으로 돌아가게 만들었지. 이는 SetBool을 사용했음에도 SetTrigger처럼 한 번만 애니메이션이 재생되는 효과를 냈어.


- 몬스터와 플레이어 간 간격이 너무 좁아. 그래서 쫒고 쫒긴다는 느낌이 없고 나란히 걷는 느낌이 더 강해.

- player.transform.position = new Vector3(returnPositionX, player.transform.position.y, player.transform.position.z); ,  monster.transform.position = new Vector3(returnPositionX - 3, monster.transform.position.y, monster.transform.position.z);
  코드 위해 주석을 달아 어떤 역할인건지 분명하게 적었어.
- player.transform.position
   1. //이 코드는 플레이어를 화면 왼쪽 끝(returnPositionX)으로 이동시키는 역할이야
   2. //몬스터에게 쫓기는 첫 번째 컷씬이 시작될 때 플레이어를 화면 밖에서 등장시키는 데 사용해
- monster.transform.position 
   1. //이 코드는 몬스터를 플레이어보다 -3만큼 더 왼쪽에 위치시키는 역할이야
   2. //이렇게 하면 플레이어와 몬스터 사이에 간격이 생겨서, 몬스터가 플레이어를 쫓는 것처럼 보이게 돼

메인화면 씬의 몬스터 추가, 변수 수정
메인화면 씬의 플레이어의 에니메이터가 같아서 게임씬의 플레이어의 에니메이터가 달라지던 문제

- 메인화면 씬에 보일 몬스터를 추가했어. MainMenuCutsceneManager 스크립트를 수정해
   1. 새로운 몬스터를 담을 public MainMenuEnemy Monster2; 변수 생성, Monster2에 쓸 이동속도 변수도 생성했어
   2. 기존에 있던 몬스터와 같은 로직 복사해 썻어, 그 대상이 Monster2 변수(새로운 몬스터를 담은)이라 기존 로직에 Monster2만 넣은거지!
   3. Monster.transform.position = Monster2.transform.position

메인화면 씬의 게임 시작 버튼 UI 이미지 변경

- 며칠 전 게임씬의 오브젝트를 메인화면 씬에 그대로 복사해버려서 에니메이터 등이 게임씬에서도 달라진 문제가 있었어, 그래서 게임씬의 플레이어의 Die 에니메이터가 없던 문제를 찾았어.
- Player 스크립트의 PlayerDie() 함수를 보면 쉽게 다시 만들 수 있었어.
- 함수의 if (animator != null) if문을 보면 animator.SetTrigger("Die"); 가 있어. 이걸 보고 전에 쓰던 에니메이터의 파라미터는 Trigger 형식의 Die라는 이름의 트랜지션이야.
- 그래서 에니메이터에서 Death. 사망 모션을 다시 추가하고 AnyState->Death로 가는 트랜지션을 추가. 그 트랜지션에 Trigger 형식의 Die 파라미터를 추가했어!

- Any State란? 유니티 애니메이션에서 어떤 상태(State)에 있든지 간에 특정 애니메이션으로 전환할 수 있는 특별한 상태를 말해.
   1. 일반적으로 애니메이션은 A 상태에서 B 상태로, B 상태에서 C 상태로 연결되는 식으로 정해진 경로를 따라가잖아?
   2. 하지만 Any State는 이런 정해진 경로 없이, 게임 오브젝트가 어떤 애니메이션을 재생하고 있든 간에 즉시 새로운 애니메이션으로 넘어갈 수 있도록 해줘
- 언제 사용할까? 주로 게임에서 긴급한 상황에 발생하는 애니메이션을 처리할 때 사용해. 예를 들어...
   1. 플레이어가 공격을 하든, 달리든, 점프를 하든 상관없이 갑자기 적에게 맞아서 **사망(Die)**하는 경우
   2. 플레이어가 걷고 있든, 서 있든, 달리든 **피격(Hit)**을 당하는 경우
- 오늘 내가 다시 만든 플레이어 사망 모션이 바로 Any State를 쓰기에 가장 적합한 예시야. 플레이어가 어떤 동작(걷기, 공격 등)을 하다가 죽음을 맞이하더라도, Die 트리거가 발동되면 즉시 사망 애니메이션으로 전환돼야 하니까.
- 그래서 애니메이터 창에서 Any State에서 Die 애니메이션으로 가는 트랜지션(Transition)을 만드는 거야. 그러면 코드로 animator.SetTrigger("Die")를 호출하는 순간, 현재 재생 중인 애니메이션과 상관없이 바로 사망 애니메이션이 재생돼.

- 그럼 파라미터의 Trigger란? 애니메이터에서 특정 애니메이션을 즉시 한 번만 재생할 때 사용하는 스위치 같은 거야. bool이나 int와 달리, 한 번 사용하면 자동으로 꺼지는 특징이 있지.
   1. 애니메이터에 Trigger 생성: 애니메이터 창에서 Parameters 탭에 Die라는 이름의 Trigger 파라미터를 만들어
   2. 코드로 Trigger 발동: 스크립트에서 animator.SetTrigger("Die"); 코드를 호출해
   3. 애니메이션 재생: 이 코드가 실행되면 Die 트리거가 켜져. 애니메이터는 Die 트리거를 조건으로 가진 트랜지션을 찾아 해당 애니메이션(예: 사망 모션)을 즉시 재생해
   4. 자동 초기화: 애니메이션 재생이 시작되면 Die 트리거는 자동으로 다시 꺼져. 그래서 다음번에 이 코드를 호출하기 전까지는 애니메이션이 다시 재생되지 않아
- 다른 파라미터와의 차이점.
   1. bool: True나 False 상태를 계속 유지해. 달리기 애니메이션처럼 켜진 상태가 유지되어야 할 때 사용하지
   2. int / float: 숫자로 여러 상태를 구분해. 여러 가지 공격 모션처럼 숫자로 상태를 구분할 때 사용하지
   3. Trigger: SetTrigger를 호출하면 단 한 번만 작동하고 바로 초기화돼. 사망이나 피격 모션처럼 일회성 이벤트를 처리할 때 유용해
- 내가 하려는 플레이어 사망 모션은 트리거를 사용하기에 가장 적합한 경우야. 플레이어의 어떤 상태든 상관없이, 죽는 순간 한 번만 사망 애니메이션이 재생되어야 하니까.

   #if UNITY_EDITOR
      UnityEditor.EditorApplication.isPlaying = false;
   #else
      Application.Quit();
   #endif

   2. 대신 #else 아래에 있는 코드인 Application.Quit();만 최종 실행 파일에 포함시켜
   3. 유저가 게임을 실행하다가 ExitButton을 눌러 QuitGame() 함수를 호출하면, 이 코드가 실행되면서 프로그램이 완전히 종료돼
**이처럼 전처리기 지시문은 개발 환경(에디터)과 실제 게임 환경을 구분해서, 각각에 맞는 종료 코드를 실행하게 만들어줘. 그래서 네 스크립트 하나로도 두 가지 환경 모두에서 게임을 올바르게 끌 수 있는 거야**

게임씬에 옵션창 생성(ReStart, Exit, Quit 버튼 추가)

   1. Time.timeScale: 게임의 시간 흐름을 조절하는 변수. 0으로 설정하면 게임이 일시정지되고, 1로 설정하면 정상 속도로 돌아가

- bool isPanelActive = !optionsPanel.activeSelf; 과 optionsPanel.SetActive(isPanelActive);의 역할
- 옵션 패널이 꺼져 있을 때:
   1. optionsPanel.activeSelf는 false가 돼
   2. !false는 true가 되므로, isPanelActive 변수에는 true가 저장돼
   3. 다음 줄인 optionsPanel.SetActive(isPanelActive);가 실행되면, optionsPanel.SetActive(true);가 되면서 패널이 켜지게 되는 거야
- 옵션 패널이 켜져 있을 때:
   1. optionsPanel.activeSelf는 true가 돼
   2. !true는 false가 되므로, isPanelActive 변수에는 false가 저장돼
   3. optionsPanel.SetActive(isPanelActive);는 optionsPanel.SetActive(false);가 되면서 패널이 꺼지게 되는 거지

- 그 밑에 if문 if (isPanelActive) { Time.timeScale = 0f; } else { Time.timeScale = 1f; } 에선 isPanelActive지역변수는 위에서 설명했던 것처럼 옵션 패널의 상태가 '켜지는'지 또는 '꺼지는'지 여부를 담고 있어.
   1. if (isPanelActive): 만약 isPanelActive가 true라면 (즉, 패널이 방금 켜졌다면), 이 코드 블록이 실행돼,
      Time.timeScale = 0f;: 이 코드는 게임의 시간 흐름을 0으로 만들어. 게임 내의 모든 움직임, 애니메이션, 물리 효과 등이 멈추게 되지. 이게 바로 일시정지 기능이야
   2. else: 만약 isPanelActive가 true가 아니라면 (즉, 패널이 방금 꺼졌다면), 이 코드 블록이 실행돼,
      Time.timeScale = 1f;: 이 코드는 게임의 시간 흐름을 **정상 속도(1)**로 되돌려. 멈췄던 게임이 다시 원래대로 흘러가기 시작하는 거지

   2. 옵션 창을 열면 OptionsManager스크립트가 Time.timeScale을 0으로 만들었지만, 카운트다운은 WaitForSecondsRealtime을 사용하고 있어서 게임이 멈췄건 말건 계속 시간이 흘러갔던 거야. 각자 따로의 시간을 가지고 있게 된거야
- 해결책은 아주 간단했어. aitForSecondsRealtime을 WaitForSeconds로 바꿨어.
   1. WaitForSeconds(): 이 함수는 **게임 시간(Time.timeScale)** 에 영향을 받아. 그러니 Time.timeScale이 0이 되면 이 함수도 멈춰.
- 이제 OptionsManager 스크립트에서 Time.timeScale을 0으로 만들었을 때, 카운트다운의 코루틴도 함께 멈추게 돼. 옵션 창을 닫아서 Time.timeScale이 1로 돌아오면, 멈췄던 카운트다운도 다시 진행되지.

09/12 **많은 시도 중 하나의 기록이야. 하지만 결국 문제를 해결 못했어**
게임 시작 시 옵션 창이 바로 뜨고, 끄면 카운트다운 전에 게임이 시작되던 문제 해결 과정.
결국 실패하고 내일 다른 방식으로 해결.

- 게임 씬을 실행했을 때, 옵션 창이 바로 나타났어. 게다가 옵션 창을 닫으면 카운트다운이 끝나기 전인데도 게임이 시작돼버리는 문제가 있었어.
- 이건 OptionsManager와 CountdownManager 두 스크립트가 게임의 시간 흐름(Time.timeScale)을 각자 제어하려고 충돌하면서 발생한 문제였어,
특히 OptionsManager 스크립트가 옵션 창을 닫을 때 무조건 Time.timeScale을 1f로 되돌리는 것이 원인이었지. 이로 인해 CountdownManager 스크립트가 게임을 멈춰놓았는데도, OptionsManager 스크립트가 멋대로 게임을 다시 시작시킨 거야. 

- Time.timeScale이란? 유니티에서 게임의 시간 흐름 속도를 조절하는 데 사용하는 변수야. 이 값은 0부터 1까지의 숫자를 주로 사용하는데, 각각 다음과 같은 의미를 가져
   1. Time.timeScale = 1f;: 이게 기본값이야. 게임 시간이 정상 속도로 흐르지
   2. Time.timeScale = 0f;: 게임 시간을 멈추게 해. 모든 물리, 애니메이션, Update() 함수 등이 정지돼. 일시정지 기능을 만들 때 주로 사용해
   3. Time.timeScale = 0.5f;: 게임 시간이 절반 속도로 느려지지. 흔히 '슬로우 모션' 효과를 만들 때 활용해
   4. Time.timeScale = 2f;: 게임 시간이 2배 빠르게 흘러가. 빨리 감기 기능을 만들 때 쓸 수 있어
**내가 만든 옵션 창의 일시정지 기능은 바로 이 Time.timeScale을 0으로 설정해서 게임을 멈추고, 다시 1로 되돌려서 게임을 재개하는 원리를 이용한 거야.**


- 먼저, 옵션창 문제. 옵션창은 O 버튼을 누르지 않으면 창이 나오면 안돼. 그래서 게임씬 Hierarchy 창에서 OptionsPanel UI를 비활성화 했어. O 버튼을 눌러야 보여야지 계속 보여지고 있으면 안되잖아?
   1. 그래서 OptionsManager 스크립트의 ToggleOptionsPanel() 함수에  bool isPanelActive = !optionsPanel.activeSelf; 와 optionsPanel.SetActive(isPanelActive); 가 있고
   2. Update에 if , else if문으로 옵션창을 켜고 끄는거야


- 카운트다운이 멈추는 문제. CountdownManager 스크립트의 WaitForSecondsRealtime 함수가 실제 시간을 사용하기 때문에, OptionsManager 스크립트의 Time.timeScale을 0으로 만들어도 카운트다운이 멈추지 않아.
- CountdownManager 스크립트에 public static bool isCountdownFinished = false; 라는 정적 변수를 추가해서, 다른 스크립트가 카운트다운이 끝났는지 알 수 있도록 '신호등' 역할을 부여했어.
   1. 카운트다운 코루틴 마지막에 이 변수 값을 true로 바꿔서 카운트다운이 끝났다는 신호를 보내도록 했지
   2. CountdownToStart() 코루틴에  yield return new에 WaitForSecondsRealtime 함수로 바꿔서 Time.timeScale과 관계없이 카운트다운이 진행되도록 했어
- WaitForSecondsRealtime을 사용한 이유? 
   1. WaitForSecondsRealtime은 Time.timeScale과 관계없이 실제 시간을 기준으로 작동해. 그래서 Time.timeScale이 0이 되어도 카운트다운은 멈추지 않고 계속 흘러가지
   2. 내가 겪었던 문제의 핵심은 OptionsManager와 CountdownManager 두 스크립트가 Time.timeScale을 제어하려다 충돌이 났던 거야
   3. WaitForSecondsRealtime을 사용함으로써 CountdownManager는 OptionsManager의 Time.timeScale 제어에 영향을 받지 않고 자신의 역할을 수행할 수 있게 된 거지
- WaitForSecondsRealtime과 WaitForSeconds의 차이
   1. WaitForSecondsRealtime은 실제 시간을 기준으로 대기해. Time.timeScale의 영향을 전혀 받지 않기 때문에, 게임이 슬로우 모션이 되거나 일시 정지되어도 항상 정확히 지정된 시간만큼만 기다려
   2. WaitForSeconds은 유니티의 게임 시간에 맞춰서 대기해. 유니티에는 게임의 속도를 조절하는 Time.timeScale 변수의 영향을 직접적으로 받아
   4. WaitForSecondsRealtime: 게임 일시 정지 메뉴, UI 애니메이션, 로딩 화면처럼 게임의 시간 흐름과 독립적으로 작동해야 하는 기능에 사용해
   5. WaitForSeconds: 적의 공격 쿨타임, 캐릭터 애니메이션 등 게임 플레이의 흐름에 맞춰서 작동해야 하는 기능에 사용해


- OptionsManager 스크립트의 수정:
   1. ToggleOptionsPanel() 함수에서 Time.timeScale을 1f로 되돌릴 때, if (isPanelActive)문의 else 문에서 if (CountdownManager.isCountdownFinished)라는 조건을 추가했어
   2. 이 조건을 통해 OptionsManager는 이제 CountdownManager 스크립트가 보낸 신호(카운트다운 끝) 를 받은 후에만 게임을 다시 시작하도록 만들었어
   3. 또, Hierarchy 창에서 옵션 패널의 체크박스를 꺼서 게임 시작 시 옵션 창이 바로 뜨는 문제를 근본적으로 해결했지
- else문 안에 if문을 또 적은 이유?
   1. 만약 if 문을 빼고 그냥 else 문에 Time.timeScale = 1f;를 넣었다면, CountdownManager스크립트가 보낸 신호(카운트다운 끝)를 무시하고 무조건 게임을 다시 시작하게 돼
   2. OptionsManager는 옵션 창을 닫는 순간, Time.timeScale을 1로 바꿔. CountdownManager 스크립트는 아직 카운트다운 중이라서 Time.timeScale이 0 이어야 하는데, OptionsManager가 멋대로 1로 바꿔버리는 거지
   3. 이러면 이전에 겪었던 것처럼, 카운트다운이 끝나기 전에 게임이 다시 시작되는 문제가 똑같이 발생해!
- else 문 안에 if (CountdownManager.isCountdownFinished)를 넣은 건, 두 스크립트가 협력하도록 만든 거야.
   1. if 문은 **"만약 카운트다운이 끝났다면"**이라는 조건을 확인해
   2. 이 조건이 true일 때만 Time.timeScale = 1f; 코드가 실행돼
- 이 한 줄의 코드가 OptionsManager에게 "야, 지금은 네가 시간을 다시 시작시키면 안 돼, 카운트다운이 끝날 때까지 기다려야 해" , 
  라고 명령하는 역할을 한 거야. else는 단순히 패널이 꺼졌을 때를 의미하고, 그 안의 if는 "패널이 꺼졌는데, 카운트다운도 끝났어?" 라는 더 구체적인 조건을 확인하는 거지.


- 하지만 이렇게 해도 결국 다시 문제는 돌고 돌아. 옵션창을 켜도 카운트는 계속 되고, 카운트가 멈춘게 아닌 게임 자체가 멈추고를 반복이야.

카운트다운 중 옵션창이 켜지지 않게 하는걸로 최종 수정, 카운트다운 중에 옵션창을 클릭하면 텍스트를 띄워서 대기하라 알림.

- 어제에 이어 옵션창과 카운트다운 시간 관련 문제는 다르게 해결했어. 
   1. 카운트다운 중에는 옵션창이 켜지지 않게 하기 (카운트다운 중에 옵션창을 켜는 상황은 잘 없고 시작하자마자 옵션창을 켜면 되니까)
   2. 옵션창 키를 누르면 텍스트가 떠서 잠시만 기다려 달라는 알림 출력

- 안되는 문제의 원인, 개념.
- Time.timeScale의 충돌: 내가 겪은 가장 큰 문제의 원인이었어. Time.timeScale은 게임의 시간 흐름을 제어하는 변수로, 
  이 값을 0f로 설정하면 게임이 일시 정지해. 두 개의 스크립트가 이 변수를 각자 제어하려다 서로의 역할을 방해한 거야.
- WaitForSeconds와 WaitForSecondsRealtime의 차이: 
   1. WaitForSeconds: 게임 시간에 맞춰 대기해. Time.timeScale이 0이 되면 이 함수도 멈춰
   2. WaitForSecondsRealtime: 실제 시간을 기준으로 대기해. Time.timeScale의 영향을 받지 않기 때문에, 게임이 멈춰도 이 함수는 계속 작동하지. 내가 카운트다운을 멈추기 위해 WaitForSeconds를 사용하게 된 이유야
- static 변수(isCountdownFinished): 
   1. CountdownManager 스크립트에 public static bool isCountdownFinished = false;라는 변수를 만들어서, 
   CountdownManager가 카운트다운이 끝났다는 신호를 다른 스크립트에게 보낼 수 있게 했어. 이건 스크립트 간의 협력을 가능하게 하는 중요한 역할이었지


- 해결과정:
- CountdownManager 스크립트는 카운트다운 기능만 담당하게 바꿨어.
- WaitForSecondsRealtime 사용. CountdownToStart() 코루틴에서 yield return new WaitForSeconds(1f);를 **yield return new WaitForSecondsRealtime(1f);**로 바꿨지.
  이렇게 해서 OptionsManager가 Time.timeScale을 0f로 바꿔도 카운트다운은 멈추지 않고 계속 흘러가게 했어.

- OptionsManager 스크립트는 옵션 창을 켜고 끄는 기능만 담당하도록 수정했어.
   1. Update() 함수를 아주 간단하게 바꿨어. 이제 O 키를 누르면 무조건 ToggleOptionsPanel() 함수가 호출돼, 
    if (Input.GetKeyDown(KeyCode.O)) { ToggleOptionsPanel(); }
   2. ToggleOptionsPanel() 함수에서 옵션창을 켜고 끄는 optionsPanel.SetActive(isPanelActive); 로직이 있어서 Update() 함수에 else문이 필요가 없었어
- ToggleOptionsPanel() 함수 수정. 이 함수에 모든 논리를 담았어. if-else 구조를 사용해서 두 가지 상황을 명확하게 분리했지.
   1. 카운트다운 중일 때 (if): isCountdownFinished 변수를 확인해서 카운트다운이 아직 안 끝났다면 경고 메시지를 띄우게 했어
   2. 정상적인 상황일 때 (else): 카운트다운이 끝난 상태라면, 옵션 창을 켜고 끄는 원래 기능을 실행하게 했지
   3. 카운트다운 중일 때 옵션창 키를 누르면 warningText.text = "카운트 중이야! 잠시만 기다려"; 라는 텍스트를 출력해
   4. 카운트다운이 끝나면 이 텍스트는 안쓰는거니 나머지 밑의 로직이 이 if문의 else문에 넣었어

- 게임씬에 warningText UI 생성. 이 UI는 카운트다운 중일때 옵션창 키를 누르면 뜰 텍스트야. 카운트다운 중에는 옵션창을 사용하지 못하게 하는거지.
- 이 UI를 OptionsManager 오브젝트에 있는 OptionsManager 스크립트의 public TextMeshProUGUI warningText;라는 변수에 WarningText UI를 인스펙터 창에서 직접 드래그해서 연결해 줬어.
- 초기 상태 비활성화로 했어. 게임이 시작될 때 이 경고 메시지가 바로 보이면 안 되잖아? 그래서 Hierarchy 창에서 WarningText UI의 체크박스를 해제해서 처음부터 비활성화 상태로 만들어 줬어.

- 처음엔 OptionsPanel UI의 자식으로 WarningText UI를 위치 시켰는데 실행하면 보이지가 않았어, 둘 다 비활성화 상태인데 왜 WarningText만 켜려고 했을 때 안됐을까?
   1. 그 이유는 부모의 상태가 자식에게 미치는 영향 때문이야. 유니티의 Transform 계층 구조는 부모-자식 관계를 따르는데, 이 관계에 다음과 같은 중요한 규칙이 있어
   2. 부모가 활성화되면 자식도 활성화될 수 있어. 하지만, 부모가 비활성화되면 자식은 아무리 활성화를 시도해도 화면에 나타나지 않아
   3. OptionsManager 스크립트에선  warningText.gameObject.SetActive(true)를 호출했어
   4. 하지만 OptionsPanel은 여전히 비활성화 상태였기 때문에, 자식인 WarningText는 **아무리 활성화 명령을 받아도 화면에 나타날 수 없는 상태였던 거야** 마치 전원을 끈 TV에서 화면이 켜지기를 바라는 것과 같아
- 그래서 WarningText를 OptionsPanel 밖으로 옮겨서 둘 사이의 부모-자식 관계를 끊어줬을 때, 
  WarningText가 독립적인 오브젝트가 되어서 제대로 나타날 수 있었던 거야. 이 유니티의 계층 구조와 활성화 규칙을 이해하면 앞으로 비슷한 문제를 만났을 때 훨씬 쉽게 해결할 수 있을 거야.


**Static 다시 이해.
- static 변수는 클래스 자체가 메모리에 로드될 때 (게임 실행할때) 딱 한 번만 메모리 공간을 할당받아. 그리고 그 이후로는 게임이 끝날 때까지 그 메모리 공간에 계속 존재해.
- 예시로 public static float Hp = 100f;라고 선언하면, 게임 시작 시 메모리의 한 구석에 **Hp라는 이름의 100f 값이 담긴 상자 하나가 만들어져**
  이 상자는 PlayerHealth라는 클래스에 소속되어 있지만, 어떤 인스턴스(객체)에도 종속되지 않아. 

- 왜 영향을 받은 상태로 계속 존재할까?: **모든 스크립트가 같은 상자를 바라보기 때문이야**,
  B 스크립트든, C 스크립트든, 모든 스크립트는 PlayerHealth.Hp라는 **단 하나의 상자(메모리 공간)**를 가리키고 있어.
- B 스크립트에서 이 상자에 담긴 값을 100f에서 50f로 바꿨다고 가정해 보자.
   1. PlayerHealth.Hp -= 50f;//Hp 상자 안의 값이 100f -> 50f 로 변경.    예시로 이 코드가 있다고 쳐보자. 이 시점부터 PlayerHealth.Hp라는 상자 안에는 50f라는 값이 들어있게 돼
   2. 이제 C 스크립트에서 PlayerHealth.Hp 값을 확인하면, B 스크립트가 바꾼 그 상자를 그대로 바라보기 때문에 변경된 값인 50f를 읽게 되는 거야
   3. 쉽게 말해 모두가 함께 사용할 수 있는 공용   if (Input.GetKeyDown(KeyCode.O)) { ToggleOptionsPanel(); }
   2. ToggleOptionsPanel() 함수에서 옵션창을 켜고 끄는 optionsPanel.SetActive(isPanelActive); 로직이 있어서 Update() 함수에 else문이 필요가 없었어
- ToggleOptionsPanel() 함수 수정. 이 함수에 모든 논리를 담았어. if-else 구조를 사용해서 두 가지 상황을 명확하게 분리했지.
   1. 카운트다운 중일 때 (if): isCountdownFinished 변수를 확인해서 카운트다운이 아직 안 끝났다면 경고 메시지를 띄우게 했어
   2. 정상적인 상황일 때 (else): 카운트다운이 끝난 상태라면, 옵션 창을 켜고 끄는 원래 기능을 실행하게 했지
   3. 카운트다운 중일 때 옵션창 키를 누르면 warningText.text = "카운트 중이야! 잠시만 기다려"; 라는 텍스트를 출력해
   4. 카운트다운이 끝나면 이 텍스트는 안쓰는거니 나머지 밑의 로직이 이 if문의 else문에 넣었어

   2. 부모가 활성화되면 자식도 활성화될 수 있어. 하지만, 부모가 비활성화되면 자식은 아무리 활성화를 시도해도 화면에 나타나지 않아
   3. OptionsManager 스크립트에선  warningText.gameObject.SetActive(true)를 호출했어
   4. 하지만 OptionsPanel은 여전히 비활성화 상태였기 때문에, 자식인 WarningText는 **아무리 활성화 명령을 받아도 화면에 나타날 수 없는 상태였던 거야** 마치 전원을 끈 TV에서 화면이 켜지기를 바라는 것과 같아

플레이어가 타일맵 밖으로 나가던 문제 해결,
콜라이더를 추가하니 몬스터가 플레이어에게 닿지 않던 문제 해결
메인화면 씬에 타이틀 제목 추가

- 플레이어가 타일맵 밖으로 나가지는 문제를 확인했어.
- 타일맵 가장자리에 Box Collider 2D가 있는 오브젝트를 둬서 플레이어가 나가지 못하게 할려고 했었어, 이 벽 콜라이더들은 Is Trigger를 꺼서 통과하지 못하게 했지.

- 문제 원인:
   1. 콜라이더의 역할 충돌: 플레이어에게 콜라이더가 하나만 있어서, 벽에 부딪히는 물리적 충돌과 몬스터와 겹치는 감지 역할을 동시에 수행할 수 없었어
   2. Rigidbody2D 설정: 플레이어의 Rigidbody2D의 Body Type이 Kinematic으로 되어 있어서, 물리적 충돌(벽에 막히는 것)이 제대로 작동하지 않았어

- 문제 해결 과정:
- 플레이어 오브젝트의 두 개의 콜라이더 역할 분리.
   1. 물리 충돌용 콜라이더 = 새로 추가한 콜라이더. (Is Trigger 끔): 타일맵 벽에 부딪히게 하는 역할
   2. 몬스터 감지용 콜라이더 = 기존의 콜라이더. (Is Trigger 켬): 몬스터에게 닿았을 때 공격 이벤트를 감지하는 역할
- 레이어 충돌 매트릭스 설정.
   1. Player 레이어와 Monster 레이어를 만들고, 서로 충돌하지 않게 설정했어. 플레이어에 Player 레이어, 몬스터에게 Monster 레이어를 달아줬어
   2. Project Settings의 **Layer Collision Matrix** 에서 Player 레이어와 Monster 레이어의 충돌을 비활성화했어
- Rigidbody2D 설정 변경.
   1. 플레이어의 Rigidbody2D에서 Body Type을 Kinematic에서 **Dynamic** 으로 변경했어. 이렇게 해서 물리 충돌용 콜라이더가 타일맵 벽에 부딪혔을 때 제대로 힘을 받아서 멈추게 되었지.

- Kinematic이란? 물리 엔진의 힘을 받지 않고 오직 스크립트로만 움직임을 제어하는 오브젝트야.
   1. 중력이나 외부 충돌에 영향을 받지 않아. 다른 오브젝트를 통과해 버리거나, 다른 Dynamic 오브젝트를 밀어내는 역할은 할 수 있지만 스스로는 밀려나지 않아
   2. rb.velocity나 transform.position을 사용해 코드로만 움직여야 해
   3. 내가 플레이어를 Kinematic으로 설정했을 때는 타일맵 벽과 부딪혀도 물리적인 충돌이 일어나지 않았기 때문에, 그냥 벽을 통과해 버렸던 거야
   4. 게임에서 플레이어를 Kinematic에서 Dynamic으로 바꾼 건, **스크립트 제어(몬스터에게 다가가는 움직임)** 와 **물리적 상호작용(벽에 막히는 것)** 이라는 두 가지 역할을 모두 필요로 했기 때문이지.
- 그럼 Dynamic이란? 물리 엔진의 모든 힘을 받는 일반적인 물리 오브젝트야.
   1. 중력, 힘(AddForce), 충돌에 의해 움직여. 다른 Dynamic이나 Static 콜라이더와 부딪히면 서로 밀어내거나 튕겨 나가
   2. 제어방식: 코드로 rb.velocity나 rb.AddForce를 사용해서 움직이게 할 수 있지만, **물리 엔진이 계산한 결과와 섞이면서 복잡해질 수 있어**
   3. 게임에서 플레이어를 Dynamic으로 바꾸면서, 타일맵 벽에 있는 Is Trigger가 꺼진 콜라이더와 부딪혔을 때 물리적인 힘을 받아서 밖으로 나가지 않고 멈추게 된 거야

빌드 후 메인화면의 배경, 버튼이 안보이던 문제 해결
Start 버튼의 스크립트 이름 변경, On Click() 연결 방식 재이해
무기 교체 기능 삭제, Q 키로 검 공격하게 수정, 게임 시작 후 바로 검 공격이 가능하게 재사용 쿨타임 조정

- 빌드 후 exe 파일을 실행하거나 빌드 후의 유니티 에디터를 보면 메인 화면씬에서 배경화면이나 각 버튼이 안보이고 플레이어, 몬스터만 보이는 문제를 확인했어.
- 원인: 문제는 메인화면 씬의 플레이어가 게임씬의 플레이어 프리팹을 가져와서 그런거야. 복사를 하고 이름과 에니메이터를 바꿔도 게임씬에 있던 프리팹의 자식으로 있던 오브젝트들은 그대로 있었지.
   1. 메인화면의 플레이어의 자식으로 또다른 메인카메라가 있었어. 그래서 메인화면 씬의 메인 카메라가 아닌 플레이어 프리팹의 메인 카메라를 우선으로 보이게 된거지
   2. 그래서 간단했어. 어짜피 메인화면에선 직접 조작을 안하니까 자식으로 있던 메인카메라, ArrowSpawnPoint, SwordPoint, SwordEnergySpawnPoint를 삭제했어
   3. 그 후 빌드를 하니까 정상적으로 메인 화면이 보였어

- 해결 중에 게임을 시작하는 Start 버튼의 스크립트를 MainMenuStartManager 라고 이름을 수정했어.
- On Click() 이벤트의 작동 방식: On Click() 이벤트는 버튼을 클릭했을 때 특정 오브젝트가 가진 스크립트의 함수를 호출하도록 만들어졌어.
- No Function 오류: 네가 스크린샷에서 본 No Function 오류는 Button 컴포넌트에 스크립트 파일 자체만 연결했기 때문이야,
스크립트 파일은 단순히 코드 덩어리일 뿐, 유니티는 어떤 오브젝트가 그 스크립트를 가지고 있는지 몰랐던 거지.
- 오브젝트 연결: GameStartManager라는 빈 오브젝트를 만들고, 그 오브젝트에 MainMenuStartManager 스크립트를 연결했어. 그리고 이 오브젝트 자체를 버튼의 On Click() 이벤트에 끌어다 넣었기 때문에, 
유니티가 '이 오브젝트의 스크립트에서 이 함수를 호출해라'는 것을 정확히 알게 되면서 문제가 해결된 거야.


- 무기 시스템 리팩토링 및 검 공격 로직 개선: 기존 무기 교체 기능을 삭제하고, 검 공격 시스템을 더욱 효율적으로 개선. 
- AttackController 스크립트에서 WeaponSwitchInput() 함수와 ChangeWeapon() 함수를 지웠어. 무기 교체 로직은 이제 필요가 없으니까.
- AttackInput() 함수에서 검 공격은 Q 키로 공격하게 기존의 활 공격의 스페이스바 키와 다르게 수정했어. if (Input.GetKeyDown(KeyCode.Q) && !isAttacking).
- weaponAnimator() 함수에 (WeaponType weaponType) 매개변수를 추가해 기존에는 CurrentWeaponType 변수를 사용해서 어떤 무기 애니메이션을 재생할지 결정했는데,

- ProcessMovementAndAttack() 함수 (몬스터가 플레이어에게 닿았을때 행동할 함수)의 if (isInStopDistance)문에 if (canAttack && !animator.GetBool("Attack"))문을 추가. 
   1. 이 if문에 ApplyTouchDamage()함수를 호출해. 
   2. 이 if문은 쿨타임이 지났고, 공격 애니메이션이 활성화되어 있지 않을 때만 공격 시작하란 뜻이야. 쿨타임이 돌아오기 전까지 다시 데미지를 주지 않아,
     만약 if (canAttack) 조건이 없었다면, 닿아 있는 동안 매 프레임마다 ApplyTouchDamage()가 호출돼서 플레이어가 순식간에 죽었을 거야.
   3. ProcessMovementAndAttack()는 FixedUpdate 함수에서 매 프레임마다 호출되는데, 
     그 안에서 몬스터와 플레이어의 거리가 StopDistance 이내인지 계속 확인하고 있지. 그리고 StopDistance 이내일 때, canAttack 조건까지 만족해야만 ApplyTouchDamage()가 호출되는 거야
   4. 즉, 이 로직을 통해 몬스터가 플레이어에게 접근하면 계속 닿아 있더라도, AttackCooldown으로 설정한 시간마다 한 번씩만 데미지를 주게 되는 거야.
- FixedUpdate()가 매 프레임마다 ProcessMovementAndAttack() 함수를 호출하고, ProcessMovementAndAttack() 함수는 플레이어와의 거리를 계산해.
   1. StopDistance 이내일 때: 몬스터는 움직임을 멈추고, canAttack 조건에 따라 쿨타임마다 ApplyTouchDamage() 함수를 호출하여 데미지를 줘
   2. topDistance를 벗어났을 때: 몬스터는 다시 플레이어를 추격해
   3. 이 로직을 통해 몬스터가 플레이어에게 계속 닿아 있더라도, AttackCooldown으로 설정한 시간마다 한 번씩만    데미지를 주게 되었어

   1. FixedUpdate()에서 ProcessMovementAndAttack()를 호출
   2. ProcessMovementAndAttack() 함수가 플레이어와의 거리를 확인
   3. 거리가 StopDistance 이내이고, AttackCooldown이 지났을 때 ApplyTouchDamage() 함수를 호출해서 데미지를 줘

- 게임 전체에서 유일해야 하는 난이도 정보를 위해 싱글통 방식을(EnemyDifficulty.Instance)
- 시간 체크 및 레벨 증가 로직.
   1. gameTimer 변수는 처음엔 0이지만 실행되면 게임시간으로써 1초마다 1씩 증가, 총 경과 시간을 누적
   2. if(gameTimer >= (currentDifficultyLevel + 1) * statInterval) 조건문을 통해 statInterval변수의 = 20;초 마다 정확히 레벨이 1씩 증가하는 타이밍을 계산
   3. 20초가 지날때마다 currentDifficultyLevel변수를 ++증가. (1씩 증가)를 통해 난이도 레벨을 올리고, UpdateMonsterLevelText() 함수를 호출하여 화면 UI enemyLevelText(Lv.)를 1씩 갱신
- 동시 스폰 개수 조정.
   1. 난이도 레벨이 오를 때마다 SpawnCountIncreasePerLevel =1; 변수를 1 추가, 
   2. Mathf.Min() 함수를 사용하여 아무리 시간이 지나도 동시 스폰 개수가 MaxNormalSpawnCount변수의 5 값을 초과하지 않도록 난이도 상한선을 설정
   3. MaxNormalSpawnCount = 5; 변수로 Normal 몬스터의 최대 스폰 수를 5마리가 넘어가지 않게 조절


- 20초마다 강화되는 전체 몬스터의 스탯
- 게임 시간이 흐를수록 currentDifficultyLevel을 1씩 증가시키고, 이를 바탕으로 Normal, Strong, Elite 등 모든 몬스터의 핵심 스탯을 강화하는 시간 기반 난이도 조절.
- 몬스터 스탯 강화 비율에 강화될 몬스터의 수치 AttackDamage = 0.2f(20%), Health = 0.2f (20%), MoveSpeed = 0.1f (10%) 증가
- GetAdjustedMonsterStat 스크립트에서 최종 값을 Enemy 스크립트의 SetEnmeyStats()함수에서 호출.
   1. EnemyStats 구조체를 통해 Normal, Strong, Elite 각 몬스터 타입의 기본 스탯을 분리하여 정의했습니다.
   2. EnemyDifficulty.Instance를 통해 난이도 관리 시스템에 selectedStats와 StatType (예: StatType.MoveSpeed)을 전달하고, 강화된 수치를 반환
   3. 이 강화된 수치(currentMoveSpeed, currentAttackDamage 등)를 몬스터 객체 내부 변수에 할당함으로써, 시간이 흐를수록 모든 타입의 몬스터가 레벨에 비례하여 강해지는 로직을 완성
   4. 이 구조는 난이도 영향을 받을 스탯과 받지 않을 스탯을 명확히 분리하여, 시스템의 유연성과 명확성을 높였어
   5. switch문을 사용해 현재 몬스터 객체의 enemyType에 따라 해당하는 selectedStats를 유연하게 선택

- 왜 Enemy스크립트가 난이도 관리자를 '호출'했는가?
   1. 이 시스템은 난이도 계산과 적용을 두 개의 스크립트로 명확히 분리하여, 객체지향 설계(OOD)의 핵심 원칙인 단일 책임 원칙과 높은 유연성을 확보
   2. `EnemyDifficulty` 스크립트는 **난이도** 자체에 대한 규칙 **(20초마다 레벨 증가, 스탯 강화 공식)**만을 관리하고, 몬스터의 내부 상태에는 관여하지 않아
   3. `Enemy` 스크립트는 자신의 상태(스탯)를 관리하고, **스폰 시점**에 맞춰 난이도 관리자에게 필요한 **강화 수치**를 직접 요청(호출)하여 적용
   4. 결론: 이 설계는 시스템의 결합도를 낮추고 유지보수를 용이하게 하며, 향후 다양한 몬스터 타입과 복잡한 스탯 구조를 추가할 때도 유연하게 대처할 수 있는 기반이 될거야
