3/3
Enemy 스크립트의 EnemyStats를 class → struct로 리팩토링

- 기존에는 EnemyStats를 class로 사용하고 있었지만, 해당 타입은 행동이나 상태 변화를 가지지 않는 **순수 설정 데이터 묶음** 이라는 점을 다시 생각하게 되었다,
  런타임 중 실제 전투 로직은 currentMoveSpeed, currentAttackDamage 같은 별도 변수에서 관리하고 있었고, EnemyStats는 단순히 “초기값을 담는 그릇” 역할만 수행하고 있었지.

- 이 구조를 명확히 하기 위해 값 타입인 struct로 변경.
  이를 통해:
   1. EnemyStats가 참조 객체가 아닌 “값 데이터 묶음”이라는 의도를 코드 레벨에서 표현
   2. 런타임 상태와 설정 데이터를 더 분리된 개념으로 정리
   3. 기능 변경 없이 내부 구조만 개선하는 리팩토링 경험 축적
- struct로 변경 후 인스펙터 값이 유지되는지도 확인, (코드 내에서 각 스텟 변수의 값은 지웠지만 실질적으로 값을 넣는건 인스펙터에서) 직렬화가 정상적으로 동작하는 것을 확인했고, 기존 기능에 영향이 없음을 테스트로 검증!

- 또한 오늘은 각 몬스터 프리팹에서 스탯을 개별적으로 수정하는 과정이 반복적이라는 점을 전부터 인지했지만 이게 맞는 방법이겠지 하고 넘어갔지만 이젠 이 문제를 해결하기 위해 향후 'ScriptableObject' 를 활용한 스탯 프리셋 구조로 확장하는 방향을 검토하기로 해보자.
   1. ScriptableObject이란게 수십, 수백의 오브젝트의 스텟을 관리, 즉 많이 있을때만 사용한도 생각했었어, 지금 내 몬스터는 3개 뿐이라서 굳이 필요 없다고 생각했거든
   2. 그런데 지금 이 문제가 ScriptableObject를 쓸 이유인거야. 지금은 각 몬스터 프리팹에서 프리팹마다 타입을 정하고 밑에 드롭다운으로 각 타입의 스텟을 조정하고 일일히 번거롭거든
   3. 그래서 내일은 한번에 조정 할 수 있게 ScriptableObject를 추가해보는거야

**몬스터의 각 타입별 스텟을 보다 편히 조정을 할 수 있게 ScriptableObject 방식을 사용해보자. 지금은 타입을 나누는게 너무 번거로우니**




3/4
ScriptableObject 사용 방법 학습 및 몬스터 스탯 관리 구조 개선

- 기존에는 몬스터 스탯을 Enemy 스크립트 내부 변수 + 인스펙터 설정으로 관리했어, 그래서 어제도 struct으로 변경만 했지 결과는 똑같거든. 이 방식은 몬스터 타입이 늘어나면 관리가 번거롭고 수정이 어려웠어,
  그래서 결국! ScriptableObject 기반으로 몬스터 스탯 데이터를 분리하기로 했지.

- EnemyStatsSO ScriptableObject 클래스 생성.
   1. 몬스터 스탯 데이터 정의: 기존의 이속, 플레이어 바로 앞에 도착하는 거리, 공격쿨타임, 데미지, 감지거리, 몬스터 색, 처치 시 점수를 ScriptableObject 클래스로 이동
   2. MoveSpeed, StopDistance, AttackCooldown, AttackDamage, DetectionRange, SpriteColor, ScoreValue

- 몬스터 타입별 스탯 에셋 생성.
   1. ScriptableObject 에셋 생성
   2. EnemyStats_Normal, EnemyStats_Strong, EnemyStats_Elite
   3. 각 몬스터의 이동속도, 공격력, 감지거리, 색상, 점수 등을 에셋에서 관리하도록 설정

- Enemy 스크립트 구조 변경.
- Enemy 스크립트에서:
   1. ScriptableObject(statsData)를 참조하도록 변경
   2. 기존 인스펙터 기반 타입별 스탯 변수 제거
   3. SetEnemyStats()에서 SO 값을 읽어 적용하도록 수정
      3-1. currentMoveSpeed = statsData.MoveSpeed;
      3-2. currentAttackDamage = statsData.AttackDamage;
   4. 또한 난이도 시스템(EnemyDifficulty)과 함께 동작하도록 using은 그대로 유지
- 이제 완성된 EnemyStatsSO 에셋을 각 몬스터 프리팹의 인스펙터에(Enemy 스크립트) 드래그 연결, 이를 통해 프리팹마다 다른 스탯을 간단하게 설정 가능해졌어.


- ScriptableObject는 단순히 데이터만 있는 스크립트라고 생각했는데 실제로는 게임 데이터를 관리하기 위한 매우 중요한 구조라는 걸 재확인.
- 특히:
   1. 데이터와 로직을 분리할 수 있음
   2. 밸런싱 작업이 쉬워짐
   3. 프리팹 설정이 단순해짐
- 처음에는 내 프로젝트에서 ScriptableObject가 굳이 필요한지 의문이 있었지만 실제로 적용해보니 왜 많은 유니티 프로젝트에서 사용하는지 이해했어.
- 결론: 몬스터 스탯 데이터를 ScriptableObject 기반으로 분리해서 프리팹별 스탯 관리와 밸런싱 작업을 쉽게 만들었다!


**우선 순위 중 다른 우선 순위가 있지만 꼭 다음 씬으로 가기 전 등장할 보스 몬스터 추가를 해보자. 새로 에셋을 다운 받기에는 현재의 작품의 이미지와 맞지 않아서 기존의 몬스터의 크기를 확 키우고 색도 다르게 입혀서 만들어보자**
**EnemyDifficulty에서 몬스터 레벨 UI도 옵저버 패턴으로 바꾸자, 아마 장애물 스크립트도 비슷할 수 있으니 가능하면 이것도 같이 옵저버로 변경해보자**

- 핵심 성과 및 변경 사항 요약.
   1. 알림 시스템 리팩토링: EnemyDifficulty와 ItemChestSpawner의 알림 로직을 TextAlimManager로 위임하여 관심사의 분리(SoC) 달성
   2. 이벤트 기반 아키텍처 도입: 직접 참조 대신 Action 이벤트를 활용한 옵저버 패턴 적용으로 클래스 간 의존성 최소화

- 문제 상황 (Troubleshooting).
   1. 강한 결합 문제: 난이도 조절 로직(EnemyDifficulty)과 아이템 스폰 로직(ItemChestSpawner)이 UI 매니저를 직접 참조하여 UI 텍스트를 수정
   2. 채널 혼선: 하나의 알림 전광판에 여러 스크립트가 동시에 접근하면서, 몬스터 강화 알림이 나와야 할 자리에 아이템 메시지가 출력되는 등 데이터가 섞임
   3. 확장성 부재: 새로운 UI 요소가 추가될 때마다 관련 로직 스크립트들을 모두 수정해야 하는 구조적 한계 발생

- 설계적 해결책: 옵저버 패턴과 책임의 분리.
- 1. 옵저버 패턴 도입:
   1. EnemyDifficulty 스크립트을 방송국으로 설정하고 각 강화 레벨, 알림 텍스트 Action<int>, Action<string> 이벤트를 선언, ItemChestSpawner 스크립트에도 적용. public static event System.Action<string> OnItemSpawned;
   2. TextAlimManager 스크립트는 수신처로서 필요한 이벤트만 구독(OnEnable)하고 해제(OnDisable)하도록 설계
   3. 로직 스크립트는 "사건이 발생했다"는 사실만 방송하고, 누가 듣는지는 신경 쓰지 않아 (느슨한 결합 구현)
- UI 매니저의 책임 강화:
   1. TextAlimManager 스크립트가 이제 모든 알림 UI 오브젝트(EnemyDifficulty, ItemChestSpawner) 를 전담 관리하도록 변경
   2. 중복되는 페이드 연출을 공용 코루틴(DisplayFade)으로 통합하여 코드 재사용성 확보
- 전광판(Channel) 분리: 몬스터 강화 알림, 몬스터 강화 레벨, 아이템 알림 UI를 각각 독립된 변수로 할당하여 메시지 혼선 차단

- 최종 결과물 구조. (역할/클래스 명/결합 방식)
   1. 방송국 / EnemyDifficulty, ItemChestSpawner / event Action (느슨한 결합)
   2. 수신 및 연출 / TextAlimManager / 이벤트 구독 및 코루틴 실행
   3. 최종 출력 / TextMeshProUGUI / 매니저에 의한 직접 제어

- 오늘의 기술적 회고.
   1. 강한 결합 vs 필연적 연결: UI 매니저(TextAlimManager)가 내부 UI 오브젝트를 직접 들고 참조 하고 있는(SerializeField) 것은 '강한 결합'이라기보다, 해당 기능을 수행하기 위한 매니저의 **당연한 책임**임을 이해. 중요한 건 로직 간의 독립성을 유지하는 것
   2. 중간 관리자의 필요성: 모든 UI 요소가 직접 방송을 듣게 하는 것보다, TextAlimManager 같은 중간 관리자 스크립트를 두는 것이 관리 포인트를 줄이는 데 훨씬 효율적임을 배웠다
   3. 아직 할게 많아. 전에는 플레이어와 UI에 연결된 방식을 옵저버로 변경했지만 이젠 매니저와 UI를 연결하는것도 옵저버로 바꿔야 하나 고민....저번 주 부터 다음 씬으로 가기 위한 포탈의 등장 조건으로 새로운 보스 몬스터도 기획했는데,
   요 근래 옵저버 패턴, ScriptableObject을 익히느라 계속 미루고 있어....줏대 없는건지, 욕심인건지, 아니면 불안한건지 잘 모르겠어

   1. 영구적인 다운로드 링크: 링크가 바뀌지 않아 포트폴리오를 매번 수정할 필요가 없어
   2. 데이터 분리: 깃허브 저장소(Repository) 내 소스 코드 용량과는 별개로 빌드 파일(바이너리)을 안전하게 보관할 수 있어 저장소가 깔끔함
   3. 사용자 경험(UX) 최적화: 릴리스된 파일의 직접 링크를 걸면, 사용자가 클릭 한 번으로 바로 게임을 다운로드할 수 있음(기존 내 방식과 같은 결과. 포폴에 다운로드 링크를 클릭하면 바로 다운로드)

      3-2. 릴리즈 방식: 깃허브의 전용 배포 서버를 이용하므로 레포지토리 용량 부담이 없고, 릴리즈라는 이름 아래 데이터가 격리되어 관리됨

- 목적:
   1. 버전별 완벽한 백업 역할(코드 복구 가능)
   2. 나중에 오픈 소스 프로젝트가 되었을 때, 다른 사람이 특정 버전의 전체 코드(레포지토리 전체)를 쉽게 가져가서 살펴볼 수 있게 함
   3. 참고: 개발자 본인은 실행 파일(.zip)만 잘 관리하면 되며, 아래의 Source code는 깃허브가 제공하는 부가적인 백업 서비스라고 이해하면 돼

- 검기(SwordEnergy)랑 강화 화살(Enhanced Arrow)이 발사되서 몬스터의 콜라이더 영역에 머무는 프레임 동안 OnTriggerEnter2D가 중복으로 호출되는 현상 발생.
- OnTriggerEnter2D는 이름 그대로 "트리거에 들어가는 순간" 실행되는 함수가 맞아, 하지만 프로그래밍의 세계에서는 '순간' 이라는 개념이 생각보다 정교하지 않아.

- 수정 전의 오해: "한 번만 닿는 거 아니야?": '화살이 몬스터에 닿았다(Enter)'라고 하면, 그 사건이 딱 한 번만 일어날 거라고 생각하지. 하지만 컴퓨터(물리 엔진)의 입장은 조금 달라.
   1. 컴퓨터의 시각: "지금 0.01초(1프레임)마다 화살 위치를 계산 중인데... 에? 이번 프레임에도 몬스터 콜라이더 안에 있네? OnTriggerEnter! 어? 다음 프레임에도 아직 겹쳐 있네? 또 OnTriggerEnter!"
   2. 특히 관통형 투사체는 몬스터의 몸통을 지나가는 '시간'이 길기 때문에, 그 짧은 찰나에 여러 번 "닿았다"는 신호를 보내버릴 수 있는 거야
   3. OnTriggerEnter2D의 진짜 의미는 이 함수는 "충돌이 시작되는 순간"에 호출되는 건 맞지만, 물리 연산의 오차나 프레임 속도에 따라 그 '순간'이 여러 번 겹쳐서 발생할 수 있어

- 그래서 SwordEnergy, Arrow, 스크립트에서 중복 체크 리스트(List)를 추가했어. 상단부에 private List<GameObject> hitEnemies = new List<GameObject>();를 선언.
   1. 각 스크립트의 OnTriggerEnter2D에 몬스터가 발사체와 충돌 시 리스트에 해당 몬스터가 있는지 확인 (Contains)
   2. 이미 있다면 return하여 로직 중단 `if (hitEnemies.Contains(other.gameObject)) return;`
   3. 없다면 리스트에 추가(Add)하고 데미지 처리 `hitEnemies.Add(other.gameObject);`
   3. 결과: 투사체가 몬스터를 완전히 통과할 때까지 단 한 번의 데미지만 들어가도록 보장함

- (쉽게 요약하는Contains과 Add) 리스트(hitEnemies) 생성: 맞은 적들의 이름을 적어둘 장부를 만든다.
- 충돌 발생 (OnTriggerEnter2D):
   1. 확인 (Contains): 리스트에 이 몬스터가 있는가?
   2. 입구컷 (return): 리스트에 있으면 아무것도 안 하고 종료 (데미지 안 줌)
   3. 통과 및 기록 (Add): 리스트에 없으면 데미지를 주고, 리스트에 이름을 적는다
   4. 결과: 몬스터 몸 안을 통과하는 동안 함수가 백 번 실행돼도, 실제 데미지는 처음 딱 한 번만 들어간다


- README에서  수정할곳을 수정하고 각 폴더 이름에 하이퍼링크를 걸어서 바로 그 폴더에 들어갈 수 있게 수정했어.
