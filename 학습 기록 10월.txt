플레이어의 콜라이더가 두개라서 아이템을 획득하면 두번 획득이 되는 버그를 발견했어

- 타일맵의 보이지 않는 벽과 충돌할 콜라이더, 몬스터에게 닿는 콜라이더. 두개가 있었잖아. 그래서 Item스크립트는 이 두 콜라이더에 대해 OnTriggerEnter2D함수가 작동했어.
- 그래서 Item 스크립트에 private bool isUsed = false; 변수를 선언했어.
- OnTriggerEnter2D함수의 첫 부분에 if (isUsed) return; 선언.
   1. 첫 콜라이더가 아이템 오브젝트에 닿으면 OnTriggerEnter2D 함수가 실행
   2. if (isUsed) return; 에서 isUsed가 false이므로 통과
   3. isUsed = true; 코드가 실행돼 (잠금장치 작동)
   4. UseItem()이 호출되어 레벨이 1 증가
   5. Destroy(gameObject); 명령이 내려지지만, 아이템 오브젝트는 아직 남아 있어 (만약 동시에 두 콜라이더와 닿았다면)
- 두번째 콜라이더가 닿으면?
   1. 아이템이 아직 사라지지 않은 짧은 찰나에 콜라이더 B가 아이템에 닿아 OnTriggerEnter2D 함수가 다시 작동
   2. if (isUsed) return; 에서 isUsed가 이미 true라서 조건이 참이 돼
   3. return;이 실행되어 함수가 즉시 종료돼
   4. 뒤에 있는 isUsed = true;나 UseItem() 코드는 실행되지 않아 (중복 획득 완벽 차단)



10/06
Item 스크립트의 private bool isUsed = false; 변수와 if (isUsed) return;란?

- if (isUsed)가 if (isUsed == true)의 축약형이며, isUsed가 true일 때만 return을 실행하여 함수를 즉시 종료시킨다는 원리야.
- isUsed 플래그가 '개별 아이템 오브젝트'에만 적용되는 잠금장치이며, 여러 아이템 동시 획득에는 문제가 없음을 최종 확인했어.
- isUsed는 bool (참/거짓) 타입으로 선언했어. if 문은 무조건 '참(True)' 또는 '거짓(False)'을 판단해야 해

- private bool isUsed = false; = [초기 상태] 이 아이템은 아직 사용되지 않았음을 선언.
- if (isUsed) return;	= [잠금장치 확인] isUsed가 true 라면 (축약형, isUsed == true와 같음) 함수를 즉시 종료(return;). 두 번째 콜라이더의 접근을 막는 핵심 방어 코드야
- isUsed = true; = [잠금장치 작동] 첫 번째 콜라이더가 닿아 획득이 시작되면, 다른 콜라이더의 접근을 막기 위해 상태를 true로 변경.
- Destroy(gameObject); = [최종 제거] 플래그로 중복을 막은 후, 다음 프레임에 오브젝트를 물리적으로 제거하도록 명령.

- return 키워드가 OnTriggerEnter2D 함수 안에서 왜 코드를 멈추게 하는걸까?
   1. 프로그래밍에서 return은 '함수의 실행을 그 자리에서 즉시 중단하고, 함수를 호출한 곳으로 돌아가라'는 명령이야
   2. OnTriggerEnter2D 함수 내부에서 return이 실행되면, 그 함수는 더 이상 아래 코드를 실행하지 않고 즉시 끝나는 거야
   3. 어디로 돌아가냐? OnTriggerEnter2D는 Unity 엔진이 이벤트를 감지할 때마다 호출하는 함수야. return이 되면 Unity는 이 함수가 끝났음을 인지하고 다음 프레임의 다른 작업을 계속 처리하게 돼

- if (isUsed) return;의 효과
   1. 역할: 조건 확인: **isUsed가 true**인지 확인 (이미 아이템이 사용 중인지 확인)
   2. 효과: false일 경우, return 명령을 건너뛰고 아이템 획득 로직을 진행
- return
   1. 역할: 실행 중단: if 조건이 **true**일 경우, 이 return이 실행되어 함수가 즉시 종료
   2. 효과: UseItem()과 Destroy(gameObject) 등 뒤에 있는 모든 코드가 실행되지 않고 중복 획득을 완벽하게 차단

- 결론으로 if (isUsed) return;은 **만약 이 아이템에 이미 획득 플래그(isUsed=true)가 걸려 있다면, 더 이상 아무것도 하지 말고 함수를 여기서 끝내!** 라는 방어적인 잠금장치 역할을 수행한거야!
- OnCollisionEnter2D는 물리적 충돌이 발생했을 때 호출되고, OnTriggerEnter2D는 'Is Trigger'가 활성화된 콜라이더가 다른 콜라이더 영역에 진입했을 때 호출돼. 두 개는 명백히 용도가 달라.

노션 포트폴리오에 문제해결에 새로운 토글 '플레이어의 스케일 변경에 따른 몬스터 추적 오차 해결 및 방어적 로직 구현(Enemy.cs)' 추가

- 초기의 문제였던. 몬스터가 플레이어의 몸 중앙으로 오지 않고 머리 위쪽에 멈춰서 공격을 해. 근데 공격을 하니까 플레이어의 체력이 닳아.
- 몬스터와 플레이어의 크기를 키우니 크기가 커진 만큼 목표 지점이 플레이어의 중앙이 아닌 머리 위로 솟아 플레이어의 중앙에 오지 않았어.
- 그래서 몬스터의 추적 목표를 플레이어의 피봇 지점에서 실제 몸 중앙으로 옮기기 위해, Enemy스크립트에 playerTargetOffsetY 오프셋 변수를 추가했어.
   1. [SerializeField] private float playerTargetOffsetY = -2.7f;
   2. FixedUpdate() 함수://플레이어와의 거리 계산
      Vector3 playerCenterPosition = playerScript.GetCenterPosition();//플레이어의 중앙 위치 가져오기,
      playerCenterPosition.y += playerTargetOffsetY;//Y축 오프셋 적용

- 플레이어 스크립트의 GetCenterPosition(); 함수는 몬스터가 플레이어의 중앙이라고 인식을 해주는 Vector3 함수야
   public Vector3 GetCenterPosition()//몬스터들이 플레이어의 '중앙'이라고 인식하고 추적/공격할 위치
   {                                 //Enemy 스크립트에서 이 함수를 참조
       //BoxCollider2D가 있다면 콜라이더의 중심 사용
       Collider2D playerCollider = GetComponent<Collider2D>();

       if (playerCollider != null)
       {
           return playerCollider.bounds.center;//True일때, 플레이어 오브젝트에 Collider2D 컴포넌트가 붙어 있을 때.
       }
       return transform.position;//false일때, Collider2D 컴포넌트가 붙어 있지 않을 때
   }
- 플레이어 스크립트Player 의GetCenterPosition() 함수를 구현해, 
  오브젝트의 위치(transform.position)가 아닌 BoxCollider2D의 중심(playerCollider.bounds.center)을 추적 기준점으로 사용했어.

- FixedUpdate: 일정한 시간 간격 (기본 0.02초)으로 호출돼.

Rigidbody2D.velocity란? (rb.velocity)
Rigidbody2D.AddForce()란?

- velocity는 2D 물리 엔진에 의해 움직이는 오브젝트의 선형 속도를 나타내는 속성(property).
- Rigidbody2D 컴포넌트가 붙어있는 오브젝트가 현재 얼마나 빨리, 어느 방향으로 움직이고 있는지를 알려주는 Vector2 값인 거야.
   1. 속도(Velocity): 물체의 X축과 Y축 방향의 속도를 나타내. Z축은 2D라서 없어
   2. 물리 적용: 이 값은 중력, 마찰, 다른 물체와의 충돌, AddForce() 같은 힘의 적용 등으로 인해 물리 시뮬레이션에 의해 계속해서 변해
- Player 스크립트의 FixedUpdate()함수에서 rb.velocity를 직접 설정하면, 유니티의 물리 시스템이 다음 FixedUpdate까지 이 속도를 유지해.
   1. 유니티는 내부적으로 (velocity * Time.fixedDeltaTime)만큼 물체를 이동시켜
   2. FixedUpdate() 함수에서 속도를 제어 하면 프레임 속도와 관계없이 `물리 계산이 정확하고 일관되게` 이루어지기 때문에 캐릭터 이동에 가장 적합한 방법이야
   3. FixedUpdate 사용 이유?: FixedUpdate는 유니티 설정에 따라 Time.fixedDeltaTime이라는 정확히 정해진 시간 간격으로 호출되어 물리 시뮬레이션을 위한 고정된 타임스텝을 제공해,
   물리 기반의 이동(속도 설정)은 반드시 이 함수 내에서 처리해야 가장 정확하고 안정적인 결과를 얻을 수 있다는 점을 강조하는 거야
   4. Time.fixedDeltaTime의 역할: 유니티는 물리 시뮬레이션에서 시간을 Time.fixedDeltaTime 간격으로 쪼개서 계산해. 물체의 새 위치 `ΔP는 ΔP=V×Time.fixedDeltaTime` 공식으로 계산되지. 이 계산을 유니티 엔진이 알아서 해줘

- 왜 Time.fixedDeltaTime은 FixedUpdate()함수에서 해야 하는가?
- 1. 물리 시뮬레이션의 일관성.(중요!)
   1-1. Update()의 문제: Update()는 컴퓨터의 성능이나 게임의 복잡도에 따라 호출되는 속도(프레임 속도)가 불안정해. 한 프레임은 0.01초일 수도, 렉이 걸리면 0.1초일 수도 있어,
   움직임을 1프레임에 1미터 이동하게 코드를 짜면, 프레임 속도에 따라 캐릭터가 빠르게 또는 느리게 움직여서 불안정해져
   1-2. FixedUpdate()의 해결책: FixedUpdate()함수는 유니티 설정(Project Settings -> Time)에 있는 Time.fixedDeltaTime 값(0.02초 등)에 맞춰 일정한 시간 간격으로만 호출돼,
   이렇게 하면 물리 엔진이 항상 똑같은 시간(0.02초)을 기준으로 충돌, 중력, 마찰 등을 계산하기 때문에 어떤 컴퓨터에서 실행해도 물리 결과가 예측 가능하고 일관되게 유지돼
- 2. Rigidbody2D.velocity의 작동 방식과 동기화.
   2-1. rb.velocity = (V)라고 설정하는 건 "다음 물리 업데이트까지 이 속도를 써!"라는 명령이야
   2-2. 유니티는 FixedUpdate()함수가 끝난 후에 물리 계산을 시작하고, 이때 설정한 속도 V를 가지고 ΔP=V×Time.fixedDeltaTime 연산을 통해 물체를 이동시켜
   2-3. 즉! velocity를 사용하는 코드를 FixedUpdate 안에 넣어야 네가 의도한 속도 V가 물리 엔진의 고정된 시간 주기와 완벽하게 동기화되는 거야

- 물리 기반의 이동(Rigidbody2D.velocity, AddForce)이나, 충돌 체크, 물리 설정 변경 등 물리 시뮬레이션에 영향을 미치는 모든 코드는 FixedUpdate()함수에 두는 것이 규칙이자 가장 좋은 방법이야.
- FixedUpdate() 함수 안에 Time.deltaTime을 써도 되긴 해. 유니티가 FixedUpdate()함수 안에서는 Time.deltaTime이 자동으로 Time.fixedDeltaTime 값을 반환하도록 해놨거든, 하지만 헷갈리지 않으려면 물리 코드에서는 명시적
  Time.fixedDeltaTime을 쓰는 게 더 명확하지!


- Rigidbody2D.AddForce()는 물체에 힘(Force)을 가해서 속도를 점진적/순간적으로 변화시키는 함수야.
   1. 이 함수는 항상 물체의 질량(Mass)을 고려하고, 힘의 종류(ForceMode2D)에 따라 물체의 가속도를 변화시켜.
   2. 점프, 폭발, 로켓 추진, 그리고 Enemy 스크립트의 TakeKnockback() 함수처럼 넉백 같은 외부 충격 효과를 만들 때 써.
- AddForce와 ForceMode2D의 관계: AddForce를 사용할 때 어떤 방식으로 힘을 줄지 지정하는 게 ForceMode2D야.
   1. Force (기본값): 지속적인 힘. 시간이 지남에 따라 물체가 점점 빨라지게(가속) 만들 때 써. (예: 로켓 엔진), 힘 F는 Time.fixedDeltaTime 동안 지속적으로 적용돼.
   2. Impulse: 순간적인 힘, 충격량. (네 넉백 코드에서 사용했지!) 질량에 비례해 순간적으로 속도를 확 바꿔버려. (예: 총알, 폭발, 넉백),
   Impulse 모드에서는 유니티가 내부적으로 ×1/Time.fixedDeltaTime 같은 계산을 해서, FixedUpdate 주기와 상관없이 항상 일정한 충격을 줄 수 있도록 보정해 줘
- 왜 FixedUpdate에서 써야해?
   1. 원칙은 동일: AddForce가 물체의 속도(Velocity)에 영향을 주므로, 물리 계산의 정확성을 위해 반드시 FixedUpdate() 안에서 호출해야 해
   2. FixedUpdate 밖에서 쓰면 힘이 적용되는 간격이 프레임 속도에 따라 변해서 넉백 거리가 들쭉날쭉해지는 문제가 생길 수 있어

이젠 게임의 `기능적/실질적 변화` 있을때만 재빌드해서 푸시하고 스크립트 코드나 주석을 수정을 할땐 그 파일의 변경할 내용을 GIT 내부에서 수정하고 커밋하고 푸시하자.**

EnemyDifficulty 스크립트의 GetSpawnTime(), GetSpawnCount() 함수를 속성으로 변경,
그로인한 EnemySpawn 스크립트에서 호출 방식 변경

- EnemyDifficulty 스크립트를 불필요한 부분을 수정하기로 했어. GetSpawnTime(), GetSpawnCount() 두 함수를 단순히 값을 반환만 하는 함수는 속성(Property)으로 대체하기로 했어.
- GetSpawnTime(), GetSpawnCount() 함수가 아닌 각각
   1. public float CurrentNormalSpawnTime => currentNormalSpawnTime;
   2. public int CurrentNormalSpawnCount => currentNormalSpawnCount;
   3. 화살표 구문으로 속성으로 추가하고 함수는 삭제

- => 표시란? C#에서 '람다 연산자(Lambda Operator)' 라고 부르는 건데, 속성(Property)에 쓰이면 '람다 표현식(Lambda Expression)' 또는 '식 본문 멤버(Expression-bodied Member)'라고 불러,
  쉽게 설명하면 "이 속성은 값을 계산하는 게 아니라, 그냥 오른쪽 변수의 값을 바로 돌려준다" 는 의미.
   1. get 역할 대신: => 뒤에 있는 코드는 무조건 get 접근자가 호출될 때 실행돼
   2. return 역할 대신: 별도의 return 키워드 없이 뒤에 있는 값(currentNormalSpawnTime)을 즉시 반환하라는 뜻이야
- 왜 이렇게 쓸까?
   1. 코드 간결성: 속성 내부에서 **단 하나의 식(Expression)**만 실행해서 값을 반환할 때, get { return ... } 이렇게 길게 쓸 필요 없이 한 줄로 깔끔하게 정리할 수 있어
   2. 읽기 전용 보장: 이 구문은 set 접근자를 가질 수 없어. 오직 값을 읽는(get) 기능만 제공해서, 이 속성이 **읽기 전용(Read-Only)**임을 코드 자체로 명확하게 보여줘
**쉽게 말하면 따로 계산이나 복잡한 로직을 추가하지 않고, 그냥 CurrentNormalSpawnTime 이걸 쓰면 currentNormalSpawnTime 변수가 가진 값을 그대로 돌려준다는 의미야!**

- 속성을 만들었으니 이 값을 호출한 EnemySpawn 스크립트의 Start()함수에서 로직을 수정해야해.
- Start() 함수의 EnemyDifficulty 스크립트를 호출하는 if (EnemyDifficulty.Instance != null)에서 
- 기존 (함수 호출)
   1. normalSpawnTime = EnemyDifficulty.Instance.GetSpawnTime();
   2. normalSpawnCount = EnemyDifficulty.Instance.GetSpawnCount();
- 변경 후 (속성 접근)
   1. normalSpawnTime = EnemyDifficulty.Instance.CurrentNormalSpawnTime;
   2. normalSpawnCount = EnemyDifficulty.Instance.CurrentNormalSpawnCount;
- 함수를 호출하는게 아닌 속성을 호출한거야.

- 속성(Property)란?
   1. 본질: 변수(Field) 와 다르게 데이터를 저장하는 공간이 아니라, 데이터를 읽거나 쓸 때 실행되는 특별한 함수(메소드) 묶음이야(get 또는 set 접근자)
   2. 접근 방식: 값을 읽거나 쓸 때 get이나 set 함수가 호출돼. 이 함수들을 통해 유효성 검사, 로깅(기록), 데이터 가공 등 추가적인 로직을 넣을 수 있어
   3. 용도: 캡슐화를 위해 사용해. 외부에서는 변수처럼 보이게 하면서, 내부에서는 데이터를 안전하게 관리하고 제어하기 위해 사용하지
   4. 내가 만든 속성은 가장 단순한 형태의 속성인 **'읽기 전용 속성'**이야. `public float CurrentNormalSpawnTime => currentNormalSpawnTime;`
   5. 이 속성은 **외부에서는 이 값을 읽어갈 수 있지만(변수처럼 사용), 쓸 수는 없다(Set이 없음)** 는 것을 확실하게 선언한 거야
   6. 이 덕분에 private 필드(currentNormalSpawnTime)는 외부의 오작동으로부터 안전하게 보호되면서, EnemySpawn 같은 외부 스크립트에게는 변수처럼 편리하게 값을 제공할 수 있게 된 거지. 이게 바로 캡슐화의 핵심이야!
