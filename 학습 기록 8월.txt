- ///는 **문서화 주석(XML documentation comment)**이라고 해서, 스크립트나 함수의 역할을 설명할 때 사용하는 특별한 주석이야. 
  Visual Studio 같은 코드 편집기에서 자동 완성 기능과 연동돼서, 다른 스크립트에서 이 함수를 사용할 때 설명이 바로 뜨게 해줘.
- 예를 들어 PlayerStatsEffects 스크립트에 이런 주석을 달았다고 치자.
  ///<summary>
  ///플레이어의 능력치 강화 및 UI 업데이트를 관리하는 스크립트입니다.
  ///</summary>
- 그리고 PlayerStatsEffects 스크립트를 참조하는 다른 스크립트....그 중에 Item 스크립트엔 PlayerStatsEffects 스크립트를 참조하는  PlayerStatsEffects playerStatsEffects = other.GetComponent<PlayerStatsEffects>(); 가 있잖아?
  Item 스크립트에서 PlayerStatsEffects에 '마우스를 대보면 플레이어의 능력치 강화 및 UI 업데이트를 관리하는 스크립트입니다.' 라고 뜨는거야
- <summary> 태그는 <summary>로 시작하면 반드시 </summary>로 끝나야 해. 이게 XML 문법 규칙이야.

08/08 타일맵 경계 이동 불가 문제 해결 (TilemapEdge 오브젝트 생성)

- 문제 발견: 캐릭터가 타일맵의 왼쪽 경계는 끝까지 이동하지만, 위/아래/오른쪽 경계에서는 미세한 간격을 두고 멈추는 문제가 있었어.
- 타일맵의 Tilemap Collider 2D와 Composite Collider 2D 설정, 플레이어의 BoxCollider2D와 Rigidbody2D 설정을 모두 점검했지만 해결되지 않았어.
   그래서 처음엔 케릭터의 콜라이더 문제였는지 타일팔레트의 에셋들이 문제였는지 몰랐었어


- Composite Collider 2D의 Is Trigger 설정에 따른 현상 분석:
- Is Trigger를 껐을 때:
   1. Composite Collider 2D는 물리적인 '벽' 역할을 해
   2. 이 상태에서 타일맵 콜라이더와 플레이어 콜라이더가 부동 소수점 오차로 인해 미세하게 겹치면서 '끼임' 현상이 발생했고, 물리 엔진이 플레이어의 이동을 멈추게 만들었어. 이것이 TilemapEdge 오브젝트를 만들게 된 근본적인 원인이야.
- Is Trigger를 켰을 때: (해결 상태)
   1. Composite Collider 2D는 물리적인 '벽'이 아닌 '통과 가능한 영역(Trigger)'으로 동작
   2. 플레이어가 타일맵 콜라이더에 닿더라도 물리적으로 막히지 않고 통과할 수 있게 됨
   3. 이 덕분에 타일맵의 가장자리까지 이동할 수 있었지만, Is Trigger가 켜진 상태에서는 충돌이 아닌 감지만 이루어지므로, 내가 수동으로 만든 TilemapEdge 오브젝트가 없었다면 맵 바깥으로 계속 이동했을거야

- 해결 과정:
- 타일맵의 복잡한 자동 콜라이더가 미세한 충돌 오차를 일으킨다는 결론을 내렸고, 타일맵의 충돌 처리를 비활성화하기로 결정했어. 
- TilemapEdge 라는 빈 오브젝트를 생성하고, 그 자식으로 Left, Right, Top, Bottom이라는 4개의 빈 오브젝트를 추가.
- 각 자식 오브젝트에 BoxCollider2D 컴포넌트를 추가하고, (Is Trigger를 켜면 콜라이더를 무시해버려) Scene 뷰에서 콜라이더의 크기와 위치를 수동으로 조정해 타일맵의 외곽에 '보이지 않는 벽'을 만들었어.
- 타일맵의 Composite Collider 2D 의 Is Trigger를 켜서 타일맵의 콜라이더를 무시하게 했어. TilemapEdge 오브젝트의 자식의 콜라이더를 받아야 하니까.
- 이 과정에서 BoxCollider2D를 타일맵 경계에 딱 맞추면 미세한 겹침 현상으로 인해 다시 이동이 막히는 문제를 발견. 이를 해결하기 위해 BoxCollider2D를 타일맵 바깥으로 아주 살짝 띄워서 배치함으로써 충돌 문제를 원천적으로 해결했어.

- 결과:
- 타일맵 오브젝트의 Tilemap Collider 2D와 Composite Collider 2D를 비활성화하고, 수동으로 만든 TilemapEdge 오브젝트의 BoxCollider2D를 통해 완벽하게 경계를 설정하는 데 성공.
- 이로써 타일맵의 미세한 물리적 충돌 문제를 회피하고, 플레이어가 원하는 대로 맵 경계선까지 이동하는 로직을 완성했음.

   [SerializeField] private AudioClip walkSound;      walkSound 변수는 내가 다운 받은 걷기 사운드 파일을 연결하는 변수야. 이것도 인스펙터에서 연결을 시켜줘!

   1. bool isMoving = (horizontalInput != 0 || verticalInput != 0); 로 케릭터가 움직이는지 아닌지를 확인하는 bool타입의 지역변수를 만들었어
   2. 그 밑의  if(isMoving) { }  if문에서 
   if (audioSource != null && walkSound != null && !audioSource.isPlaying)//오디오 컴포넌트와 소리 파일이 모두 연결되어 있고, 현재 걷기 소리가 재생 중이 아니라면, 소리를 재생해! 라는 의미야.
   {
      audioSource.clip = walkSound;
      audioSource.loop = true;//반복 재생
      audioSource.Play();//위의 상태로 사운드 플레이 시작!
    }

- AudioSource.Play()에서 Play()는 유니티에서 오디오 소스 컴포넌트에 할당된 오디오 클립을 재생하는 명령어야. 그냥 소리를 틀어달라고 스크립트로 부탁하는 거라고 생각하면 돼!

   2. 배경음악처럼 반복 재생: audioSource.loop가 true로 설정되어 있으면, 오디오 클립이 끝났을 때 다시 처음부터 재생돼

   4. 네가 걷기 소리를 구현했을 때 audioSource.loop = true;를 썼던 것처럼, Play()는 loop 설정에 따라 다른 방식으로 작동할 수 있는 거지

   { swordAudioSource.PlayOneShot(swordAttackSound); }

- 문제가 생겼어. 로직을 추가하고 실행하니 케릭터가 움직이지 않을때 활, 검 공격시 사운드가 들리지 않았어!

- 유니티에서 GetComponent<T>()는 해당 게임 오브젝트에 붙어있는 컴포넌트 중에서 가장 첫 번째로 발견되는 T 타입의 컴포넌트를 반환해.
- 플레이어 오브젝트에 AudioSource 컴포넌트가 세 개가 있는데, 두 스크립트 모두 Start() 함수가 실행될 때마다 첫 번째 AudioSource 컴포넌트를 가져오게 돼.

   2. PlayerAttack 스크립트의 swordAudioSource 변수에도 **똑같은 첫 번째 AudioSource**가 들어있어

- Player 스크립트의 HandleWalkingSound()함수가 케릭터가 움직이면 사운드를 재생하게 해주는 함수야. 여기서 bool isMoving = (horizontalInput != 0 || verticalInput != 0);
  이 로직이 문제였던지. 즉, 오브젝트의 가장 먼저 있던 걷는 사운드. 그 사운드를 정하는 함수에서 bool 타입의 로직이 문제였던거야.
   1. isMoving이 true일 때: walkingAudioSource.Play()로 걷기 사운드를 재생해.
   2. isMoving이 false일 때: walkingAudioSource.Stop()으로 걷기 사운드를 멈추지.

- 움직이지 않으니 사운드를 내지 않는거지. 또 GetComponent<T>를 쓰면 가장 위에 있던 오디오소스 컴포넌트를 가져오니까 움직이지 않으니 어떤 사운드를 내지 않던거야!!!!!!!

- 해결 방법은 GetComponent<AudioSource> 를 스크립트에 적지 않고 [Header("")]에 있던 [SerializeField] 변수들로만 오디오 컴포넌트를 드래그로 연결시켜주는거야.
**컴포넌트를 쓴다고 모든 컴포넌트의 GetComponent<T>() 를 써야 하는건 아니야!**
- GetComponent<T>()를 사용하는 경우

   2. 이런 컴포넌트들은 GetComponent<T>()로 가져오는 게 더 안전하고 편리해
   3. 코드로 동적으로 컴포넌트를 가져올 때: 다른 오브젝트에 있는 스크립트를 가져와야 하거나, 오브젝트가 생성될 때 동적으로 컴포넌트를 가져와야 할 때 사용해.

   2. 예를 들어, 공격할 때 생성되는 화살 프리팹이나, 점수가 표시될 UI 텍스트 컴포넌트 같은 것들이 여기에 해당해.

08/13 체력회복 아이템 획득 시 사운드 추가, 아이템의 사운드가 들리지 않는 문제 해결

- https://assetstore.unity.com/packages/audio/sound-fx/rpg-essentials-sound-effects-free-227708 사운드 파일 중 하나를 사용했어.
- 처음에는 전에 했던 플레이어, 몬스터처럼 사운드를 쉽게 넣을 수 있는 줄 알았어. 하지만...아이템이 획득하면 바로 사라지는 'Destroy(gameObject);' 때문에 사운드도 들리지 않는 문제가 생겼어.
- 문제점 파악: 아이템이 획득되면 Destroy(gameObject) 코드 때문에 아이템 오브젝트가 즉시 사라지고, 오브젝트에 붙어있던 AudioSource 컴포넌트도 함께 파괴되어 사운드가 재생되지 않는 문제를 발견했어.
- 최종 해결 로직: 아이템 오브젝트와 사운드를 분리하는 방법을 사용했어
   1. 아이템이 획득되면 소리 재생을 전담할 **'임시 게임 오브젝트'**를 코드로 생성했지
   2. 이 임시 오브젝트에 AudioSource 컴포넌트를 추가하고, spatialBlend를 0으로 설정해 2D 사운드가 되도록 했어. 이렇게 해서 카메라와의 거리에 상관없이 항상 일정한 볼륨으로 소리가 나게 했어
     **코드 안에서만 존재하는  AudioSource 컴포넌트야. 인스펙터에서 내가 직접 추가하는  AudioSource 컴포넌트가 아니야!**
   3. 소리가 재생되는 시간만큼만 임시 오브젝트를 유지하고, 소리가 끝나면 자동으로 파괴되도록 Destroy(soundObject, soundToPlay.length)를 사용했어
   4. 아이템 오브젝트는 소리와 상관없이 즉시 Destroy(gameObject)로 파괴했어
- 지속성 vs. 일회성: 플레이어 사운드처럼 지속적으로 존재하는 오브젝트의 사운드와 아이템처럼 일회성으로 사라지는 오브젝트의 사운드 로직이 달라야 한다는 것을 알게 됐어.
- 2D vs. 3D 사운드: AudioSource의 spatialBlend 값을 조절해서 소리 크기를 일정하게 유지하는 2D 사운드와 거리에 따라 소리가 변하는 3D 사운드를 구분하는 방법을 배웠어.
- 코드와 오브젝트 분리: 오브젝트가 파괴되어도 특정 기능(사운드 재생)이 계속 작동해야 할 때는, 해당 기능을 담당할 임시 오브젝트를 코드로 만들어 분리하는 것이 효과적이라는 것을 깨달았지.


- 코드로 컴포넌트를 추가해야 했던 이유!

  이걸 해결하기 위해 우리가 사용한 방법이 바로 소리 재생을 위한 '독립된 임시 오브젝트'를 만드는 것이었어.
   1. GameObject soundObject = new GameObject("OneShotAudio"); : 이 코드로 아이템 오브젝트와는 별개로 소리만을 위한 임시 오브젝트를 만들었어
   2. AudioSource tempAudioSource = soundObject.AddComponent<AudioSource>(); : 그리고 이 임시 오브젝트에 AudioSource 컴포넌트를 코드로 붙여준 거야
- 이렇게 하면 아이템 오브젝트는 Destroy(gameObject)로 즉시 파괴되어 화면에서 사라지더라도, 소리를 재생하는 soundObject는 계속 남아있게 돼.
  그리고 Destroy(soundObject, soundToPlay.length) 코드가 소리가 끝날 때까지 기다렸다가 이 임시 오브젝트를 파괴해주니까, 아이템은 즉시 사라지면서 소리는 끝까지 재생될 수 있었던 거야.
- 컴포넌트를 코드로 추가하는 것은 이런 '일회성' 또는 '임시' 오브젝트에 기능을 부여할 때 아주 유용하게 쓰이는 방법이야.

08/14 이동속도 아이템에 사운드 추가, ItemChest에 이동속도 아이템이 뜨지 않던 문제 해결, 검 아이템 + 활 아이템 + 방어력 아이템에도 사운드 추가, itemChest 오브젝트가 깜빡이는 문제 해결

- https://assetstore.unity.com/packages/audio/sound-fx/rpg-essentials-sound-effects-free-227708 에셋스토어에 이동속도 사운드를 다운 받았어.

- 어제 Item 스크립트에서 아이템을 획득시 사운드를 들리게 OnTriggerEnter2D() 함수에서 많이 고생했잖아? 그래서 스크립트를 수정하지 않아도돼. Item스크립트를 사용하는 아이템 오브젝트는 이 하나의 스크립트에서 관리하니까
   이제 인스펙터에 AudioSource 컴포넌트를 추가 하지 않기로 했잖아? Item 스크립트 내부에서 임시로 만든 오브젝트에 코드 안에서,
   AudioSource tempAudioSource = soundObject.AddComponent<AudioSource>(); 를 추가 했어, 그래서 인스펙터에 컴포넌트 추가는 안해도 돼
- Item_Speed 인스펙터에 헤더의 '아이템 획득 사운드' 에서 MoveSpeedSound 변수에 사운드클립을 드래그해서 추가했어.


- ItemChest의 인스펙터의 ItemPrefabs 배열에 Item_Speed를 연결했는데 상자에서 이동속도 아이템이 나오지 않는 문제를 발견했어. 처음에는 그냥 운이 안좋았나 싶었는데 스폰 시간을 1초로 줄이고 계속 상자를 획득해도 아이템이 뜨지 않는거야!!
- ItemChest 스크립트의 SpawnItems() 함수에서 아이템을 랜덤으로 선택할 때 Random.Range의 max 값이 itemPrefabs.Length가 아닌 ItemSpawnPoints.Length로 잘못 설정되어 있었어.
- 내가 인스펙터에 설정한 아이템 개수(5개)와 스폰 포인트 개수(3개)가 달랐기 때문에, 인덱스 3과 4에 있는 아이템은 상자에서 절대 나오지 않는 버그를 확인했어. 이동 속도 아이템(Item_Speed)이 바로 여기에 있었던 거지.
- 수정 전 코드에서는 아이템 종류를 선택할 때 Random.Range(0, ItemSpawnPoints.Length)를 사용했어.
   1. ItemSpawnPoints.Length는 3이었기 때문에, Random.Range(0, 3)은 0, 1, 2 세 개의 숫자 중 하나만 반환해
   2. 그런데 아이템 배열(itemPrefabs)의 길이는 5였지?
   3. 따라서 itemPrefabs[0], itemPrefabs[1], itemPrefabs[2]만 선택되고, itemPrefabs[3]과 itemPrefabs[4]는 영원히 선택되지 않았던 거야
- 해결방법:

- AudioSource.Play()
   특징: AudioSource 컴포넌트에 할당된 기본 AudioClip을 처음부터 끝까지 재생해
   용도: 배경 음악처럼 길게 계속 재생되는 소리
- AudioSource.PlayOneShot()
   특징: AudioSource가 이미 재생 중인 소리에 영향을 주지 않고, 지정한 AudioClip을 한 번만 재생해
   용도: 총소리, 발소리처럼 동시에 여러 번 발생하거나 겹쳐서 재생되어야 하는 짧은 소리
- AudioSource.PlayClipAtPoint()
   특징: AudioSource 컴포넌트가 없어도, 지정한 **위치(Point)** 에서 AudioClip을 한 번만 재생해. 사운드 재생이 끝나면 자동으로 사라지는 임시 오브젝트를 생성해서 소리를 내
   용도: 몬스터 사망, 아이템 스폰처럼 특정 지점에서 한 번만 발생하는 소리
**이 세 가지는 모두 AudioSource가 필요하지만, Play와 PlayOneShot은 기존 컴포넌트를 쓰고, PlayClipAtPoint는 임시 컴포넌트를 자동으로 만들어서 사용한다는 차이가 있어!**

- OnAttackEnd() 함수를 추가. 이 함수는 공격 애니메이션이 완전히 끝나는 시점에 유니티의 애니메이션 이벤트로 호출되도록 만들었어. 이 함수의 유일한 역할은 isAttacking 변수를 다시 false로 바꿔주는 거야,

- 선언, OnAttackEnd()함수에도 isAttacking은 둘 다 false야. 왜 두 개가 필요할까?
   1. 시작: 게임이 시작되면 isAttacking은 **false**야.
   2. 공격 시작: 플레이어가 공격키를 누르면, isAttacking을 **true**로 바꿔서 "공격 중" 상태로 만들어.
   3. 애니메이션 재생: 공격 애니메이션이 재생돼.
   4. 공격 종료: 애니메이션이 끝날 때 OnAttackEnd() 함수가 호출돼.
   5. 상태 초기화: isAttacking = false; 코드가 실행되면서, "공격 중 아님" 상태로 돌려놓는 거야.
**결론적으로, 하나는 시작 값을 정하는 역할이고, 다른 하나는 동작이 끝났을 때의 상태를 리셋하는 역할이라서 둘 다 꼭 필요해.**

- 에니메이터에서 활 공격의 파라미터는 Trigger인데 검 공격의 파라미터는 Bool이야. 왜 이렇게 따로 해뒀을까? 둘 다 똑같이 공격키를 누르면 실행되는건데
- Trigger (활 공격): Trigger는 일회성 이벤트야. 마치 버튼처럼, animator.SetTrigger()를 호출하면 한 번만 실행되고 자동으로 꺼지지. 활 공격처럼 애니메이션이 단순하고 짧은 경우, 코드가 복잡해지지 않아도 돼서 유용해.
- Bool (검 공격): Bool은 '상태'를 나타내. animator.SetBool("Attack(Sword)", true);를 호출하면, 코드로 false로 바꿔주기 전까지 계속 true 상태를 유지해.
- 왜 검 공격에 Trigger를 쓰지 않았나?:
   1. 검 공격 모션이 연타나 공격 속도 증가와 같은 상황에서 자주 꼬이는 버그가 있었잖아? Trigger는 자동으로 꺼지기 때문에, 우리가 공격 키를 빠르게 연타하면 Trigger가 꺼지기도 전에 다시 켜져서 애니메이션이 꼬이는 문제가 생겼었어
   2. 그래서 더 확실한 제어가 필요했지. Bool을 사용하면 공격이 시작될 때 true로 켜주고, 
   애니메이션이 완전히 끝난 후 OnAttackEnd() 함수에서 직접 false로 꺼줄 수 있어. 이렇게 수동으로 상태를 제어하니 연타를 하거나 공격 속도가 빨라져도 모션이 꼬이는 문제 없이 항상 끝까지 재생되는 거야
**Trigger는 자동으로 껐다 켜지기 때문에 연타에 취약하지만, Bool은 OnAttackEnd() 함수에서 우리가 직접 false로 바꿔주잖아.** 
**이 방법은 애니메이션의 시작과 끝을 완벽하게 제어하기 때문에, 아무리 연타해도 모션이 꼬이지 않고 항상 부드럽게 재생될 수 있어.**
  결론적으로, Bool을 사용하면 코드가 조금 더 들어가더라도 게임의 안정성을 확보할 수 있기 때문에 지금처럼 따로 유지하는 것이 훨씬 더 좋은 방법이야!**

- void 함수에서 return은 두 가지 용법이 있어.
- 값 반환: 함수가 어떤 특정 값을 호출한 곳으로 돌려줄 때 사용해. (예: public int GetScore() { return score; })
- 함수 즉시 종료: 함수를 실행하던 도중에 그 자리에서 바로 함수를 끝내고 싶을 때 사용해. 이 경우 return 뒤에 아무것도 쓰지 않아. PlayerAttack 스크립트의 SwordAttack 함수가 이 용법으로 쓰인 거야.
  SwordAttack 함수는 swordAttackCollider가 연결되지 않았을 때 더 이상 아래 코드를 실행할 필요가 없잖아. 그래서 Debug.LogError를 찍고 return;을 써서 함수를 즉시 종료시킨 거지.
  이렇게 하면 불필요한 코드가 실행되는 것을 막고 오류를 안전하게 처리할 수 있어.

08/24 GetComponent<T>() 와 public 또는 [SerializeField]의 스크립트 참조 방식의 차이, 불필요한 public 변수를 private으로 변경, 인스펙터에 보이게 할 public 변수들을 [Header("")]로 분류, [HideInInspector]의 사용.

- 스크립트를 참조하는 방식 두가지를 내가 섞어서 쓰고 있어. 하나는 참조할 변수를 만들어 인스펙터에 드래그해서 연결하는 방식,
  다른 하나는 스크립트 안에서 추가하는 방식.
- GetComponent<T>()를 쓰는 이유.
   1. GetComponent<T>()는 스크립트가 붙어 있는 바로 그 게임 오브젝트에 있는 다른 컴포넌트(스크립트 포함)를 찾아오는 함수야. 
   **말 그대로 Get Component. 컴포넌트를 가져온다잖아!**
   2. 예시로 playerHealth = GetComponent<PlayerHealth>(); 이 코드는, Player 오브젝트에 있는 PlayerAttack 스크립트가 같은 Player 오브젝트에 있는 PlayerHealth 스크립트를 찾아오라는 뜻이지
   그래서 인스펙터에 직접 연결할 필요 없이 코드로 자동으로 가져올 수 있어.
- public 변수를 쓰는 이유.
   1. 그럼 왜 public 변수도 쓸까? public은 다른 게임 오브젝트에 있는 컴포넌트를 연결할 때 주로 사용해
   2. 예를 들어 PlayerAttack 스크립트가 쏘는 Arrow 프리팹에는 Arrow 스크립트가 붙어 있잖아? PlayerAttack 스크립트는 Arrow 스크립트와 같은 오브젝트에 있지 않으니까 GetComponent()로 바로 가져올 수가 없어
   이럴 때 public 변수를 선언해서 인스펙터에 노출시키고, 거기에 Arrow 프리팹을 직접 드래그해서 연결하는 거야.
- [SerializeField]라는 더 좋은 방법.
   1. public은 다른 스크립트에서도 값을 바꿀 수 있다는 단점이 있잖아? 그래서 나온 게 [SerializeField]야
   2. private 변수를 선언하면서 [SerializeField]를 붙이면 코드는 private이라 안전하게 보호돼, 인스펙터에서는 public처럼 보이니 드래그로 연결할 수 있어
- 결론:
   같은 오브젝트에 있는 컴포넌트를 가져올 때는 GetComponent<T>()를 Start()나 Awake() 함수에서 사용해
   다른 오브젝트에 있는 컴포넌트를 연결할 때는 [SerializeField]와 private 변수를 사용하는 게 가장 좋은 습관인거야!


- public 변수지만 그 스크립트 안에서만 사용되거나

- 이렇게 하면 직접 수정을 할 필요가 없거나 수정하면 안되는 변수들을 인스펙터에 숨길 수 있지. 


- 인스펙터에서도 수정을 할 public 변수들에 [Header("")]를 추가해 잘 분류하게 만들었어.
- public 변수들이 많이 있잖아? 근데 제각각 다른 종류의 변수들이 섞여서 분류를 잘 해놓은거지!

- [HideInInspector]는 말 그대로 public 변수를 인스펙터에 안보이게 하는거야. public 변수는 인스펙터에 보이잖아? 이걸 사용하면 public 변수라도 인스펙터에 안보이게 할 수 있어.
   1. 용도: 변수는 public으로 선언해서 다른 스크립트가 접근해야 하지만, 인스펙터에서 값을 수정하면 안 될 때 사용해
   2. 작동 방식: 이 속성을 변수 위에 붙이면 유니티 에디터는 그 변수를 인스펙터 창에 표시하지 않아. 하지만 변수는 여전히 public 상태를 유지하기 때문에 다른 스크립트에서는 정상적으로 값을 읽거나 쓸 수 있지
**내가 ObstacleBolt 스크립트에서 MoveDirection 변수를 인스펙터에서 숨기면서도 ObstacleSpawner에서 값을 할당하고 싶어 했던 것처럼, [HideInInspector]는 이런 경우에 아주 유용해.**

   2. 만약 EnemyDifficulty 스크립트가 실수로 여러 개 생성되면, 몬스터 스폰 주기나 스탯이 중복으로 계산되어 게임이 꼬일 수 있겠지. 싱글톤은 이런 문제를 미리 막아줘

- 전역 접근성: 
   싱글톤은 어디서든 클래스이름.Instance를 사용해 즉시 접근할 수 있어. EnemySpawn 스크립트에서 EnemyDifficulty.Instance.GetSpawnTime()처럼 한 줄로 깔끔하게 호출할 수 있는 거지.
   if (EnemyDifficulty.Instance != null)
   {
      normalSpawnTime = EnemyDifficulty.Instance.GetSpawnTime();
      Debug.Log($"EnemySpawn: EnemyDifficulty로부터 초기 스폰 주기 {normalSpawnTime}s 가져옴");
   }
   else
   {
      Debug.LogError("EnemySpawn: EnemyDifficulty.Instance를 찾을 수 없어! EnemyDifficulty 스크립트가 씬에 있는지 확인해!");
      normalSpawnTime = 4f;//기본값으로 설정 (오류 방지)
   }


- EnemySpawn 스크립트에서 EnemyDifficulty 스크립트를 직접 참조하는 변수를 선언하지 않았어. 이게 싱글톤 패턴 스크립트의 특징 중 하나야.
   1. 다른 스크립트가 싱글톤 객체를 참조하기 위해 public 변수나 FindObjectOfType를 사용할 필요가 없어. 대신, EnemyDifficulty.Instance를 통해 언제든 필요할 때마다 바로 접근할 수 있어
   2. Start() 함수 안에서 EnemyDifficulty.Instance를 통해 필요한 정보를 가져오고 있어
   3. EnemySpawn 스크립트가 EnemyDifficulty를 인스펙터에서 직접 연결할 필요 없이,
   코드 안에서 **EnemyDifficulty.Instance**를 통해 바로 접근할 수 있어. 이 덕분에 코드가 더 간결해지고, 오브젝트 간의 의존성이 줄어들며, 유니티 에디터에서의 드래그앤드롭 작업도 필요 없게 돼

- 다른 방법 대신 싱글톤을 쓴 이유는 뭘까?
- public 변수 드래그앤드롭을 사용하지 않는 이유:
   1. EnemyDifficulty 스크립트는 UI, 몬스터 스폰 스크립트 등 여러 곳에서 참조해야 해. 모든 스크립트의 public 변수에 일일이 이 스크립트를 드래그해 넣는 건 비효율적이고 실수할 확률이 높아. 또 귀찮지
   2. 그래서 나중에 스크립트가 늘어날수록 관리가 매우 어려워져.
- GetComponent를 사용하지 않는 이유:
   1. 성능 문제: GetComponent나 FindObjectOfType는 게임 오브젝트 전체를 순회하면서 특정 컴포넌트를 찾는 함수야. 이 과정은 성능 비용이 높아서,
      Update() 함수처럼 매 프레임 호출될 경우 게임 성능에 큰 영향을 줄 수 있어. 싱글톤은 이와 달리, EnemyDifficulty.Instance를 통해 이미 준비된 참조를 바로 사용하기 때문에 성능 손실이 없어
   2. 안전성 및 유지보수: FindObjectOfType<EnemyDifficulty>()를 사용하면 씬에 여러 개의 EnemyDifficulty가 있을 때 어떤 것을 가져올지 보장할 수 없어. 또한, 
      오브젝트의 이름이 바뀌거나 씬에서 사라지면 NullReferenceException 오류가 발생할 수 있지. 싱글톤은 객체의 유일성을 보장하고, 씬이 바뀌어도 DontDestroyOnLoad로 객체를 유지시켜줘서 이런 문제를 예방해
   3. 코드 복잡성: 매번 FindObjectOfType 같은 긴 코드를 작성하는 것은 비효율적이고 코드를 지저분하게 만들어
      싱글톤은 EnemyDifficulty.Instance 라는 간결한 코드로 필요한 스크립트에 바로 접근할 수 있게 해줘서 코드를 훨씬 깔끔하게 만들 수 있어
**요약하자면, GetComponent나 FindObjectOfType는 오브젝트를 "찾는" 과정이 필요하지만, 싱글톤은 이미 준비된 "인스턴스" 를 바로 사용할 수 있게 해줘. 이게 가장 큰 차이야**


- { get; private set; }의 역할
- public static EnemyDifficulty Instance { get; private set; }는 참조는 허용하되, 수정은 막는 아주 중요한 역할을 해.
- public get;: 다른 스크립트가 Instance를 통해 EnemyDifficulty 스크립트의 참조(reference)를 읽어올 수 있게 해. 예를 들어, EnemySpawn 스크립트가 Instance를 이용해 GetSpawnTime() 함수를 호출하는 것처럼.
- private set;: Instance 속성에 값을 할당하거나 변경하는 것을 오직 EnemyDifficulty 스크립트 내부에서만 가능하게 해. 이렇게 함으로써 외부에서 싱글톤 객체를 실수로 망가뜨리는 것을 방지하고, 유일성을 확고하게 보장해줘.
- 그냥 get만 적어도 public get으로 인식해
   1. { get; private set; }: 외부에서 읽기는 가능(public get), 쓰기는 불가능(private set)
   2. { get; set; }: 외부에서 읽기, 쓰기 모두 가능(public get, public set)


- 기존에는 private EnemySpawn enemySpawnRef; , private TextAlimManager textalimManager; 선언하고, 
  Start() 함수에 enemySpawnRef = FindObjectOfType<EnemySpawn>(); , textalimManager = FindAnyObjectByType<TextAlimManager>(); 를 써서 두 UI와 오브젝트를 연결했어.
- 오늘 배운대로 이렇게 하면 여러 장점이 있어!
- 성능 향상: 
   1. FindObjectOfType는 게임 시작 시 씬에 있는 모든 오브젝트를 검색해서 찾는 방식이라 비효율적이야
   2. 하지만 [SerializeField]는 게임이 시작되기 전에 이미 유니티 에디터에서 연결이 끝나므로, 코드가 실행될 때 찾는 과정이 아예 없어서 성능이 훨씬 좋아
- 안전성 및 오류 방지:
   1. FindObjectOfType는 찾으려는 스크립트가 씬에 없거나, 오브젝트가 비활성화되어 있으면 null을 반환해서 NullReferenceException 오류가 발생하기 쉬워
   2. [SerializeField]는 인스펙터에서 직접 연결하기 때문에 연결되지 않았을 경우 유니티가 경고를 띄워줘서 실수를 바로 알 수 있고, 실행 중에 참조가 끊어질 위험이 줄어들어
- 직관적인 작업 흐름:
   1. 어떤 스크립트나 오브젝트가 연결되어 있는지 코드를 보지 않고도 인스펙터 창에서 한눈에 확인할 수 있어
   2. 이건 협업하거나 나중에 코드를 다시 볼 때 매우 유용해. FindObjectOfType를 사용하면 코드를 직접 열어봐야만 어떤 스크립트와 연결되는지 알 수 있거든
**요약하자면, [SerializeField] 방식은 성능, 안전성, 가독성 면에서 FindObjectOfType보다 훨씬 뛰어나. 코드를 깔끔하게 유지하고 버그를 줄이는 데 큰 도움이 된다구!**

   PlayerShield playerShield = other.GetComponent<PlayerShield>();

   {

      {
          PlayerShield playerShield = other.GetComponent<PlayerShield>();

- ObstacleBolt 스크립트에서 여기서 other는 발사체와 충돌한 바로 그 오브젝트를 의미해. 발사체가 플레이어에게 닿으면, other는 곧 플레이어 오브젝트가 되는 거지.
- 따라서 other.GetComponent<PlayerShield>()는 "충돌한 오브젝트(플레이어)에서 PlayerShield 컴포넌트를 찾아 가져와" 라는 뜻이 돼.
- 발사체 스크립트에 PlayerShield 스크립트 컴포넌트가 없어도, 충돌한 상대방(플레이어)에게는 스크립트가 있으니 제대로 작동하는 거야. GetComponent<>()는 해당 스크립트가 붙어있는 게임 오브젝트에서만 컴포넌트를 찾을 수 있어.


- ObstacleBolt 스크립트에서 이 발사체에 닿으면 체력, 방어력을 닳게 해. 하지만 [SerializeField] private이나 public으로나 변수를 만들어 인스펙터에 드래그로 연결하는 방법은 이 발사체에선 사용할 수 없어.
프리팹은 씬에 있는 오브젝트를 직접 참조할 수 없기 때문이야. '프리팹(Prefab)'과 '씬(Scene) 오브젝트'의 차이 때문에 생긴 일이지.

- 프리팹 (Prefab)은 설계도. 실체가 없는 상태, 즉 게임 내부에 존재하지 않는 상태인거야.
   1. 프리팹은 게임 오브젝트의 **템플릿(Template)**이야. 게임 프로젝트 폴더에 저장돼 있지
   2. 프리팹은 아직 씬에 존재하지 않기 때문에, 씬 안에 있는 다른 오브젝트를 직접 참조할 수 없어
   3. 네가 발사체 스크립트를 [SerializeField]로 만들었을 때, 유니티는 "아, 이 변수에 씬에 있는 플레이어 오브젝트를 연결해 줘야지" 하고 인식해,
   그런데 발사체는 아직 씬에 없는 프리팹이라서 플레이어와 연결할 수 없었던 거지
- 씬 오브젝트는 실제 건물.
   1. 씬에 있는 오브젝트는 프리팹을 바탕으로 게임에 실제로 배치된 실체야
   2. 이 오브젝트들은 서로를 참조할 수 있어. 예를 들어, 게임 시작부터 씬에 있는 플레이어 오브젝트는 똑같이 씬에 있는 체력 바 UI를 [SerializeField]로 연결할 수 있지

- [SerializeField]는 다른 오브젝트나 스크립트를 연결할 때 아주 좋은 방법이지만, 프리팹이 씬에 있는 오브젝트를 참조할 때는 사용할 수 없어. 이런 경우에는 두 가지 방법으로 문제를 해결할 수 있어.
   1. 충돌 시점에 GetComponent로 찾기: 내가 최종적으로 해결했던 방법이야. 발사체가 플레이어와 충돌하는 순간, other.GetComponent<>()를 사용해서 그 자리에서 바로 필요한 스크립트를 찾아 데미지를 주는 방식이지
   2. 생성 시점에 FindObjectOfType으로 찾기: 발사체가 씬에 생성되자마자(Start()나 Awake() 함수에서) FindObjectOfType<>()를 사용해 플레이어를 찾아서 변수에 저장해두는 방식도 있어

- 상황에 따라 더 효율적인 방법을 선택하면 돼. GetComponent는 충돌이 일어나는 특정 순간에만 필요할 때 좋고, FindObjectOfType은 게임이 시작될 때부터 계속 참조해야 할 때 유용해.
- Bolt1 프리팹은 ObstacleSpawner가 자신을 복제하는 순간, 즉 런타임(Runtime) 이 되어서야 비로소 씬에 나타나. 
그때 플레이어와 충돌할 수 있게 되는 거지. 그래서 충돌이 일어나는 OnTriggerEnter2D 함수 안에서 GetComponent를 사용해 플레이어 스크립트를 찾는 방식이 가장 안전하고 효율적인 거야.

- 하지만 반대로 ObstacleSpawner 스크립트의 경우는 반대지. 실체가 없는 Bolt1 발사체를 연결해 시간마다 맵에 스폰되게 하잖아.
- ObstacleSpawner 스크립트는 씬 뷰에 존재하는 ObstacleSpawner_OBJ 게임 오브젝트에 붙어있지. 반면에 발사체 프리팹 Bolt1은 프로젝트 폴더에만 있는 프리팹 에셋이야. 
- 씬 오브젝트(ObstacleSpawner 스크립트)는 프리팹 에셋(Bolt1)을 참조할 수 있어, 하지만 프리팹 에셋(ObstacleBoltPrefab)은 씬에 있는 오브젝트 등을 참조할 수 없어.

- PlayerAttack 스크립트를 AttackController로 이름을 바꿨어.
- PlayerAttack 스크립트 이름을 AttackController로 바꾼 이유?
   1. 원래 PlayerAttack 스크립트는 플레이어의 공격에 관련된 모든 것을 처리했어. 하지만 검과 활이라는 여러 무기에 대한 로직을 추가하니, 하나의 스크립트가 모든 무기의 쿨타임, 애니메이션, 공격 효과 등을 다루는 건 너무 복잡해졌지
   2. 그래서 스크립트의 역할을 더 명확하게 만들기 위해 이름을 AttackController로 바꿨어. Controller라는 이름처럼, 이 스크립트는 플레이어의 입력을 받고 어떤 무기를 쓸지 결정하는 '조종' 역할만 하게
- 스크립트를 분리해야 하는 이유? 전까진 이 스크립트가 '단일 책임 원칙(Single Responsibility Principle)'을 위반하고 있어. 하나의 스크립트가 너무 많은 일을 하고 있거든.
   1. 가독성 및 유지보수: 지금처럼 한 스크립트에 모든 게 있으면 나중에 활 공격 로직만 수정하고 싶어도, 검 공격 코드까지 다 확인해야 해서 실수하기 쉬워.
   2. 재사용성: 만약 다른 캐릭터에 활 공격만 적용하고 싶다면? PlayerAttack 스크립트 전체를 가져가야 하는데, 그러면 검 관련 코드까지 불필요하게 따라오게 돼.
   3. 협업 용이성: 만약 팀으로 개발한다면, 활 담당 개발자와 검 담당 개발자가 동시에 한 스크립트를 수정하다가 충돌이 일어날 가능성이 높아.


- 활/검 공격 로직을 별도의 스크립트로 만든 이유.
- 이건 '책임 분리' 라는 디자인 원칙을 적용한 거야. 무기마다 고유한 공격 방식(활 공격, 검 공격), 쿨타임, 데미지 등 세부적인 로직이 달라. 이 모든 걸 AttackController 하나에 다 넣으면 코드가 너무 길고 복잡해져.
- 그래서 다음과 같이 역할을 나눈 거야.
   1. AttackController: Input.GetKeyDown(KeyCode.Space) 같은 키보드 입력을 감지하고, 각 무시 스크립트에게 전달해 공격 되지는지 안되는지 확인하고 가능하면 공격이 가능하게 해,

   3. SwordWeapon: 검 공격에 대한 모든 것 (쿨타임 계산, 대미지, UI 업데이트 등)을 책임지는 역할을 해

08/29 검 공격 모션 딜레이 문제 해결(바로 공격이 가능하게 모션 시간을 줄임), Loop Time과 Has Exit Time 차이, 에니메이터의 Any State의 역할.

- 검 공격 모션 Attack01에 불필요한 빈 시간이 있어서 공격 키를 눌러도 바로 모션이 나오지 않았어. 공격키를 누르면 바로 공격이 되야 하는데 아주 잠깐의 딜레이가 있어.
- 처음에는 모션 클립 속도를 빠르게 했어. 근데 이건 내가 원하던 방식이 아니야. 모션이 빨라졌을뿐 필요없는 모션은 그대로 있는거잖아.
- 애니메이션에서 Attack01 검 공격 클립의 다이아몬드 모양의 키프레임을 시작점(0:00)에서 내가 원하던 지점 (약0:08초) 으로 옮겨서 딜레이를 없앴어.
   1. 이것도 처음엔 하얀색 세로줄(재생 헤드)만 옮길려고 했어, 근데 이건 단순히 재생위치를 나타내는것 뿐이야
   2. 애니메이션의 실제 동작은 그 아래 있는 다이아몬드 모양의 키프레임들이 결정해
- 이렇게 문제는 해결하니 움직일때나 몬스터들이 가까이 붙어서 급한 상황에서 바로 검 공격을 하면 데미지, 넉백, 검기 발사체가 작동하게 되서 더욱 깔끔해졌어.


- Loop Time (애니메이션 클립 설정). 이건 애니메이션 클립 자체가 어떻게 동작할지를 정하는 설정이야.
- 기능: Loop Time에 체크하면, 애니메이션이 끝까지 재생된 후 다시 처음으로 돌아가서 무한 반복돼.
- 용도: Idle (가만히 서 있는) 모션이나 Walk (걷는) 모션처럼 계속 반복되어야 하는 애니메이션에 사용해.
- 내 경우엔 검 공격 모션에 Loop Time이 체크되어 있으면, 공격 모션이 한 번 끝나도 계속 반복되려고 해서, 다른 상태로 넘어가지 못하고 제자리에서 공격 모션을 계속하는 것처럼 보였던 거야.

- Has Exit Time (트랜지션 설정). 이건 트랜지션(상태와 상태를 잇는 화살표) 이 어떻게 동작할지를 정하는 설정이야.
- 기능: Has Exit Time에 체크하면, 트랜지션이 '현재 재생 중인 애니메이션이 끝날 때까지 기다려' 라고 명령해. 애니메이션이 끝나는 순간 다음 상태로 넘어가지.
- 용도: 공격 모션처럼 한 번만 재생되고 끝나야 하는 애니메이션에 사용해. 만약에, Idle 상태에서 Attack1, 3(검, 활 공격) 상태로 넘어갈 때 이걸 체크 해제하면 공격 키를 누르자마자 즉시 공격 모션이 나오고, 
  Attack 상태에서 Idle 상태로 돌아올 때 이걸 체크하면 공격 모션이 완전히 끝난 후에야 Idle로 돌아오게 돼.
- 내 경우엔 Attack 모션이 끝나는 걸 기다렸다가 Idle로 돌아와야 하는데, Attack 모션 자체가 Loop Time 때문에 끝나지 않으니 Has Exit Time이 아무리 기다려도 트랜지션이 발동되지 않았던 거야.

**Loop Time: 애니메이션 클립의 무한 반복 여부를 결정해. (계속 반복 재생할 거야? 아니면 한 번만 재생하고 끝낼 거야?)**
**Has Exit Time: 트랜지션의 발동 타이밍을 결정해. (현재 모션이 끝나는 걸 기다렸다가 다음 모션으로 넘어갈 거야? 아니면 즉시 넘어갈 거야?)**

- 그럼 Walk. 걸을때의 모션이나 Die. 죽을때 모션에선 어떻게 쓰냐?
- 걷기 모션은 캐릭터가 걷고 있는 동안 계속해서 반복되야 해.
   1. Loop Time: 걷기 애니메이션 클립(Walk.anim)에는 **Loop Time에 반드시 체크해야 해** 이렇게 하면 캐릭터가 걷고 있는 동안 애니메이션이 자연스럽게 계속해서 반복될 거야
   2. Has Exit Time: 보통 걷기 모션에서 Idle이나 공격 모션으로 넘어갈 때는 키 입력을 기반으로 바로 전환돼야 하기 때문에, 트랜지션 화살표의 Has Exit Time은 보통 체크하지 않아 (예: Walk -> Attack 트랜지션)
- 정리: 걷기 모션은 Loop Time을 켜서 반복시키고, 다른 모션으로 넘어갈 때는 Has Exit Time을 꺼서 즉시 전환되게 만들어.

- 죽음 모션은 한 번만 재생되고 끝나야 하잖아. 캐릭터가 죽었는데 계속 죽는 모션이 반복되면 이상하겠지?
   1. Loop Time: 죽음 애니메이션 클립(Die.anim)에는 Loop Time을 반드시 꺼야 해
   2. Has Exit Time: 죽음 모션으로 넘어갈 때는 대부분 Any State에서 바로 Die로 트랜지션해. 이때 Has Exit Time은 필요 없어 (어차피 한 번만 재생되면 되니까)
- 정리: 죽음 모션은 Loop Time을 끄고, 다른 모션으로 돌아올 필요가 없기 때문에 죽음 모션에서 다른 모션으로 돌아오는 트랜지션도 만들지 않아.

- 애니메이션 클립 설정 (Loop Time)
   1. 걷기 (Walk): 켬 (무한 반복)
   2. 죽음 (Die): 끔 (한 번만 재생)	
   2. 공격 (Attack): 끔 (한 번만 재생)
- 트랜지션 설정 (Has Exit Time)
   1. 걷기 (Walk): 끔 (키 입력 시 즉시 전환)
   2. 죽음 (Die): 신경 쓸 필요 없음 (보통 돌아오는 트랜지션 없음)
   3. 공격 (Attack): 켬 (애니메이션 끝까지 기다렸다가 돌아옴)


- Any State의 역할. 말 그대로 '어떤 상태에서든' 이라는 뜻이야.
- dle, Walk, Die 등등, 현재 어떤 애니메이션이 재생되고 있든 관계없이, Any State에 연결된 트랜지션의 조건이 만족되면 해당 애니메이션으로 즉시 넘어갈 수 있어.
- 지금 내 에니메이터에선 Idle과 Walk에서 Attack 모션으로 돌아오는 트랜지션을 따로 만들지 않아도, Any State에 있는 트랜지션들이 그 역할을 대신하고 있는 거야.

**예를 들어, 내가 걷고 있는 상태(Walk)에서 공격 키를 누르면 Attack(Sword) 파라미터가 true가 돼. Walk 상태에서 Any State로 이어지는 보이지 않는 경로를 통해, Attack(Sword) 조건이 충족되어 Attack01(Sword) 모션으로 바로 넘어가.**
**그래서 애니메이터는 이미 효율적으로 잘 구성되어 있으니 굳이 Idle이나 Walk에서 Attack으로 가는 트랜지션을 일일이 만들 필요가 없는 거야용!**



08/30 MainMenu씬에서 움직이는 배경이미지 생성

- MainMenu 씬에선 게임 시작하는 버튼만 있고 아무런 
- 초기 시도: 여러 개의 UI Image 사용
   1. 처음에는 여러 개의 UI Image 오브젝트를 만들어서 배경을 구성했어. 산, 숲, 하늘 등 여러 레이어로 나누고, 각각에 BackgroundScroller라는 스크립트를 추가해서 스크롤 속도를 다르게 설정했어 
   2. 하지만 이미지가 화면 밖으로 나가면 옆에 여백이 생기는 문제가 발생했고, 2개의 이미지를 이어 붙여서 해결하려고 했어
   3. 이미지가 화면 밖으로 사라지는 문제를 해결하기 위해, 복제한 이미지를 옆에 붙여서 끊김 없이 이어지게 만들었어. Pos X와 Left, Right 값을 조절해서 두 이미지를 정확히 이어 붙였지만, 미세한 틈이 생기는 문제가 발생했어

- 앵커 프리셋과 위치 문제 해결
   1. MainNenu의 Canvas Scaler 인스펙터에서 Scale With Screen Size로 설정하고 Match 값을 0으로 조절해서 UI가 화면 비율에 맞게 보이도록 했어
   2. Reference Resolution도 X: 1920. Y: 1080으로 했어
   3. 배경 이미지가 화면을 꽉 채우게 하기 위해 앵커 프리셋을 **Alt 키를 누른 채로 스트레치**로 설정했어
   4. 하지만 이 때문에 Pos X 값이 사라지고, 이미지들이 겹쳐 보이는 문제가 생겼어. 그래서 Left와 Right 값을 조절해서 이미지를 정확히 이어 붙였어

- Scale With Screen Size과 1920x1080으로 한 이유.
   1. UI 비율 유지: Scale With Screen Size를 사용하면, 네가 만든 UI 요소들이 화면 크기가 바뀌어도 비율을 유지하며 함께 커지거나 작아져
   1920x1080을 기준으로 UI를 만들었을 때, Reference Resolution을 이 값으로 설정하면 유니티가 UI를 다른 해상도에 맞춰 자동으로 조절해 줘
   2. 작업의 편의성: UI를 배치하거나 디자인할 때, 특정 해상도(예: 1920x1080)를 기준으로 작업하면 돼서 훨씬 편해. 나중에 다양한 해상도에서 테스트했을 때도 크게 틀어지지 않아

- 최종 해결책: Raw Image로 전환

   1.. UI 이미지 방식은 미세한 틈이 생기는 문제가 계속 발생했어. 이 문제를 해결하기 위해 Raw Image 컴포넌트로 전환했어. Raw Image는 오브젝트를 실제로 이동시키지 않고 텍스처의 uvRect 속성을 조작해서 스크롤 효과를 만들 수 있거든,
   그래서 UI-Image로 만든 배경이미지 UI는 지우고 UI-Raw Image로 만들었어
   2. 이 방식에서 이미지가 깨지는 문제가 발생해서, 이미지 파일 자체의 **Wrap Mode**를 **Repeat**로 변경해서 이미지가 끊임없이 반복되도록 설정했어
   3. 스크립트를 수정해. RawImage UI를 쓰니 private RawImage rawImage;를 선언
   4. Update 함수에 if (rawImage != null) 문도 수정했어
    if (rawImage != null)
    { Rect uvRect = rawImage.uvRect;
      uvRect.x += scrollSpeed * Time.deltaTime;//x축(좌우)으로 이동
      rawImage.uvRect = uvRect;
    }   
   5. 이제 생성한 UI 오브젝트에 BackgroundScroller 스크립트를 연결시켜 public float scrollSpeed = 변수의 속도를 조절해 오른쪽에서 왼쪽으로 갈때의 속도를 설정했어
   6. 결과적으로, 하나의 Raw Image만으로도 틈 없이 완벽하게 반복되는 무한 스크롤 배경을 완성했어!!

- 이미지 무한 반복의 자세한 이유.
- 이미지가 사라지지 않고 무한반복 되는건 배경화면 이미지 파일의 **Wrap Mode** 때문이야! 
   1. Wrap Mode가 **Clamp**일 경우, 이미지를 보는 시점이 텍스처의 끝에 도달하면 더 이상 움직이지 못하고 멈춰버려
   2. 하지만 Wrap Mode를 **Repeat**로 바꾸면, 텍스처의 끝에 도달했을 때 유니티가 자동으로 이미지를 처음부터 다시 이어 붙여줘
   3. 그래서 스크립트가 uvRect.x 값을 계속 증가시켜도, Repeat 모드 때문에 이미지가 끊임없이 반복되는 것처럼 보이는 거지



08/31 117회 헌혈, UI Image와 Raw Image의 차이, Sprite Packer란?

- 117회 헌혈을 했어. 별거 아닌거라고? 그냥 취미생활이라고? 기념품 받을려고 하는거 같다고? **절대 아니야** 넌 누군가의 생명을 구하는 중요한 행동을 5년 넘게 하는거야.


- 두 가지는 둘 다 이미지를 화면에 표시하는 UI 컴포넌트지만, 작동 방식과 용도에서 큰 차이가 있어. 간단하게 말하면, Image는 스프라이트를 표시하고, Raw Image는 텍스처를 표시해.

- UI Image (UI 이미지) Image 컴포넌트는 UI에서 가장 흔하게 쓰이는 컴포넌트야. 주로 Sprite 타입의 이미지를 다루는 데 최적화되어 있어.
   1. 스프라이트: 스프라이트는 그림 파일(png, jpg)을 게임에서 사용할 수 있도록 유니티가 변환한 형식이야. 주로 2D 게임 캐릭터나 UI 버튼 같은 작은 이미지들을 잘라내서 효율적으로 관리하는 데 사용돼
   2. 용도: Image 컴포넌트는 주로 버튼, 아이콘, 메뉴 배경처럼 크기가 작고 정적인 UI 요소에 사용해, 버튼, 아이콘, 배경 등 UI 요소를 만들 때 주로 사용
- 장점
   1. Sprite 최적화: Sprite는 Sprite Packer를 통해 여러 이미지를 한 장의 큰 이미지(아틀라스)로 묶어서 메모리를 효율적으로 관리할 수 있게 해줘
   2. 다양한 타입: Simple, Sliced, Tiled, Filled 등 여러 가지 이미지 표시 모드를 지원해서 UI 디자인을 유연하게 할 수 있어
- 단점
   Sprite를 기반으로 하기 때문에, 이미지 자체의 픽셀 좌표를 직접 다루는 데는 부적합해. 그래서 이미지를 스크롤할 때 내가 겪었던 것처럼 여러 이미지를 이어 붙여야 했고, 미세한 틈이 생길 수 있었지

- Raw Image (로우 이미지) Raw Image 컴포넌트는 Image 컴포넌트보다 더 원시적인(Raw) 이미지를 다루는 데 사용돼. 이건 텍스처(Texture)를 표시하는 데 최적화되어 있어
   1. 텍스처: 텍스처는 스프라이트보다 더 일반적인 이미지 형식으로, 3D 모델의 표면에 입히는 그림이나, 비디오, 렌더 텍스처(스크린에 보이는 화면을 이미지로 만든 것) 등에 사용, 
   무한 스크롤 배경, 동영상 스트리밍, 웹캠 화면 등 이미지를 실시간으로 직접 조작해야 할 때 사용해
   2. 용도: 어제 만들었던 것처럼 무한 스크롤 배경이나, 미니맵, 카메라 화면처럼 크고 동적인 이미지에 주로 사용돼. uvRect라는 속성을 조작해서 이미지를 스크롤하는 것도 Raw Image의 주요 기능 중 하나야
- 장점
   1. 텍스처 직접 조작: uvRect 속성을 이용해서 이미지 텍스처의 좌표를 직접 조작할 수 있어. 그래서 이미지를 실제로 옮기지 않고도 무한 스크롤 같은 효과를 쉽게 만들 수 있지
   2. 데이터 직접 연결: Render Texture나 WebCamTexture와 같은 외부 소스에서 가져온 이미지를 바로 연결해서 보여줄 수 있어
- 단점
   Sprite Packer를 사용할 수 없어서 Image 컴포넌트만큼 메모리 관리가 효율적이지 않을 수 있어

- Image: 액자에 사진(스프라이트)을 걸어두는 것과 같아. 한 번 걸어두면 그 사진의 형태나 크기를 쉽게 바꿀 수 있지만, 사진을 통째로 옮겨야 해.
- Raw Image: 롤러 스크린에 영화 필름(텍스처)을 투사하는 것과 같아. 필름을 직접 움직여서 영상의 어느 부분을 보여줄지 자유롭게 조절할 수 있지.
**어제 겪었던 것처럼, Image 컴포넌트로 무한 스크롤을 만들려다 보니 위치 오류나 틈이 생기는 문제가 발생했어. 하지만 Raw Image는 처음부터 그런 동적인 처리를 위해 만들어진 컴포넌트라서, uvRect를 이용해 깔끔하게 해결할 수 있어**


- Sprite Packer는 유니티에서 여러 개의 작은 스프라이트 이미지들을 자동으로 하나의 큰 이미지(아틀라스)로 합쳐주는 기능이야. 이 기능은 주로 2D 게임 개발에서 메모리 사용량과 렌더링 성능을 최적화하기 위해 사용.

- 왜 Sprite Packer를 사용해? 
- 게임에는 수많은 스프라이트 이미지 (캐릭터 애니메이션 프레임, 아이콘, UI 등)가 사용돼. 만약 이 이미지들을 개별적으로 불러와서 렌더링하면, 유니티는 각 이미지마다 별도의 '드로우 콜(Draw Call)'을 보내야 해
   드로우 콜(Draw Call): CPU가 GPU에게 "이 이미지(텍스처)를 여기 이 위치에 그려줘"라고 명령하는 것을 말해
- 드로우 콜이 많아지면 CPU에 부담이 커져서 게임 성능이 느려져. Sprite Packer는 이 문제를 해결하기 위해 여러 개의 스프라이트를 하나로 합쳐서 드로우 콜 횟수를 줄여줘.
- Sprite Packer를 사용하면 여러 개의 스프라이트를 하나의 큰 텍스처로 합쳐. 그러면 유니티는 이미지를 그릴 때 단 한 번의 드로우 콜만 보내면 돼. 이렇게 드로우 콜 횟수를 줄여서 게임의 성능을 크게 향상시킬 수 있지.
- 장점
   1. 성능 최적화: 여러 스프라이트를 한 번에 렌더링할 수 있게 되어 드로우 콜 횟수가 줄어들고, 결과적으로 게임이 더 부드럽게 실행돼
   2. 메모리 절약: 여러 개의 작은 이미지 파일 대신 하나의 큰 아틀라스 파일만 메모리에 로드하면 돼서 메모리 사용량이 줄어들어
   3. 관리 용이성: 수많은 작은 파일들을 일일이 관리할 필요 없이, 유니티가 자동으로 아틀라스를 생성해주기 때문에 개발이 훨씬 편리해져

**어제 사용했던 UI Image 컴포넌트가 바로 이 Sprite Packer 기능을 가장 잘 활용하는 대표적인 예시야. 반면,** 
**최종적으로 무한 스크롤 배경을 위해 사용했던 Raw Image는 Sprite Packer를 지원하지 않고 텍스처를 개별적으로 사용하기 때문에, 효율적인 이미지 관리가 필요할 땐 Image 컴포넌트가 더 좋은 선택일 수 있어**
