Vector3 GetValidSpawnPosition()//EnemySpawn 스크립트
{
    if (SpawnCollider == null) return Vector3.zero;
    int maxAttempts = 100;
    Bounds bounds = SpawnCollider.bounds;

    for (int i = 0; i < maxAttempts; i++)
    {
        float randomX = Random.Range(bounds.min.x, bounds.max.x);
        float randomY = Random.Range(bounds.min.y, bounds.max.y);
        Vector3 randomPos = new Vector3(randomX, randomY, 0);

        if (SpawnCollider.OverlapPoint(randomPos))//영역 내부 확인
        {
            Collider2D hit = Physics2D.OverlapCircle(randomPos, 0.3f, SpawnableLayer);//장애물 확인
            if (hit == null) return randomPos; 
        }
    }
    return Vector3.zero;//안전 장치
}

- 옵션창의 QuitGame 버튼 클릭 시, 프로세스가 즉시 종료되니 버튼 클릭 사운드가 들리는 중간에 끊겨.
- 그래서 OptionsManager 스크립트의 QuitGame() 함수 밑에 코루틴을 추가하고 WaitForSecondsRealtime을 사용하여 사운드가 출력될 최소한의 시간(0.15초)을 확보한 뒤 종료되도록 수정했어.
   1. QuitWithTinyDelay() 라는 이름의 코루틴을 추가해서 버튼을 클릭시 사운드가 들릴 0.15f(0.15초) 동안 종료를 멈췄다가 사운드가 다 들릴때쯤 시간이 끝나 종료를 해
   2. QuitGame()함수에는 호출할 코루틴에 0.15f가 있고 코루틴 함수에는 매개변수로 (float Delay)를 추가
      2-1. 매개변수로 쓰는 이유는 나중에 시간을 QuitGame 함수에서 숫자 하나만 고치면 되니까 관리가 훨씬 편리해지지
- QuitWithTinyDelay() 코루틴에 게임 종료(전처리기) 로직을 작성, QuitGame() 함수는 옵션창에서 게임종료 버튼을 누르면 이 신호를 받아 코루틴이 작동하게 해.
- 재시작, 메인화면 이동 버튼 사운드는 SoundManager와 OptionsManager는 DontDestroyOnLoad 덕분에, 씬이 바뀌는 와중에도 AudioSource가 소리를 끝까지 낼 수 있었던 거야. Quit은 아예 프로세스 자체를 종료시키니 예외였던 거지.

- 짧게 했지만 오늘은 인지하는 즉각적 반응의 한계치(0.1s)를 고려한 수치 조절, 함수 호출 시 데이터가 전달되는 원리(인자와 매개변수) 체득, 씬 전환 시 파괴되지 않는(DontDestroyOnLoad) 싱글톤 객체의 특성 재확인. 세가지를 다시 알고 배웠어.

몬스터 사망 시 모든 콜라이더 비활성화

- **6. 몬스터가 죽으면 바로 콜라이더를 해제해서 플레이어나 몬스터가 출동되지 않게 하자** 의 문제를 해결했어. 방법은 쉬웠어.
   1. 콜라이더를 비활성화를 한다고 해서 Layer Collision Matrix를 건드려야 하는 줄 알았거든, 이걸 건드려서 다른 콜라이더가 영향을 받아 해결이 안될 줄 알았어
   2. 하지만 이걸 건드리지 않아도 됐어! 그저 Enemy 스크립트에서 EnemyDie() 함수에 몬스터 사망시 모든 콜라이더 비활성화 로직만 넣으면 됐으니까
   Collider2D[] colliders = GetComponents<Collider2D>();
   foreach (Collider2D col in colliders)
        col.enabled = false;

- Collider2D[] colliders = "이 몬스터(GameObject)에 붙어 있는 모든 Collider2D들을 몽땅 긁어모아서 colliders라는 이름의 상자에(지역변수) 담아줘!"라는 뜻이야.
- foreach (Collider2D col in colliders) = 상자(colliders) 안에 콜라이더(col)가 여러 개 들어있다고 치자. 난 지금 그 콜라이더을 전부 없애고 싶어,
그때 "상자 안에 있는 콜라이더를 하나씩 꺼내서, 다 끌때까지 반복해줘!" 라고 시키는 게 바로 foreach야.
   1. 상자에서 첫 번째 콜라이더를 꺼내서 col이라는 임시 이름표를 붙여
   2. col.enabled = false;를 실행해 (첫 번째 꺼짐)
   3. 상자에 다음 콜라이더가 있는지 확인해
   4. 또 있으면 두 번째 콜라이더를 꺼내서 다시 col이라고 부르고 false로 만들어 (두 번째 꺼짐)
   5. 더 이상 꺼낼 게 없으면 알아서 끝내(종료)

- if문으로 쓸 수 있지 않아? 만약 if문으로 쓰려고 했다면 코드가 아주 복잡해졌을 거야. 
   1. if (첫 번째 콜라이더가 있으면) 꺼줘;
   2. if (두 번째 콜라이더가 있으면) 꺼줘;
   3. ... (하나하나 수동으로 적어서 꺼야하겠지)
- 하지만 foreach를 쓰면 콜라이더가 1개든 100개든 수가 많아도 딱 저 두 줄로 끝낼 수 있어. "있는 만큼 다 처리해줘" 라는 뜻이니까 아주 간단한 foreach문인거지.

   1. 문자열 의존성을 제거하여 잠재적인 런타임 오류 방지, 추후에 사망 애니메이션 종료 시점이나 페이드 아웃 효과 등 추가적인 시퀀스 삽입이 용이하도록 확장성 확보!

옵저버 패턴을 통한 객체 간 결합도(Coupling) 해소 및 시스템 유연성 확보

- 기존 구조에서 Player 스크립트는 이동, 전투와 같은 본질적인 로직 외에도 UI 텍스트 갱신, 게임오버 연출 등 게임 전반의 흐름을 직접 통제하고 있었어. 이는 전형적인 SRP(단일 책임 원칙) 위배였지.
   1. 강한 결합(Tight Coupling)의 독성: UI 레이아웃이 바뀌거나 점수 표시 방식이 변경될 때마다 핵심 물리/전투 로직이 담긴 Player 코드를 수정해야 했어. 이는 작은 수정이 예기치 못한 버그를 전파하는 '수정의 연쇄 작용'을 초래할 수 있는 위험한 상태였지.
   2. 인스펙터 의존성의 한계: 씬이 바뀔 때마다 수동으로 UI 오브젝트를 드래그 앤 드롭해야 하는 방식은 개발자의 실수를 유발하고, 프로젝트 규모가 커질수록 NullReferenceException의 온상이 되는 불안정한 구조였어.

- 해결책1: GameOverManager 리팩토링 (사망 이벤트 분리)
   1. 송신부(Player): OnPlayerDead 이벤트를 선언하고, 사망 시점(Invoke)에만 집중해. 이제 플레이어는 자신의 죽음을 누가 처리하는지, 게임이 멈추는지 아닌지 알 필요가 없어
   2. 수신부(GameOverManager): 플레이어의 생존 여부를 감시(구독)하다가 신호가 오면 즉시 게임오버창 패널을 활성화하고 시간(Time.timeScale)을 정지시켜
   3. Before: Player -> GameOverManager (직접 호출, 강한 결합)
   4. += (주소록 등록): "게시판에 새 글 올라오면 나한테도 연락해 줘"라고 내 전화번호를 적어두는 거야. 이걸 **구독(Subscribe)**이라고 해
   5. -= (주소록 삭제): "이제 나 이사 가니까 연락 안 해줘도 돼"라고 내 번호를 지우는 거야. 이걸 안 하면, 이사 간 집에 전화를 거는 꼴이 돼서 유니티가 "전화받을 사람이 없는데?"라며 에러(NullReference)를 뿜는 거지
   6. After: Player -> [OnPlayerDead 이벤트] <- GameOverManager (이벤트 기반, 느슨한 결합), +=(구독)과 -=(해제)
   7. 결과: 플레이어는 이제 '사망 처리'라는 무거운 짐을 내려놓고 진정한 의미의 객체 독립성을 확보했어
- 기술적 타협과 결정.
   1. 싱글톤은 접근을 편하게 해주지만, 옵저버 패턴은 관계를 자유롭게 해준다!
   2. GameOverManager를 싱글톤으로 만든 덕분에 어디서든 접근은 쉬웠지만, 플레이어가 죽을 때 직접 매니저를 부르는 방식은 여전히 플레이어에게 '짐'이었지
   3. 이번 리팩토링을 통해 플레이어는 이제 "누가 내 사망 처리하든 상관없어, 난 그냥 죽었다는 사실만 알릴 뿐이야" 라는 진정한 의미의 객체 독립성을 갖게 됐어, '느슨한 연결' 을...

   3. 메모리 안전성 확보: 유니티 생명 주기(OnEnable, OnDisable)를 활용해 구독과 해제를 철저히 관리함으로써, 씬 전환이나 오브젝트 파괴 시 발생할 수 있는 메모리 누수와 유령 이벤트를 방지했어!

   2. 하지만 파일이 많아지는 불편함보다, 코드 한 줄 고치기 위해 수백 줄의 스크립트를 뒤지는 '스파게티 코드'의 위험이 더 크다고 이해했어, 폴더 구조화와 명확한 네이밍(Naming Convention)을 통해 파편화 문제를 해결하기로 하고 분리하기로 결정

PlayerHealth, PlayerShield 스크립트의 체력, 방어력 UI바를 옵저버 패턴으로 변경
BowWeapon 스크립트 중 활 쿨타임 UI바를 옵저버 패턴으로 변경

- 어제에 이어 오늘도 옵저버 패턴으로 수정, 연습하고 있어, 이제 플레이어와 UI, 매니저와 UI에 대한건 전부 옵저버 패턴으로 바꿔서 스크립트의 가독성, 느슨한 결합의 장점을 몸으로 익힐려고해.
- 기존 구조의 문제점: PlayerHealth, PlayerShield, BowWeapon 등 기능 스크립트가 UI(Slider, Text)를 직접 들고 조작
- 리스크: UI 이름이나 구조가 바뀌면 모든 기능 스크립트를 다 수정해야 해, 특히 Update() 문에서 매 프레임 UI를 체크하는 방식은 성능 낭비와 코드 복잡도를 유발해.

- 그래서 옵저버 패턴을 도입했어.
   1. 각 기능 스크립트(방송국)는 static event Action을 선언하여 데이터 변경 시 '방송'만 수행
   2. UI 전용 매니저 스크립트(수신기)를 생성하여 해당 방송을 '구독'하고, 신호가 올 때만 UI를 갱신하도록 분리
   3. 객체 간 결합도(Coupling) 최소화: 활 공격이나 체력 로직은 이제 UI의 존재를 몰라도 됨. (관심사 분리 성공)
 
- 오늘 추가한 두 스크립트 PlayerStatusUIManager, WeaponCooldownUIManager 스크립트가 PlayerHealth, PlayerShield, BowWeapon 스크립트의 신호를 받아 UI를 조작하는 방송국 역할이야.
   1. PlayerHealthBar, PlayerShieldBar는 PlayerStatusUIManager 스크립트에서 처리 (여기서 체력, 방어력 UI바에게 데미지를 받거나 회복 시 UI 바의 변경을 관리)
   2. BowCooldownBar는 WeaponCooldownUIManager 스크립트에서 처리 (여기서 활 공격시 쿨타임 바의 활성화/비활성화를 처리) 

- 왜 옵저버 패턴이야?
   1. 의존성 제거(Decoupling): 기존에는 BowWeapon 스크립트가 슬라이더 오브젝트를 직접 Find로 찾고 제어했어. 이는 무기 로직에 UI라는 '불순물'이 섞인 상태라고 할 수 있어. 리팩토링 후, 무기는 오직 '데이터의 변화'만 알리고, UI는 그 신호를 받아 자신의 모습만 바꿔.
   2. 성능 최적화: 매 프레임 Update()에서 if 문을 돌리며 UI 상태를 체크하던 방식을 제거. 오직 이벤트가 발생(Invoke)했을 때만 UI 함수가 실행되므로 CPU 부하를 줄여줘 작은것 하나하나가 모여서 큰 부하가 될테니까
   3. 가독성 및 유지보수: 스크립트의 역할이 명확해져. 각 무기, 체력/방어 코드를 열었을 때 공격 로직만 보이고, UI 코드를 열었을 때 출력 로직만 보이게 됨


- 만약 나중에 포폴에 옵저버 패턴에 대해 기술할때 이렇게 적어보는게 어떨까?
   1. 답변 핵심: "강한 결합(Tight Coupling)의 위험성을 인지하고 이를 개선했습니다."
   2. "기존 구조에서는 UI 컴포넌트 하나만 수정해도 핵심 시스템인 Player 스크립트 전체를 다시 컴파일하고 검토해야 하는 비효율이 있었습니다. 이를 해결하기 위해 데이터의 주체와 출력의 주체를 분리하는 옵저버 패턴을 적용했습니다,
   결과적으로 객체 간 의존성을 0에 가깝게 낮췄으며, 새로운 무기나 UI 요소를 추가할 때 기존 코드를 수정하지 않고도 확장할 수 있는 유연한 구조를 구축했습니다."

검 강화 시스템 로직 결함 수정 및 UX 최적화
v1.6.2로 빌드

- 문제 상황.
   1. 검 강화 아이템을 최대치(10개)까지 획득했어도 의도했던 최저 쿨타임(5초)에 도달하지 못하고 6초에서 멈추는 현상 발생
   2. 쿨타임 UI 숫자가 정수(CeilToInt)로 표시되어, 실제 스킬 사용 가능 시점보다 1초가량 더 길게 느껴지는 역체감(UX 문제) 발생

- 원인 분석.
   1. 로직 오류: 기존 방식은 아이템 3개를 모을 때마다 강화를 발동시킨 후 스택을 0으로 초기화해. 이로 인해 최대 10개를 획득해도 3세트(3, 6, 9개)만 인정되어 쿨타임 감소가 3회만 적용됨. (이건 활 강화 로직에만 있어야 하는거야, 검은 그냥 쿨타임만 줄이면 끝이라서)
   2. 시각적 오차: UpdateSwordSkillUI() 함수에서 Mathf.CeilToInt 사용 시 남은 시간이 0.1초만 되어도 화면에는 '1'이 계속 떠 있어 유저는 1초를 더 기다려야 하는 것으로 착각하게 됨

- 해결.
   1. 스택 계산 방식 변경: 검 아이템 3회 획득시, 강화를 발동시킨 후 스택을 초기화하는 대신, 전체 누적 획득 횟수를 기준으로 currentEnhanceStacks % 3 == 0 조건문을 사용해서 9개째 획득 시 정확히 3차 강화가 이루어지도록 수정, 
   그 이후 강화 스택 10 달성시 쿨타임은 9스택의 5초로 유지하고 UI에서 Max로 표시 (기존 if (isEnhanced) 로직 삭제)

검, 무적 쿨타임 아이콘 UI 시스템 리팩토링 (옵저버 패턴)

- 리팩토링 배경. 왜 구조를 바꿔야 했어?
   1. 객체 간 강한 결합(Tight Coupling): SwordWeapon, InvincibilitySkill 클래스가 UI의 세부 컴포넌트(Image, TMP)를 직접 소유하고 제어함에 따라, 로직과 표현이 뒤섞여 스파게티 코드가 될 위험이 있었어.
   2. 유지보수 효율 저하: UI 구조가 바뀌면 모든 기능 스크립트를 열어서 Find 경로나 참조를 수정해야 했어. 이러면 "코드 하나를 고치면 열 군데가 터지는" 전형적인 나쁜 방식인거지.
   3. 코드 중복: 각 스크립트마다 Update 함수 내에서 UI를 갱신하는 유사한 로직이 반복되어 코드가 비대해져 가독성이 떨어져

- 그래서 오늘 검과 무적 쿨타임 UI에도 옵저버 패턴(Observer Pattern) 도입했어.
   1. 관제탑(Subject) 구축: 모든 무기와 스킬의 쿨타임 정보를 수신하여 UI로 출력하는 WeaponCooldownUIManager 스크립트가 신호를 받게 해
   2. 이벤트 기반 통신: 각 기능 스크립트에 static event Action<float, float>을 선언해서 데이터의 변화가 생길 때만(또는 데이터 그 자체를) 방송(Invoke)하는 구조로 변경
   3. 관심사의 분리
      3-1. 기능 스크립트(활,검,무적): "나는 오직 공격과 스킬 로직에만 집중할게!"
      3-2. UI 매니저: "나는 너희가 보내준 데이터를 바탕으로 유저에게 시각적 피드백(텍스트, 오버레이)을 주는 것에만 집중할게!"

- 상세 작업 내역.
   1. 활(Bow): 슬라이더 기반의 활 쿨타임을 먼저 옵저버화하여 구조적 안정성을 테스트함 (내가 처음 했던 옵저버 패턴)
   2. 검(Sword): 검 강화 아이템 획득 시 SwordSkillCooldown 수치가 즉각 변동됨. 이를 UI에 실시간으로 매끄럽게 반영하기 위해 Update 기반의 데이터 스트리밍 방식을 채택
   3. 무적 스킬(Invincibility): 20초의 긴 쿨타임을 시각화. 검 UI와의 통일성을 위해 ToString("F1") 포맷을 적용하여 소수점 단위의 정밀한 피드백 제공
   4. 방어적 프로그래밍: WeaponCooldownUIManager 스크립트에서 OnEnable에서 구독하고 OnDisable에서 구독을 해지하여, 오브젝트 파괴 시 발생할 수 있는 메모리 누수 및 MissingReferenceException 에러 방지

- 리팩토링 결과 및 성과!
   1. 코드 가독성 향상: 각 스크립트에서 UI 관련 코드(약 20~30줄 이상)가 제거되어 핵심 로직이 한눈에 들어오고 코드량이 줄어들었어
   2. 확장성 확보: 향후 새로운 무기나 시스템이 추가되더라도 WeaponCooldownUIManager 스크립트에 수신 채널만 추가하면 즉시 UI 구현 가능
   3. 성능 및 안정성: 실제 게임 로직 데이터와 UI 데이터가 100% 동기화됨을 확인. Update 기반의 데이터 스트리밍 방식을 채택하여 강화 아이템 등에 의한 수치 변동에 유연하게 대응
      3-1. 그래서 100% 옵저버 패턴 방식을 쓴게 아니야....2/1일에 적었던거 기억해? "내 모든 구상을 무조건 구현하는 것보단, 현재 프로젝트 구조에서 `최선의 타협점` 을 찾는 것이 더 수준 높은 개발 역량임을 깨달았어",
      아직은 내가 부족하고 자신이 없지만 나중에는 꼭! 완전히 바꿔보자
   4. 향후 과제: 현재처럼 Update에서 매 프레임 Invoke 하는 방식을 유지 중이지만, 나중에 최적화가 필요한 시점이 오면 '상태 변화 시점에만 단발성 호출' + 'UI 내부 코루틴 처리' 방식으로 고도화 고려 가능
      4-1. 성능 최적화가 필요한 단계에 이르면, 쿨타임이 진행 중일 때만 방송을 켜고 완료 시 방송을 끄는 '조건부 스트리밍' 도입 고려
      4-2. UI 코루틴화: Subject는 시작 신호만 보내고, UI 내부에서 독립적인 코루틴으로 숫자를 깎는 방식으로 완전한 '이벤트 기반' 구조로의 전환 도전
      
**이제 난 드래그 앤 드롭->코드 내 연결->옵저버로 신호만 전달 로직으로 성장한거야!**
