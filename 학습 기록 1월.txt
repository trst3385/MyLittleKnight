포탈 등장 사운드, 플레이어가 포탈에 닿았을때 씬이 넘어가기 전 일시정지 후 사운드 추가

- 포탈 오브젝트가 타일맵에 나타날 때와 플레이어가 포탈에 닿았을 때의 사운드를 각각 구현하여 청각적 몰입도 향상.
- NextStagePortal 스크립트에 코루틴과 OnEnable()함수를 이용해서 Time.timeScale 조절과 WaitForSecondsRealtime을 조합해 씬 전환 전 짧은 정지 연출 추가.
   1. 처음에는 포탈 오브젝트는 비활성화 상태야. 그래서 OnEnable으로 활성화가 됐을때 사운드가 들리게 기능 추가
   2. MoveToNextScene 코루틴으로 플레이어가 포탈에 닿았을때 다음 씬으로 넘어가기 전 게임을 일시정지 후 닿았을때의 사운드를 추가
   3. WaitForSecondsRealtime으로 닿았을때의 사운드 길이만큼 일시 정지 후, 사운드가 끝나면  Time.timeScale을 1로 돌려놔 다음 게임을 진행
- SoundManager 오브젝트를 활용해 포탈 오브젝트에서 사운드를 관리하는게 아닌 SoundManager에서 관리를 해 SFX관리와 사운드 끊김을 방지했어.

- OnEnable() = 오브젝트가 활성화 됐을때 호출하는 함수.(Awake, Start 함수와 달리 활성화 될 때마다)
- OnDisable() = 반대로 오브젝트가 비활성화 됐을때 호출 하는 함수.(스크립트거나 오브젝트든 똑같이)
   1. 호출 시점: gameObject.SetActive(true)가 될 때마다, 오브젝트가 활성화될 때마다. 꺼졌다 켜질 때마다 실행되어야 하는 연출(사운드 등)에 적합해
   2. 게임 도중 포탈을 껐다 켰다 할 때마다 매번 소리를 내고 싶다면 반드시 OnEnable을 써야 해. 만약 Start에 소리를 넣었다면, 포탈이 처음 생길 때(게임 시작하자마자)만 소리가 나고 나중에 다시 켰을 때는 소리가 안 났을 거야
   3. Awake/Start를 썼다면? 게임이 시작될 때 포탈은 비활성화 상태잖아? 만약 여기에 사운드 코드를 넣었다면, 나중에 미션을 깨서 포탈이 짠! 하고 나타나도 소리가 안 났을 거야. 이미 게임 시작 때 한 번 실행되고 끝났으니까
   4. OnEnable을 썼으니까 평소엔 숨어있다가(비활성화) SetActive(true)가 되는 순간 "나 나타났어! 이제 사운드 출력할게!" 하고 소리를 낼 수 있는 거야

SRP에 맞는 포탈 생성 과정의 로직 수정, 포탈 시스템 전면 리팩토링

- GameTimer는 오직 게임 시간만을 알려주고 포탈은 GameTimer UI의 값을 받는 식으로 수정했어.
- 포탈 오브젝트 자체를 비활성화하면 스크립트의 Update()가 멈춰서 스스로 조건을 감시하지 못하는 유니티의 엔진 특성을 발견.
- 포탈은 시작할땐 꺼져 있다가(비활성화) 포탈 매니저가 깨워주면 나타나서 사운드를 재생하고 씬 이동을 담당.
- 새 오브젝트 PortalManager와 PortalManager 스크립트를 추가. 
   1. PortalManager는 GameTimer의 시간과 MonsterCountManager의 1, 2씬마다 처치해야 할 몬스터 수를 감시하다가 조건 충족 시 포탈을 활성화하는 역할
   2. PortalManager가 이 두 스크립트의 시간과 처치 한 몬스터를 확인 후 포탈을 활성화하게 바꿨어
   3. NextStagePortal: 포탈 오브젝트는 처음에는 꺼져 있는 상태고 PortalManager에서 조건이 맞으면 isActivated = true로 포탈을 활성화 지시를 받으면 포탈이 타일맵에 등장
   4. 포탈 오브젝트는 활성화 되면 등장 시의 사운드와 플레이어가 닿으면 잠시 멈추고 다음씬으로 넘어가는 사운드가 재생된 후 다음씬으로 넘어가는 역할을 해
- GameTimerUI에서 더 이상 사용하지 않는 isPortalActivated 변수를 삭제하여 컴파일 경고(CS0414)를 제거.

- SRP(단일 책임 원칙)를 적용해서 객체 간의 의존성을 낮추고, 유니티의 생명주기(Lifecycle)를 고려한 설계가 얼마나 중요한지 체득했지.
- 인스펙터 연결의 번거로움 해결.
   1. public이나 [SerializeField]를 써서 인스펙터에 연결하는 방식은 아주 확실하지만, 새로운 씬을 만들 때마다 매번 포탈 오브젝트를 클릭해서 드래그 앤 드롭해 줘야 해. 만약 깜빡하면 NullReferenceException 오류가 나겠지?
   2. FindAnyObjectByType을 쓰면: 씬에 GameTimerUI가 하나만 있다면, 코드가 알아서 찾아가기 때문에 내가 손수 연결해 줄 필요가 없어. **자동화** 가 되는 거지!
- GetComponent를 쓸 수 없는 이유. GetComponent는 같은 게임 오브젝트 안에 있는 스크립트를 찾을 때 쓰는 함수야.
   1 .지금 상황: GameTimerUI는 보통 화면 UI(Canvas) 쪽에 있고, 포탈은 맵 12시에 방향에 있지? 서로 다른 오브젝트에 있기 때문에 GetComponent로는 찾을 수 없어
   2. 그래서 씬 전체를 뒤져서 해당 타입을 찾아내는 FindAnyObjectByType을 쓴 거야

- 씬마다 이름이 다른 오브젝트 Portal1, Portal2를 태그(Tag)를 이용해 유연하게 참조하도록 수정. (포탈 오브젝트에 Portal 태그 추가)
   1. OptionsManager: 볼륨 조절 및 씬 재시작 로직 유연화
   2. PortalManager: 게임씬1,2의 포탈 오브젝트에 태그(Portal) 기반 자동 참조 시스템 구축
   3. EnemyDifficulty: Awake 단계 초기화로 데이터 참조 순서 문제 해결
   4. SoundManager: AudioSource 자동 설정 및 믹서 연동 보완
   5. ObstacleDifficulty: 난이도 조절 시스템 싱글톤 전환

   1. 원인 파악: 유니티의 Start 함수 실행 순서는 보장되지 않아. 데이터를 주는 쪽과 받는 쪽 모두 Start에서 처리하다 보니, 초기화가 되기 전에 값을 참조하는 Race Condition(경쟁 상태) 문제를 확인
   2. 해결: 데이터를 제공하는 매니저의 초기화 로직을 Awake() 함수로 옮겨, 어떤 상황에서도 참조하기 전에 값이 먼저 준비되도록 설계 변경


- SoundManager 스크립트의 [RequireComponent(typeof(AudioSource))] [RequireComponent]에 대해.
   1. 스크립트가 실행되는 데 반드시 필요한 컴포넌트를 유니티가 강제로 자동으로 추가하고 관리하게 만드는 명령어야
   2. 특정 스크립트가 실행되기 위해 "반드시 필요한 컴포넌트"를 강제로 지정하는 속성(Attribute)
   3. 클래스 선언부 바로 위에 [RequireComponent(typeof(필요한컴포넌트))] 형식으로 작성해
- 이걸 왜 썼어? (처음 써본 이유와 장점)
   1. 삭제 방지: 누군가(혹은 미래의 나) 실수로 AudioSource만 삭제하려고 하면 유니티가 "이 스크립트에서 쓰고 있어서 안 돼!"라며 경고창을 띄우고 삭제를 막아줘
   2. 자동화: 이 스크립트를 SoundManager 오브젝트에 붙이는 순간, 유니티가 알아서 AudioSource 컴포넌트도 같이 딱! 붙여. 내가 일일이 Add Component를 누를 필요가 없는거지
   3. 의도 명확화: 코드를 보는 다른 사람(혹은 미래의 나)에게 "이 스크립트는 AudioSource 없이는 작동 안 하니까 꼭 같이 써!" 라고 말해주는 가이드라인 역할
   4. 런타임 에러 방지: 코드가 실행될 때 GetComponent를 했는데 컴포넌트가 없어서 발생하는 NullReferenceException 에러를 원천 봉쇄할 수 있어
- SoundManager처럼 특정 컴포넌트(AudioSource)를 주력으로 사용하는 매니저를 만들 때 이 속성을 써주면, 프리팹을 만들거나 다른 씬에서 재사용할 때 세팅을 까먹을 일이 없어서 아주 안전해.

1,2,3씬마다 FireBallSpawnArea의 위치 변경 문제 수정
옵션창 시스템 전면 개편

- 각 씬마다 FireBallSpawnArea의 위치를 조정했어, 매니저 프리팹에서 각 매니저의 위치(Position)을 0/0/0으로 하고 오버라이드를 해보니 일단 각 씬마다 맞는 위치에 잡혔어.
- 확실한 방법이 아닌거 같아. 콜라이더의 위치를 각 씬마다 수정하고 매니저 프리팹에서 각 오브젝트의 위치를 0/0/0으로 하고 오버라이드를 했는데 씬마다 콜라이더 위치가 미세하게 변경될뿐 정상적으로 작동해.


- 싱글톤으로 만든 OptionsManager 매니저 하나로 모든 씬에서 드래그 없이 옵션창 돌아가게 만들었어. 기존에는 싱글톤으로만 만들었지 버튼 하나하나 작동에는 OnClick()이나 인스펙터 연결은 그대로라서.

- 겪었던 문제 (삽질의 기록):
   1. 비활성화 오브젝트 문제: GameObject.Find로는 꺼져 있는 옵션창을 못 찾음
   2. 참조 누락: 씬이 바뀔 때 매니저는 살아있는데 UI는 파괴되어 2, 3번 씬에서 먹통이 됨
   3. UI 레이어 순서: 하이어라키 순서 때문에 사운드창의 Done버튼의 글자나 BGM 텍스트가 이미지 뒤로 숨어서 안 보임
   4. 부모-자식 종속성: 카운트다운 경고창(WarningText)이 옵션패널 자식으로 들어갔는데, 부모를 안 켜고 자식만 켜려다 보니 안 보이는 논리 오류 발생
- 해결 과정:

- TryGetComponent는 유니티에서 성능과 안정성을 동시에 잡기 위해 권장되는 아주 유용한 기능이야. 기존에 쓰던 GetComponent와 null 체크(if != null)를 한 번에 합쳐놓은 '진화형'이라고 생각하면 돼!
- GetComponent가 실패했을 때 발생하는 'Managed Null' 문제는 유니티 엔진(C++)과 스크립트(C#) 사이의 브릿지 연산 때문에 발생해. TryGetComponent는 이 과정을 생략하고 직접적으로 컴포넌트 유무를 판별하기 때문에 가비지 컬렉터(GC)의 부담을 덜어줘.

- 기존 방식 GetComponent: (보통은 컴포넌트를 가져올 때 이렇게 2단계로 작업했어)
PlayerStatsEffects stats = other.GetComponent<PlayerStatsEffects>(); //1. 일단 가져와본다
if (stats != null) //2. 비어있는지 확인한다
{
    stats.ArrowDamageUp(10, 0.2f);
}

- 개선된 방식 TryGetComponent:
if (other.TryGetComponent<PlayerStatsEffects>(out var stats)) //가져오기와 확인을 동시에!
{
    stats.ArrowDamageUp(10, 0.2f);
}

- GetComponent와 이번에 쓴 TryGetComponent의 차이?
   1. 성능이 더 좋아 (가장 큰 이유): 유니티 내부적으로 GetComponent는 컴포넌트를 찾지 못했을 때 'Managed Null'이라는 가짜 Null 상태를 만드느라 연산 비용이 추가로 발생해,
   반면에 TryGetComponent는 컴포넌트가 없으면 그냥 false를 뱉고 끝내기 때문에 훨씬 가볍고 빨라
   2. 코드가 짧고 깔끔해져 (가독성): 변수를 미리 선언하고, 할당하고, 다시 if문으로 검사하는 세 줄짜리 코드가 딱 한 줄로 줄어들어. 한 '코드 다이어트'의 핵심 기법 중 하나야
   3. 에러 방지 (안정성): GetComponent를 썼을 때 가끔 NullReferenceException 에러가 나서 게임이 멈추는 경우가 있잖아? TryGetComponent는 성공했을 때만 내부 로직이 돌아가기 때문에 에러로부터 훨씬 안전해

- 코드 안의 구문 out var는 무슨 뜻이야? (other.TryGetComponent<PlayerStatsEffects>(out var stats))
   1. Try...: "한번 시도해 볼게!" (성공하면 true, 실패하면 false 반환)
   2. out: "성공하면 이 결과를 밖으로 내보내줄게"라는 뜻, 메서드 내부에서 값을 할당하여 호출자에게 반드시 전달하겠다는 약속
   3. var stats: "성공해서 나온 그 컴포넌트를 stats라는 이름의 변수에 담아줘"라는 뜻, 컴파일러가 타입을 추론하게 하여 코드의 유연성을 높임
   4. 안정성 확보: if 조건문 안에서 변수 선언과 할당이 동시에 이루어지므로, 스코프(범위)가 명확해지고 실수로 잘못된 변수를 참조할 가능성을 차단

- 오늘 Item 스크립트에 이렇게 들어갔어
if (other.TryGetComponent<PlayerStatsEffects>(out var statsEffects))
{
    //여기서 statsEffects는 이미 "절대 null이 아님"이 보장된 상태야!
    //그래서 안심하고 로직을 짤 수 있어.
    UseItem(statsEffects, ...);
}
