- OnDrawGizmosSelected함수는 MonoBehaviour를 상속받는 모든 스크립트에서 사용할 수 있는 유니티의 '메시지 함수' 중 하나.   
- 주요 목적:
- 디버깅: 눈에 보이지 않는 버그(예: 공격 범위가 예상과 다름)를 시각적으로 찾아내기 쉬워져.
- 개발 편의성: 게임 오브젝트의 특정 속성이나 로직을 씬 뷰에서 직관적으로 파악할 수 있어 효율적이야.
- 설계 시 도움: 기획 단계에서 특정 범위나 영역을 시각적으로 정의할 때 유용해.

   1. Gizmos.color: 기즈모의 색상을 설정해. (예: Gizmos.color = Color.red;)
   2. Gizmos.DrawWireSphere(center, radius): 중심점과 반지름을 가진 **빈 원(구)**을 그려.
   3. Gizmos.DrawSphere(center, radius): 중심점과 반지름을 가진 **채워진 원(구)**을 그려.
   4. Gizmos.DrawWireCube(center, size): 중심점과 크기를 가진 **빈 사각형(큐브)**을 그려.
   5. Gizmos.DrawCube(center, size): 중심점과 크기를 가진 **채워진 사각형(큐브)**을 그려.
   6. Gizmos.DrawLine(from, to): 시작점부터 끝점까지 선을 그려.
   7. Gizmos.DrawRay(from, direction): 시작점부터 특정 방향으로 광선을 그려.

 OnDrawGizmos()와의 차이점:
 - OnDrawGizmos(): 이 함수는 해당 GameObject가 선택되지 않아도, Scene 뷰에 있는 모든 Gizmos가 항상 그려져. 게임 내 모든 몬스터의 감지 범위를 한꺼번에 보고 싶을 때 유용할 수 있지만, 너무 많은 기즈모가 동시에 그려지면 Scene 뷰가 복잡해질 수 있어.
 - OnDrawGizmosSelected(): 선택된 GameObject에 대해서만 기즈모가 그려져. 특정 오브젝트만 자세히 보고 싶을 때 훨씬 깔끔하고 효율적이야.

 - [Serializable]
 - [Serializable]는 Unity가 네가 만든 커스텀 클래스(또는 구조체)를 인스펙터 창에 표시하고, 그 안에 있는 변수들의 값을 저장(직렬화)하고 불러올 수 있게 해주는 역할을 해.
 - 왜 필요해?
 - 기본적으로 Unity는 MonoBehaviour를 상속받는 스크립트나 public으로 선언된 기본 데이터 타입(int, float, string, Vector3 등)의 변수들만 인스펙터에 자동으로 보여주고 저장해 줘.
 - 하지만 EnemyStats처럼 네가 직접 정의한 새로운 클래스나 구조체를 public으로 선언해도, 그 안에 있는 변수들은 기본적으로 인스펙터에 나타나지 않아. Unity가 이 커스텀 타입을 어떻게 인스펙터에 표시하고 저장해야 할지 모르기 때문이야.
 - [Serializable]를 붙여주면, Unity에게 "아, 이 클래스(EnemyStats)는 인스펙터에 보여주고 값들을 저장해도 돼!" 라고 알려주는 셈이야.
 
 
 - [Header("헤더 텍스트")]
 - [Header("헤더 텍스트")]는 유니티 인스펙터 창의 가독성을 높이기 위해 사용되는 시각적인 속성이야. 인스펙터에 변수들을 그룹별로 묶어주고, 각 그룹의 제목을 표시해 줘.
 - 왜 필요해?
 - 스크립트에 public 변수가 많아지면 인스펙터 창이 길어지고 복잡해져서 어떤 변수가 어떤 역할을 하는지 한눈에 파악하기 어려워질 수 있어.
 - [Header]를 사용하면 관련된 변수들을 특정 제목 아래에 모아서 보여줄 수 있기 때문에, 인스펙터가 훨씬 깔끔해지고 사용하기 편리해져.
 
 -요약하면, [Serializable]는 커스텀 데이터 타입을 인스펙터에서 '편집 가능하게' 해주고, [Header]는 인스펙터 UI를 *'시각적으로 정리'*해주는 역할을 하는 거야. 둘 다 Unity 개발 워크플로우를 효율적으로 만드는 데 중요한 역할을 해.

 - GetComponent<PlayerHealth>()로 얻어온 PlayerHealth 스크립트 인스턴스의 참조를 playerHealth와 같은 변수에 저장하여, 이 변수를 통해 해당 스크립트의 변수나 함수에 접근하고 조작할 수 있음을 이해.
 - (playerHealth는 PlayerHealth 스크립트의 "대리자" 또는 "리모컨" 역할).
 
 - OverlapCircleAll() = 정확한 풀네임은 Physics2D.OverlapCircleAll()
 - 주어진 특정 2D 좌표를 중심으로, 특정 반지름을 가진 가상의 원을 그리고, 그 원 안에 있는 모든 2D 콜라이더(Collider2D)들을 찾아서 배열로 반환해 주는 함수야.
 
 - 주요 파라미터 (괄호 안에 들어가는 값들):
 - Vector2 point (원의 중심 좌표): 원을 그릴 중심 위치를 지정해. 보통 transform.position이나 특정 스폰 지점의 월드 좌표를 사용하지.
 - float radius (원의 반지름): 원의 크기를 결정하는 값이야. 이 반지름 안에 들어오는 콜라이더들을 찾아.
 - LayerMask layerMask (선택 사항, 검색할 레이어): 특정 레이어에 있는 콜라이더만 찾고 싶을 때 사용해. 이 파라미터를 사용하면 원하는 종류의 오브젝트만 감지할 수 있어서 효율적이야. 예를 들어, 몬스터나 플레이어만 감지하고 싶을 때 사용하지.
 
 - 나의 스크립트에서 이 함수는 몬스터를 스폰하기 전에, 스폰하려는 위치에 이미 다른 오브젝트(플레이어, 다른 몬스터, 또는 타일맵의 특정 부분)가 있는지 없는지 확인하는 용도로 사용되고 있어.
 
   Collider2D[] colliders = Physics2D.OverlapCircleAll(cellCenterWorld, 0.5f, SpawnableLayer);
   
   if (colliders.Length == 0) // 아무런 오브젝트도 겹치지 않았다면 유효한 스폰 지점
   {    // ... 몬스터 스폰 로직 ...   }
       
   
 - 위 코드에서:
 
 - cellCenterWorld: 몬스터를 스폰하려는 타일의 중심 월드 좌표가 되겠지.
 - 0.5f: 이 좌표를 중심으로 반지름 0.5f 크기의 원을 그려서 그 안에 콜라이더가 있는지 찾아봐.
 - SpawnableLayer: SpawnableLayer에 설정된 레이어(예: 플레이어, 다른 몬스터, 타일맵 등)에 있는 오브젝트만 검사하도록 해.
 - 만약 colliders 배열의 길이가 0이라면 (즉, 찾은 콜라이더가 아무것도 없다면), 그 위치는 몬스터가 스폰되기에 안전하고 유효한 지점이라고 판단하는 거야
 
 - 요약하자면, OverlapCircleAll은 특정 영역에 무엇이 있는지 감지할 때 사용하는 Unity 2D 물리 함수의 한 종류야.

 07/01 Enemy 스크립트 관리 시스템 심화 이해

 - [Serializable] 속성: EnemyStats와 같은 사용자 정의 클래스(또는 구조체)가 유니티 인스펙터에 노출되어 그 안에 있는 변수들(MoveSpeed, detectionRange 등)을 직접 편집할 수 있도록 해주는 핵심 속성임을 파악했어.

 - public EnemyStats normalStats, strongStats, eliteStats 변수: 이 변수들이 [Serializable] 덕분에 인스펙터에 각 타입별로 펼쳐지는 스탯 섹션(예: Normal Stats)을 만들고, 그 안에 세부 능력치들을 설정할 수 있게 해준다는 것을 알게 됐어.
 - [Header] 속성: 인스펙터에서 변수들을 시각적으로 그룹화하고 제목을 달아주는 역할이며, 항상 그 아래에 오는 변수 선언에 적용되어야 한다는 규칙을 이해했어. (그렇지 않으면 오류 발생)
 - detectionRange vs currentDetectionRange 변수의 역할 분담: detectionRange (EnemyStats 안에 있는 것): 인스펙터에서 각 몬스터 타입별로 설정하는 '설계 값' 또는 **'템플릿 값'**임을 이해했어,
 이 값을 변경해야 몬스터의 감지 거리가 바뀌고, 이걸 변경해야 빌드 후 상태에서도 적용이 돼. 인스펙터의 스탯 설정에서 수정된 값을 detectionRange가 받고 이걸 currentDetectionRange 변수가 스크립트에 저장하게 돼.

   그리고 외부에서 그 static 변수를 불러올 때는 항상 가장 최근에 수정된 그 최종적인 값을 가져오게 되는 거야.이게 static 변수의 가장 중요한 특징이야. 한 번 정의되면 모든 곳에서 공유되는 단 하나의 값이라는 거지.**

 07/05 싱글톤 패턴 이해
 
 - 싱글톤 패턴이란? 싱글톤 패턴 (Singleton Pattern)은 디자인 패턴 중 하나로, 어떤 클래스의 인스턴스를 애플리케이션 내에서 오직 하나만 존재하도록 보장하고, 그 인스턴스에 전역적으로 접근할 수 있도록 하는 방법을 말해.
   단 하나의 인스턴스만 보장:
   - 보통 클래스를 만들면 필요할 때마다 new MyClass() 또는 유니티에서 AddComponent()나 Instantiate()를 통해 여러 개의 인스턴스를 만들 수 있어.
   - 하지만 싱글톤은 특별한 로직을 통해 "이 클래스는 게임 전체에서 오직 한 번만 만들어질 수 있어!" 라고 규칙을 정해두는 거야.
 
   어디서든 쉽게 접근 가능:
   - 보통 다른 스크립트의 함수나 변수에 접근하려면 해당 스크립트의 참조(myScript.someVariable)를 가지고 있어야 해.
   - 싱글톤 패턴을 사용하면 EnemyDifficulty.Instance.GetCurrentNormalSpawnTime()처럼 클래스(스크립트) 이름(EnemyDifficulty)에 .Instance만 붙여서 어디서든 바로 접근할 수 있게 돼. 마치 전역 변수처럼 사용할 수 있는 거지.
 
 - 왜 싱글톤 패턴을 사용할까?
   전역 접근: 
   - EnemyDifficulty 스크립트 처럼 게임의 전반적인 상태(난이도)를 관리하는 중요한 매니저 스크립트들은 게임의 어떤 부분에서든 쉽게 접근해서 현재 난이도 정보를 가져오거나 설정할 필요가 있어,
   - 싱글톤을 사용하면 FindObjectOfType<EnemyDifficulty>()처럼 게임 오브젝트를 찾아오는 복잡한 과정 없이 EnemyDifficulty.Instance만으로 바로 접근할 수 있지.
   - 단일성 보장: 난이도 조절 같은 기능은 여러 개의 인스턴스가 존재하면 문제가 생길 수 있어. 예를 들어 EnemyDifficulty 인스턴스가 두 개라면, 각각 다른 스폰 주기를 계산해서 혼란을 줄 수 있겠지? 싱글톤은 이런 문제를 원천적으로 막아줘.
 
 **싱글톤 패턴을 사용하면 EnemyDifficulty.Instance.GetCurrentNormalSpawnTime()처럼 **클래스 이름(EnemyDifficulty)**에 .Instance만 붙여서 어디서든 바로 접근할 수 있게 돼,
   (이때 클래스 이름은 보통 스크립트 파일 이름과 동일) 마치 전역 변수처럼 사용할 수 있는 거지.**
 **'한 개의 스크립트'는 곧 싱글톤으로 만들고 싶은 '클래스'를 의미하고, 그 '객체'는 그 클래스의 '인스턴스'를 의미하는 거지.**

  public EnemySpawn enemySpawner; (외부 참조/직접 할당):
   - 유니티 인스펙터에서 수동으로 드래그 앤 드롭하거나, 코드에서 다른 스크립트 인스턴스(예: this)를 직접 할당하여 참조를 얻는 방식.
   - 장점: 명확한 관계 설정, 코드로 동적 할당 가능.
   - 단점: 수동 설정 필요, NullReferenceException 가능성.
 
  GetComponent<T>() (동적 탐색)
  - 호출하는 게임 오브젝트에 붙어있는 특정 타입의 컴포넌트(스크립트 포함)를 찾아 가져오는 방식.
   - 장점: 자동화, 런타임에 유연하게 컴포넌트 참조 가능.
   - 단점: Find 계열 함수는 성능 부하 가능성, 해당 컴포넌트가 없으면 null 반환.
   **핵심: GetComponent<T>()는 해당 게임 오브젝트에 <T> 타입의 컴포넌트가 반드시 붙어 있어야만 정상적으로 작동하며, 없으면 null을 반환한다는 것을 명확히 인지.**

     방어력 UI 해결: PlayerShield 스크립트의 인스펙터에서 Shield Bar 슬롯에 실제 UI 슬라이더 오브젝트가 연결되어 있지 않았어. 슬라이더를 드래그앤드롭하여 연결함으로써 방어력 UI가 정상적으로 작동하게 되었어. 체
     체력 UI 해결: PlayerHealth 스크립트의 private Slider healthSlider; 변수에 [SerializeField] 속성이 누락되어 있었어. 이 때문에 유니티 인스펙터에 Health Slider 슬롯 자체가 보이지 않아 체력바 UI 슬라이더를 연결할 수 없었어,
     [SerializeField]를 추가하고 인스펙터에서 체력바 슬라이더를 연결함으로써 체력 UI도 정상적으로 작동하게 되었어.
 
 - [SerializeField] 속성
     용도: private 또는 protected 필드를 유니티 에디터의 인스펙터 창에 노출시켜서 편집할 수 있도록 해줘.
     어떨 때 쓰냐면:
     변수를 public으로 선언하면 다른 스크립트에서 마음대로 접근하고 변경할 수 있어서 캡슐화(데이터 보호)가 잘 안돼.
     이럴 때 변수를 private으로 선언해서 외부 접근을 막으면서도, 유니티 에디터에서 값을 설정하거나 확인하고 싶을 때 [SerializeField]를 붙이는 거야.
     장점: 캡슐화를 유지하면서 유니티 에디터의 편리함을 활용할 수 있어.



07/08 시간이 지날때마다 몬스터의 스텟 증가 구현. 그로 인한 EnemyDifficulty 스크립트를 중점으로 Enemy, EnemyHealth 스크립트 수정

- EnemyDifficulty 스크립트에서 [SerializeField]로 statInterval, atkIncrease, hpIncrease, speedIncrease 변수 구현
   statInterval: n초 마다 몬스터 스텟 강화
   atkIncrease: 공격력 증가 비율   
   hpIncrease: 체력 증가 비율
   speedIncrease: 이동 속도 증가 비율
- Update() 함수에서 gameTimer를 통해 currentDifficultyLevel을 주기적으로 증가시키고, 
  GetAdjustedMonsterStat() 함수를 통해 각 스탯 타입(공격력, 체력, 이동 속도)에 따라 currentDifficultyLevel에 비례하여 스탯을 강화된 값으로 반환하도록 구현.

- Enemy 스크립트의 EnemyStats 클래스 수정. maxHealth 변수 제거: 몬스터의 최대 체력 관리는 EnemyHealth.cs에서 전적으로 담당하도록 분리하여 중복 제거.
- Awake() 함수 수정. SetEnmeyStats() 함수를 Start() 대신 Awake()에서 호출하도록 변경하여, 다른 스크립트가 몬스터 스탯을 참조하기 전에 난이도 적용된 스탯으로 초기화되도록 안정성 강화.
- SetEnmeyStats() 함수 최종 수정 및 연동. 몬스터 타입(Normal, Strong, Elite)에 따라 기본 스탯(selectedStats)을 가져옴:
   EnemyDifficulty.Instance.GetAdjustedMonsterStat() 함수를 호출하여 selectedStats의 MoveSpeed와 attackDamage를 현재 난이도 레벨에 맞춰 동적으로 보정하여 currentMoveSpeed, currentAttackDamage에 할당 완료.
   StopDistance, attackCooldown, detectionRange, scoreValue는 난이도 영향을 받지 않으므로 selectedStats 값을 그대로 사용.
   spriteRenderer.color는 몬스터 타입에 따라 고정 적용.

- EnemyHealth 스크립트 최종 수정 및 역할 확인
- baseMaxHP 변수 사용: 몬스터의 기본 최대 체력을 [SerializeField] private float baseMaxHP로 설정하여 인스펙터 노출과 내부 관리의 균형을 맞춤.
- Awake() 함수에서 난이도 체력 적용:
   EnemyDifficulty.Instance.GetAdjustedMonsterStat(baseMaxHP, StatType.Health)를 호출하여 난이도 보정된 최대 체력(currentMaxHP)을 받아와 적용 완료.
   몬스터의 시작 체력(CurrentHP)을 이 currentMaxHP로 초기화.
   EnemyHealth 스크립트의 Awake() 함수에서 Enemy 스크립트 참조를 미리 가져와, Die() 함수 내부에서 발생하는 GetComponent<Enemy>() 호출에 의한 성능 부하를 개선.

07/12 게임 난이도 상승 알림 UI 구현, EnemyDifficulty 스크립트 수정, Invoke의 역할

- 30초마다 몬스터 스탯이 강해질 때 화면 중앙 상단에 알림 메시지가 표시되도록 DifficultyNotificationText UI 생성.

- EnemyDifficulty 스크립트 수정. EnemyDifficulty.cs 스크립트에 TextMeshPro를 참조하는 변수를 추가하고, 몬스터 스탯 난이도가 올라갈 때 알림 텍스트가 표시되도록 코드를 추가.
- gameTimer 변수를 이용해서 난이도 레벨이 오를 때 알림 UI의 텍스트를 업데이트하도록 코드를 추가했어.
- Invoke("ClearNotification", 3f)를 사용해서 알림이 3초 뒤에 사라지도록 기능을 구현.
- 이렇게 수정된 EnemyDifficulty 스크립트를 DifficultyManager 게임 오브젝트에 컴포넌트로 추가. **이 DifficultyManager 오브젝트는 게임 화면에는 보이지 않지만, 게임 전체의 난이도를 관리하는 스크립트를 담는 '컨테이너' 역할을 해.**

   DifficultyNotificationText UI에는 아무 스크립트도 없어. EnemyDifficulty 스크립트가 직접 이 UI를 제어해서 알림 텍스트를 띄우고, Invoke를 사용해서 3초 뒤에 사라지게 만드는 거야.
   DifficultyManager 오브젝트의 인스펙터에 [Header("UI 알림")] [SerializeField] private TextMeshProUGUI notificationText; 가 있어서 DifficultyNotificationText UI를 연결해,
   DifficultyManager 오브젝트에 있던 EnemyDifficulty 스크립트의 몬스터가 더 강해졌다는 알림이 DifficultyNotificationText UI에 전달이 되는거지!

- Invoke는 유니티에서 특정 함수를 **"일정 시간 뒤에 실행해 줘"**라고 명령하는 기능이야.
- 내가 쓴 EnemyDifficulty 스크립트 코드에서는 Invoke("ClearNotification", 3f)가 "3초 뒤에 ClearNotification()이라는 함수를 호출해 줘"라는 역할을 한 거지. 덕분에 알림 메시지가 계속 화면에 남아있지 않고 사라질 수 있었어.
- Update 함수에서 매 프레임마다 시간을 직접 체크하는 것보다 훨씬 간편하게 타이머 기능을 구현할 수 있는 유용한 함수야.

07/15 Elite 몬스터 움직임 떨림 현상 해결 (Rigidbody2D Interpolate 설정), 게임오버(GameOver) UI에 최종 점수 표시 기능 추가, Player 스크립트 수정, Unity 에디터에서 컴포넌트 연결 (가장 중요했던 부분!)

- 문제: Rigidbody2D를 사용하는 오브젝트의 물리 업데이트(FixedUpdate)와 화면 렌더링(Update) 주기가 서로 달라서 움직임이 미세하게 떨리거나 흐릿하게 보이는 현상 발생.
- 해결: Rigidbody2D 컴포넌트의 Interpolate 옵션을 Interpolate로 설정하여 물리 위치와 렌더링 위치 사이를 부드럽게 보간하여 시각적인 떨림 현상 제거.
- Interpolate(보간)
  이전 FixedUpdate의 물리 위치와 현재 FixedUpdate의 물리 위치 사이를 **부드럽게 '연결'**해줘.
  Update에서 화면을 그릴 때, 이전 프레임과 현재 프레임 사이의 움직임을 예측해서 중간값을 채워 넣어. 마치 두 점 사이에 선을 긋는 것처럼.
  이렇게 하면 물리 업데이트는 딱딱 끊어져도, 화면에는 오브젝트가 부드럽게 움직이는 것처럼 보이게 돼,
  대부분의 2D 물리 기반 게임에서 Interpolate를 사용하면 부드러운 움직임을 얻을 수 있어. 네 문제가 이걸로 해결된 거지.
- Extrapolate (외삽)
  Interpolate랑 비슷하게 움직임을 부드럽게 해주지만, 얘는 **현재 속도를 기반으로 다음 FixedUpdate 위치를 '미리 예측'**해서 화면을 그려.
  Interpolate보다 조금 더 즉각적인 반응을 줄 수 있지만, 물리 계산이 갑자기 크게 바뀌거나 속도가 급변하면 오히려 예측이 틀려서 약간 부자연스러워 보일 수도 있어.
  보통은 Interpolate가 더 안정적이고, 대부분의 상황에서 충분히 부드러운 결과를 보여줘.
**결론적으로 Interpolate를 사용함으로써 물리 업데이트와 렌더링 업데이트 간의 시간차를 시각적으로 부드럽게 메꿔준 거야. 덕분에 네 엘리트 몬스터의 움직임이 훨씬 자연스러워진 거지!**

- GameOverManager 스크립트가 게임 오버 UI를 활성화하고, Player 스크립트로부터 최종 점수를 가져와 UI에 표시하며, 게임 재시작 시 점수를 초기화하도록 만들었어.
- GameOverManager 스크립트에 public TextMeshProUGUI FinalScoreText; 변수를 추가하여 게임 오버 UI에 표시할 텍스트 요소를 연결할 수 있게 했어.
- public int currentScore = 0; 변수를 만들어 게임오버 UI에 보여질 최종 점수를 만들었어.
- public Player playerScript; 변수를 추가하여 Player 스크립트의 인스턴스를 참조할 수 있게 했어.

- Player 스크립트가 점수를 관리하는 주체가 되도록 하고, GameOverManager가 이 점수에 접근할 수 있도록 준비하며, 점수를 초기화하는 기능을 추가했어.
- public void ResetScore() 함수를 추가하여 currentScore를 0으로 만들고, 인게임 점수 UI도 초기화할 수 있게 했어.
- public static int currentScore = 0; 를 public int currentScore = 0; 으로 수정해 static 키워드를 제거했어. 이렇게 함으로써 게임 재시작 시 점수가 자동으로 초기화되도록 했어.

**static을 쓰면, currentScore는 더 이상 각각의 Player 캐릭터가 '자기 자신'의 점수를 가지는 것이 아니게 돼대신, currentScore는 Player라는 '클래스(설계도)'에 직접 속하는 변수가 돼버려,
  그래서 게임 안에 플레이어 캐릭터가 몇 명이든 상관없이, 또는 플레이어 캐릭터가 파괴되고 새로 생겨나도, Player 클래스에는 오직 하나의 currentScore 변수만 존재하고 그 값을 모두가 공유하게 돼,
  이건 마치 "점수판"이라는 개념 자체가 하나인 것과 같아. 그 점수판은 어떤 특정 플레이어에 속한 게 아니라, 그냥 '게임' 전체에 존재하는 유일한 점수판인 거지. 그래서 어떤 플레이어가 점수를 올려도 그 '유일한' 점수판의 점수가 바뀌는 거야.**

07/19 헌혈, EnemyDifficulty 스크립트의 Instance = this as EnemyDifficulty; 에서 as의 뜻, Instance 변수 재이해

- 헌혈 114회

- as의 역할
  as EnemyDifficulty: as 연산자는 this라는 객체를 EnemyDifficulty 타입으로 변환하려고 시도해.
  만약 변환이 성공하면 (this가 진짜 EnemyDifficulty 타입이 맞으면), 변환된 값을 반환해 줘.
  만약 변환이 실패하면, 에러를 내지 않고 그냥 null 값을 반환해 줘.
  이게 그냥 강제로 형변환하는 (EnemyDifficulty)this랑 다른 점이야. 강제 형변환은 실패하면 프로그램이 멈춰버리는 오류(Exception)가 발생할 수 있는데, as는 안전하게 null을 반환해서 프로그램이 계속 실행될 수 있게 해 줘.
- 왜 하필 as를 쓸까?
  사실 EnemyDifficulty 스크립트 안에서 this는 100% EnemyDifficulty 타입이 맞으니까 그냥 Instance = this; 라고 해도 똑같이 작동해.
- 하지만 개발자들이 as를 쓰는 이유는 몇 가지가 있어.
  1.명확성: 코드를 읽는 다른 사람(또는 미래의 나)에게 "여기서 this를 EnemyDifficulty 타입으로 간주하고 사용하려는 의도구나" 라는 것을 명확하게 보여주는 역할을 해.
  2.안전성 (더 복잡한 경우): 비록 이 코드에서는 실패할 일이 없지만, 상속 관계나 더 복잡한 코드에서는 변환이 실패할 가능성이 있어. 그럴 때 as를 쓰면 에러 대신 null을 받을 수 있어서 훨씬 안전하게 코드를 짤 수 있어
- 간단한 비유:
  as 연산자: "이게 '사과'인지 확인해보고 맞으면 담아줘. 아니면 그냥 아무것도 담지 마."
  강제 형변환: "이건 무조건 '사과'야! 무조건 담아! (사과가 아니면 상자를 엎어버림)"
**내가 쓴 코드에서는 this가 항상 EnemyDifficulty니까 as를 썼어도 에러 없이 성공적으로 Instance에 할당되는 거야.

- Instance는 쉽게 말해서, 우리가 만든 싱글톤 패턴의 '유일한' 통로 역할을 하는 변수야.
- C#에 내장된 특별한 키워드(Keyword)가 아니야. 그냥 우리가 임의로 정한 변수 이름일 뿐이야, 개발자들이 싱글톤 패턴을 만들 때 관습적으로 사용하는 이름이지.
- 핵심은 Instance라는 이름이 아니라, 그 앞에 붙은 public static이야.
  public static이 붙었기 때문에, Instance는 '어떤 오브젝트에도 속하지 않고', 클래스 자체에 딱 하나만 존재하는 특별한 변수가 되는 거지.
  그리고 Awake() 함수에서 Instance = this;라고 코드를 짜서, 이 변수가 **'게임에서 가장 먼저 만들어진 그 인스턴스'**를 가리키도록 규칙을 정해준 거야.
**그러니까 Instance는 "싱글톤 패턴의 규칙을 따르기 위해 우리가 붙여준 이름표" 라고 생각하면 돼. 이 이름을 보면 "아, 이 변수는 이 스크립트의 유일한 하나뿐인 인스턴스구나" 하고 바로 알 수 있게 되는 거지.**

- 내 EnemyDifficulty 스크립트를 예로 들어보면.
  public static EnemyDifficulty Instance: 이 코드는 EnemyDifficulty라는 클래스에 속한 Instance라는 특별한 변수를 만드는 거야. static 키워드 때문에 이 변수는 오직 하나만 존재할 수 있어.
  Instance = this;: Awake() 함수에서 이 코드가 실행될 때, this가 **'지금 이 스크립트가 붙어있는 오브젝트'**를 가리키거든. 그래서 Instance 변수에 '바로 이 오브젝트'를 넣어주는 거야.

  변수는 프로그래밍 언어의 기본 단위야. 메모리 안에 값을 저장하는 '그릇' 자체를 말해.

- 속성 (Property 또는 Attribute)
  속성은 객체지향 프로그래밍(OOP)에서의 개념이야. 어떤 오브젝트가 가진 **'특징'이나 '상태'**를 말해
  예를 들어, Player라는 오브젝트의 '이동 속도'나 '현재 점수' 같은 특징들을 우리는 '속성'이라고 부르지.

  다시 말해 변수는 그냥 메모리 상의 공간에 대한 이름표고, 속성은 그 변수가 나타내는 '의미'를 포함한 개념인 거지.

- 코루틴이란? 프로그래밍에서 특정 작업을 메인 스레드를 막지 않으면서(Non-blocking), 정지했다가 다시 시작할 수 있는 함수나 루틴을 말해. 유니티에서 특히 많이 쓰이는 개념.
- 일반 함수 (Blocking): 내가 라면을 끓이는데, 물이 끓을 때까지 가만히 서서 물만 쳐다보고 있는 거야. 물이 다 끓어야만 면을 넣고 다음 단계로 넘어갈 수 있어,
  이 동안에는 다른 어떤 일도 할 수 없어. (게임으로 치면, 어떤 작업이 끝날 때까지 게임이 멈춰 버리는 거지.)
- 코루틴 (Non-blocking): 라면 물을 올려놓고, 물이 끓는 동안 옆에서 설거지를 하거나 다른 재료를 손질하는 거야,
  물이 끓는 소리가 나면 설거지를 멈추고 다시 라면으로 돌아와 면을 넣는 식이지. 즉, 하나의 작업을 완전히 끝내지 않고도 잠시 멈췄다가 나중에 다시 이어서 할 수 있는 거야.

- IEnumerator는 C#의 인터페이스야. 쉽게 말해서 "어떤 컬렉션(목록)을 하나씩 순회(iterate)할 수 있게 해주는 약속"이라고 생각하면 돼.
- IEnumerator 인터페이스에는 주로 다음 두 가지 멤버가 있어:
  Current (속성): 현재 순회 중인 항목(객체)을 반환해줘.
  MoveNext() (메서드): 다음 항목으로 이동하는 역할을 해. 다음 항목이 있으면 true를 반환하고, 더 이상 항목이 없으면 false를 반환하지.
- NotificationManager 스크립트를 보면 StartCoroutine() 메서드가 코루틴을 실행하면, 유니티는 코루틴 내부의 yield return 문을 만날 때마다 잠시 실행을 멈추고 MoveNext()가 호출될 때까지 기다려,
  yield return이 반환하는 값(예: null, WaitForSeconds)은 다음 MoveNext() 호출 시점이 언제가 될지를 유니티에 알려주는 역할을 하지.

- yield는 C#의 특별한 키워드야. 이 키워드는 메서드를 일반적인 함수처럼 한 번에 쭉 실행시키는 대신, 이터레이터 메서드로 만들어줘.
- 이터레이터 메서드는 yield return을 만날 때마다 값을 반환하고, 메서드의 실행 상태를 "기억"한 채 잠시 멈춰. 그리고 다음 값이 요청될 때(즉, 다음 MoveNext() 호출 시) 멈췄던 지점부터 다시 실행을 재개하는 거지.
- yield에는 두 가지 주요 사용법이 있어:
- yield return [값]; 
  현재 값을 반환하고, 메서드의 실행을 일시 중지해.
  유니티 코루틴에서는 이 [값]에 null(다음 프레임 대기), new WaitForSeconds(시간)(지정 시간 대기) 등을 넣어서 언제 코루틴을 재개할지 유니티에게 알려줘.
  DisplayNotification 예시에서 yield return null;과 yield return new WaitForSeconds(displayDuration);이 바로 이 용법이야.
- yield break;:
  이터레이터의 실행을 완전히 종료하고, 더 이상 반환할 값이 없음을 나타내.
  이게 호출되면 코루틴도 여기서 완전히 끝나게 돼. DisplayNotification 스크립트에는 직접적으로 없지만, 특정 조건에서 코루틴을 중간에 종료하고 싶을 때 사용할 수 있어.
- 코루틴에서 yield의 역할 요약
  코루틴은 yield 키워드를 사용해서 컨트롤의 흐름을 유니티 엔진에게 양보하는 거야. yield return을 만나면 "잠시 나 쉬고 있을 테니, 다음 프레임이나 특정 시간이 지나면 다시 나를 깨워줘!"라고 말하는 것과 같지,
  이렇게 함으로써 게임의 메인 스레드가 멈추지 않고 계속해서 다른 중요한 작업들을 처리할 수 있게 되는 거야.
**정리하자면, 코루틴은 IEnumerator 인터페이스를 구현한 이터레이터 메서드이며, 그 이터레이터 동작을 가능하게 하는 핵심 키워드가 바로 **yield**인 셈이야,
  이 둘 덕분에 유니티에서 시간 기반의 복잡한 비동기 로직을 깔끔하고 효율적으로 구현할 수 있는 거지.**

07/24 ItemChest 스크립트의 같은 위치에 아이템이 겹쳐 스폰되는 오류 해결, 게임 시작 시 EnemySpawn 스크립트를 수정해 Normal몬스터 스폰 딜레이 추가 

- 수정 전 문제점:
  기존 SpawnItems() 함수는 ItemSpawnPoints 배열에서 매번 전체 범위를 대상으로 무작위 인덱스를 선택했어.
  이 때문에 여러 아이템을 스폰할 때 같은 스폰 포인트가 중복해서 선택되서 아이템들이 한 곳에 겹쳐 스폰되는 오류가 발생했지.
- 해결 방법 1.동적인 List 사용: 
  고정된 배열(ItemSpawnPoints) 대신, 요소를 자유롭게 추가하고 제거할 수 있는 List(availableSpawnPoints)를 새로 만들었어. 이는 스폰 포인트를 한 번 사용하면 제거하기 위한 준비 단계야.
- 해결 방법 2. RemoveAt() 함수로 중복 방지:  
  for 반복문 안에서 아이템을 스폰할 때마다, 사용한 스폰 포인트를 availableSpawnPoints.RemoveAt(randomSpawnPointIndex) 코드를 이용해 즉시 리스트에서 제거했어,
  이렇게 해서 다음 루프에서는 리스트의 크기가 줄어들어, 이미 사용한 스폰 포인트를 다시 선택할 가능성을 원천적으로 차단했어.
- 해결 방법 3. 안전장치 추가:
  스폰할 아이템 개수가 스폰 포인트 개수보다 많을 경우를 대비해, 스폰할 아이템 개수를 List의 크기(availableSpawnPoints.Count)로 제한하는 코드를 추가하여 오류를 방지했어.
- Instantiate() "복제하다" 라는 뜻처럼, 유니티에서 기존에 있던 오브젝트를 복사해서 새로 만드는 함수야. 게임에 새로운 오브젝트를 생성하는 함수지 
  내 코드에서 Instantiate(itemToSpawn, selectedSpawnPoint.position, Quaternion.identity); 이렇게 사용했어.
  이 코드가 하는 일이 itemToSpawn이라는 **프리팹(원본 오브젝트)**을 복사해서, selectedSpawnPoint.position이라는 위치에, Quaternion.identity(기본 회전값)으로 새로 만들어내는 역할을 해.
  게임이 시작될 때 프리팹으로 미리 만들어둔 아이템을, 상자가 열리는 순간 게임 월드에 "복제해서 나타나게" 하는 함수라고 생각하자.
- RemoveAt()는 List에서 특정 위치(인덱스)에 있는 요소를 제거하는 함수
  내 코드에서 availableSpawnPoints.RemoveAt(randomSpawnPointIndex); 이렇게 사용했어.
  이 코드가 하는 일이 availableSpawnPoints라는 리스트에서 randomSpawnPointIndex에 해당하는 스폰 포인트를 목록에서 완전히 지워버려.
  내가 Random.Range로 스폰 포인트를 하나 선택해서 아이템을 만들었다면, 그 자리를 다시는 사용하지 않도록 리스트에서 없애는 역할을 하는 거야. 이 덕분에 아이템들이 서로 겹치지 않고 정해진 스폰 포인트에 하나씩만 나오게 되는 거지.
**요약하면, Instantiate가 아이템을 "만들어내는" 역할을 한다면, RemoveAt는 그 아이템이 놓일 자리가 중복되지 않도록 "자리를 관리"하는 역할을 한다고 생각하면 돼.**

- Player, Enemy 스크립트에선 플레이어나 몬스터가 이동할때 모습을 SpriteRenderer.flipX로 했었어. 이건 스프라이트 이미지 자체만 뒤집는 것이야.
   1. GameObject의 Scale 값은 그대로 (3, 3, 3)을 유지하면서, Sprite Renderer가 이미지를 좌우로 반전시켜서 보여주는 거지
   2. 이게 일반적으로 가장 깔끔하고, Collider나 다른 컴포넌트의 크기에 영향을 주지 않기 때문에 더 선호되는 방법이야
- 하지만 오늘 만든 발사체는 transform.localScale.x 방식을 썻어.
   1. 이 방식은 GameObject 자체의 크기를 음수 값으로 바꾸는 것이야
   2. transform.localScale = new Vector3(-3, 3, 3) 코드는 발사체 오브젝트의 X축 크기를 -3으로 바꾸는 거야. Scale 값이 음수가 되면 오브젝트 자체가 좌우로 반전돼서 보이게 되지
   3. 내가 flipX 방식을 시도했을 때 네 발사체 스프라이트가 제대로 반응하지 않아서, 더 강력하게 오브젝트 자체를 뒤집는 localScale 방식을 사용한 거야,

- 대부분의 경우 flipX만으로 충분하고 더 깔끔하지만, 어떤 이유로든 flipX가 제대로 작동하지 않을 때는 localScale이 아주 유용한 대안이 될 수 있어.
