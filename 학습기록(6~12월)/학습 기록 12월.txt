오디오 시스템 구조 안정화 (SoundManager스크립트의 도입 )
옵션 창 UI/UX 개선

- 아이템 획득 시 소리가 끊기는 문제와 SFX 볼륨 제어 불가 문제를 해결하기 위해 싱글톤 SoundManager 시스템을 도입했어,
SoundManager 오브젝트를 생성하고 싱글톤 패턴으로 구축하여, 게임 전체의 일회성 SFX 재생을 중앙에서 관리하도록 역할을 확립했어.
   1. 문제점: 아이템 획득 시 Destroy로 인해 오브젝트에 붙은 사운드 컴포넌트가 즉시 제거되어 소리가 끊기는 문제를 겪었어,
   아이템은 획득시에 파괴되고 동시에 획득 시 사운드가 들려야해. 하지만 Destroy로 인해 아이템이 삭제가 되니 사운드가 들리지 않아
   2. 해결책: 아이템 파괴는 Item 스크립트가 담당하고, 획득 사운드 관리는 영구적인 SoundManager 스크립트가 담당하도록 역할을 분리했어.
   3. 아이템 파괴는 item 스크립트가 하지만 획득 시 사운드 관리는 이젠 SoundManager 스크립트가 관리해서 Item 스크립트에서 SoundManager 스크립트를 호출하는 식으로 바꿨어

- item.cs 로직 변경: 비효율적인 동적 AudioSource 생성 로직을 제거하고, 획득 사운드 재생 코드를 SoundManager.Instance.PlaySFX(soundToPlay) 호출로 대체했어,
이를 통해 아이템이 즉시 파괴되더라도 소리가 끊기지 않고 SFX 슬라이더의 제어를 받도록 수정했지.
- SFX 제어 완성: 나머지 몬스터, 장애물 등 다른 모든 효과음 소스(AudioSource)의 Output을 SFX 믹서 그룹에 연결하여, SFX 슬라이더가 모든 효과음을 일관되게 제어할 수 있도록 시스템을 완성했어.!


- SoundControlPanel의 BGM과 SFX 텍스트를 추가해 각 슬라이더가 어떤 용도인지 구별이 가능하고 흰색으로 설정하여 가독성을 높였어.
- GameExitManager 스크립트를 제거하고, OptionsManager 스크립트의 Update 함수를 수정하여 O 키 대신 Escape (ESC) 키로 옵션 패널을 켜고 끄도록 통합했어.
   1. 이로써 ESC는 일시 정지/메뉴 열기 역할만 수행하며, 게임 종료는 옵션 창 내부의 'Quit Game' 버튼을 통해서만 가능하도록 안전한 종료 절차를 확립
- 옵션창의 버튼 이름 변경. 옵션 창의 Exit 버튼을 **'Main Menu'**로, Quit 버튼을 'Quit Game' 등으로 변경하여, 두 종료 기능의 역할을 명확히 구분했어.

SoundManager 스크립트 위치 변경(Cha폴더로)
SoundManager 스크립트의 PlaySFX 함수에 XML 문서화 주석(///<summary>) 추가

- SoundManager 스크립트는 처음 생성했을때 여러 사운드 에셋이 모여있는 Cha 폴더 내부의 'Sound' 폴더에 있었어. 이 폴더는 여러 사운드에셋을  모아둔 창고일뿐이야,
그래서 다른 매니저 스크립트들과 함께 관리되는 'Cha' 폴더로 이동하여 프로젝트 구조의 일관성을 높였어. **Core 시스템이란? 게임의 핵심이 되는 기능, 게임 시스템을 다루는 뼈대같은 스크립트야!**


- XML 주석 도입: SoundManager 스크립트의 핵심 함수인 **PlaySFX** 함수 바로 위에 **XML 문서화 주석 (///<summary>)** 을 추가하여 코드의 가독성 및 문서화 수준을 높였어.
   1. 결과: 다른 스크립트(Item 스크립트 등)에서 PlaySFX 함수를 호출할 때, 함수 위에 툴팁(Tooltip) 형식으로 함수의 역할("SFX 믹서 그룹을 통해 소리를 재생하는 공용 함수")이 즉시 표시되도록 개선했어
   2. 효과: 이로써 이 PlaySFX함수를 사용하는 개발자(미래의 나도 포함)가 SoundManager 스크립트를 열어보지 않고도 PlaySFX 함수의 기능을 바로 파악할 수 있게 되어 유지보수 효율이 크게 향상했지

- XML 주석 작성 방법 (기록용)
- 목적: XML 주석은 단순한 설명이 아닌, C# 컴파일러가 인식하여 IDE(에디터)에서 함수 설명을 툴팁으로 자동 제공하는 공식 문서화 기능이야.
- 작성 방법:
   1. 설명을 달고자 하는 함수 선언 바로 윗줄에 슬래시를 세 번 (///) 입력
   2. 에디터가 자동으로 <summary> 태그를 완성해 주면, 그 안에 함수의 핵심 기능을 간결하게 작성
///<summary>
///SFX 믹서 그룹을 통해 소리를 재생하는 공용 함수
///</summary>
//이 주석은 바로 밑의 PlaySFX 함수에 대한 설명으로 연결
public void PlaySFX(AudioClip clip)
{
    // ... 함수 내용 ...
}

게임이 종료되도 영구적으로 볼륨 설정을 영구적으로 저장 기능 구현
카운트다운 사운드도 SFX(효과음)볼륨으로 조절 가능하게 수정

- 게임을 종료했다가 다시 시작해도 볼륨 설정값이 마지막에 조절했던 볼륨 그대로 유지되도록 구현하기 위해,
OptionsManager 스크립트에 `PlayerPrefs` 을 활용한 영구	 저장 로직을 추가.
   1. SetBGMVolume, SetSFXVolume 함수에서 사용자가 슬라이더를 조절할 때마다 **PlayerPrefs.SetFloat("KeyName", volume)**을 추가, 사용하여 변경된 볼륨 값(0.0 ~ 1.0)을 디스크에 즉시 기록
   2. PlayerPrefs.Save()를 통해 데이터 손실 없이 안전하게 저장되도록 구현
   3. Start() 함수에  **PlayerPrefs.GetFloat("BGMVolume", 1f)**를 사용하여 저장된 값을 불러옴 (저장된 값이 없을 경우 기본값 1f(최대 볼륨)를 사용하도록 안전장치 마련, SFXVolume도 동일한 로직)
   4. 로드된 값을 슬라이더에 반영하고, 해당 값으로 SetBGMVolume(SFXVolume도 동일) 함수를 호출하여 Audio Mixer에 적용, 볼륨이 초기화되지 않도록 개선


- CountdownManager 스크립트의 게임 시작 전 카운트다운 소리도 SFXVolume 슬라이더로 조절하도록 수정했어.
- CountdownManager 오브젝트의(스크립트와 동일한 이름) Audio Source 컴포넌트의 Output을 **SFX Mixer Group**으로 연결.
   1. 스크립트는 소리 재생 명령만 수행하고, 볼륨 값에 대해 알 필요가 없어
   2. OptionsManager 스크립트는 오직 Audio Mixer에게 "SFX 볼륨을 이 값으로 설정해줘"고 명령(SetFloat)만 하는거야
   3. Audio Mixer가 중앙에서 그 볼륨 값에 맞춰 CountdownManager 스크립트에서 들어오는 소리를 조절하여 재생
   4. 효과: 스크립트 간의 의존성을 높이지 않고, 오디오 믹서를 통해 모든 SFX가 단일한 설정 값의 통제를 받도록 시스템 구조를 완성한거야**

**오늘 몸이 좋지 않아 많은 기능을 추가하지는 못했지만, 게임의 기본기이자 가장 중요한 시스템 중 하나인 옵션 및 사운드 영구 저장 시스템을 완벽하게 마무리했어,
  기능의 양보다 코드의 품질과 안정성을 높이는 데 집중했고, 내 시스템 설계 능력과 책임감을 증명하는거야.**
**내일은 git, 노션 포트폴리오에 시연 영상을 다시 업로드하자. 옵션키, 사운드 조절 기능이 추가됐으니까**

포트폴리오에 문제해결의 '옵션창의 각종 기능 구현`에서 재시작, 메인화면으로 이동, 게임 종료에 대한 로직 설명

- 옵션창의 각종 기능 구현 토글에서 각 기능(옵션창을 켜면 게임 멈춤, 재시작, 메인화면 이동, 게임 종료 기능에 대해 로직과 작동 방식을 설명했어.
- 각 기능마다 작은 토글 (제목3 토글)을 만들어서 가독성을 확보하면서 명확하게 분류를 했어.
   1. `게임 상태 제어 및 UI 무결성 로직` 작은 토글에 `Time.timeScale을 사용한 일시정지, CountdownManager.isCountdownFinished 변수 체크를 통한 카운트다운 중 옵션 창 접근 차단 및 경고 메시지 출력 구현` 설명을 적어,
   옵션창이 켜졌을때는 게임이 일시정지, 카운트다운이 작동 중에 옵션창을 켜면 warningText.text = "카운트 중이야! 잠시만 기다려!"; 작동
   2. 'Scene 및 Application 제어 로직' 작은 토글에 `SceneManager.LoadScene API를 사용한 재시작 및 메인 화면 이동, #if UNITY\_EDITOR를 활용한 빌드 환경 대응 종료 처리(Application.Quit()) 구현.`을 설명을 적었어
      2-1. RestartGame() 함수의 SceneManager.LoadScene(SceneManager.GetActiveScene().name); 으로 게임씬을 재로드(재시작)
      2-2. ExitGame() 함수의 SceneManager.LoadScene("MainMenuScene"); 으로 메인화면씬 (MainMenuScene)으로 이동
      2-3. QuitGame()함수의 전처리기로 게임을 종료 로직을 설명:
       #if UNITY_EDITOR
       UnityEditor.EditorApplication.isPlaying = false;
       #else
       Application.Quit();
       #endif

- 전처리기 지시문이란: 컴파일이 시작되기 전에 특정 코드를 포함할지/제외할지 결정하는 지시문이야. 모든 전치리기는 # 지시어로 시작해. (컴파일 하기전에 소스 파일들을 정리하고, 정의 된 부분만 컴파일)

   1. Rigidbody가 None (보간 없음)으로 설정되어 있으면, 물리 계산과 화면을 그리는 속도가 서로 달라
   2. 물리 계산 (Fixed Update): 1초에 50번 (예시), 화면 그리기 (Update): 1초에 120번 (예시). 화면이 120번 그려지는 동안, 물리 위치는 50번만 업데이트돼
   3. 결과로 화면이 새로 그려질 때마다 오브젝트의 위치가 듬성듬성 바뀌니까, 특히 오브젝트가 빠를 때 화면에서 '끊기거나 덜덜 떨리는' (Jittering) 현상이 발생해
- Interpolate의 역할.
   1. 이전 프레임의 위치를 기반으로 현재 프레임의 위치를 예측하여 움직임을 부드럽게 보간(Blend) 해줘
   2. 이전 위치 기억: 물리 업데이트 A가 끝났을 때의 위치를 기억해
   3. 현재 위치 계산: 물리 업데이트 B가 곧 끝날 위치를 계산해
   4. 예측 및 보간 (Blend): 물리 업데이트 A와 B 사이에서 발생하는 렌더링 프레임이 화면을 그릴 때, A 위치와 B 위치 사이를 시간 비율에 맞춰 부드럽게 예측하여 그려
   5. 즉, Interpolate는 실제 물리 계산 결과(A와 B)를 무시하지 않으면서, 그 사이의 시각적인 움직임을 채워서 연속적으로 보이게 만들어 주는 거야
- 결과로 실제 물리 업데이트는 듬성듬성해도, 우리 눈에는 A에서 B로 튕기듯이 이동하지 않고 아주 부드럽게 미끄러지듯이 이동하는 것처럼 보여. 이 덕분에 몬스터나 화살에서 느꼈던 떨림 현상(Jittering)이 사라지는 거야.

다음을 위해 추가 게임씬 생성(기존 게임씬 복사)

- 활 강화 사운드가 아이템을 먹을 때마다 매번 들려서 귀가 피로하고, '강화 성공'의 임팩트가 부족했어. 그래서 활 아이템 3회 획득해서 강화가 됐을때만 사운드가 들리게 했어.
   1. 나머지 연산자(% 3 == 0)를 도입해 딱 3, 6, 9번째 획득 시에만 텍스트 연출과 강화 사운드가 터지도록 로직을 수정
   2. 활 레벨 UI는 10이 되면 Max가 되지만 강화 스택은 12, 15, 18번째... 그 이상도 3의 배수라면 무조건 사운드와 연출이 터지게 되어 있어
- 사운드 파일이나 오디오 소스가 누락되었을 때 문제를 찾기 쉽고, 게임이 멈추지 않도록 if (null) 체크를 넣고, Debug.LogWarning을 통해 내가 실수한 부분을 즉시 알 수 있게 방어 로직도 구축했지.

- 코드 구조의 고민 (역할 분담)
   1. BowWeapon 스크립트: 강화 스택 데이터라는 '본체'를 관리
   2. PlayerStatsEffects 스크립트: 데이터 변화를 감지해 UI와 사운드라는 '표현'을 담당
   3. 스크립트를 하나에 다 몰아넣지 않고, "데이터 주인"과 "연출 담당"을 나누는 것이 복잡하지만 장기적으로 코드가 깔끔해져,
   한 스크립트에 몰아 넣으면 찾기는 편할지라도 가독성 문제와 '단일 책임 원칙(SRP)' 에 위반돼


- 또다른 게임씬 준비.
   1. 한개의 씬으로만 게임 플레이하면 지루하니위해 씬 복제(Duplicate)를 통해 Stage 2(GameScene2)의 기반을 마련했어
   2. 새로 생성한 게임씬은 차이를 두기 위해 나무 오브젝트(플레이어 실루엣과 Sprite Mask 기능)와 장애물(FireBall, Spike) 생성 오브젝트 ObstacleDifficultyManager를 비활성화
   3. 더 추가할 계획이야. 1, 2, 3 단계로 추가해 단계별로 장애물, 몬스터 강화를 조절할거야

**오늘은 단순히 코드를 많이 적은 날, 여러 스크립트를 관리한 날이 아니라, "어떻게 하면 유저에게 더 짜릿한 피드백을 줄까?"와 "어떻게 하면 코드를 더 안전하게 짤 것인가"를 고민한 날이였어. 공부 시간의 양보다 질적으로 훨씬 성장한거같아**
**오늘처럼 "왜?"라고 질문하고 그 해답을 구조적으로 풀어낸 짧은 시간이 내 실력을 몇 배는 더 빠르게 키워줄 거야!**



12/19
3개의 게임씬(GameScene)으로 분리해 각 씬마다 장애물 등장

- 단일 씬 기반의 플레이에서 벗어나, 사용자가 게임에 점진적으로 적응할 수 있도록 단계별 난이도 시스템을 추가했어.
- GameScene 1 (No Obstacle): 낮은 난이도. 장애물 없이 몬스터 사냥과 활 강화 시스템 익히기에 집중.
- GameScene 2 (FireBall): 발사체 장애물 추가. 좌우에서 날아오는 불덩이를 피해서 전투하는 순발력 요구.
- GameScene 3 (All): 발사체 + 가시 함정. 바닥과 발사체를 모두 신경 써야 하는 복합적인 최종 난이도.

- ObstacleDifficultyManager 오브젝트는 1,2,3 모든 씬에서 활성화 상태를 유지. 씬이 바뀌어도 매니저가 존재하므로 다른 스크립트와의 데이터 참조(Null) 오류를 방지해.
- 코드를 직접 수정하지 않고, 각 씬의 Hierarchy에서 자식 오브젝트인 'Spawner'들만 켜고 끄는 방식으로 스테이지 성격을 즉각 변경할 수 있게 설계한거야.
- 씬 이름을 특징에 맞게(GameScene1_NoObstacle 등) 변경하여 개발 중 혼선을 방지하고 Build Settings를 정돈. (위에서부터 메인씬, 게임씬1,2,3)

씬 전환 시스템 및 포탈 연출 구현

- 스테이지별 생존 시간을 설정하고, 목표 달성 시 포탈의 등장과 함께 다음 단계로 이동하는 '게임 루프(Game Loop)' 완성.
- GameTimerUI 스크립트를 확장하여(GameTimer UI에 위치) 경과 시간이 1분에 도달하면 특정 위치에 포탈이 생성되도록 구현.
- 포탈의 NextStagePortal 스크립트를 추가해 Ontrigger와 밟았을때 포탈 상하좌우의 룬 글자에 빛이 나도록 추가했어(이 에셋을 다운받았을떄 있던 기본 스크립트를 내 방식으로 바꿨어)
   1. OnTriggerEnter2D와 OnTriggerExit2D를 활용해 플레이어가 밟을 때만 룬이 푸른색으로 빛나도록(Alpha 보간) 처리
   2. isPortalSpawned 플래그(bool)를 사용해서 만약의 중복 생성을 방지하고 안정성을 높였어

- 완성된 스크립트를 포탈 프리팹에 넣고 GameTimerUI의 인스펙터에 포탈 프리팹을 넣고 자식으로 spawnPoint 오브젝트를 만들어 Transform  위치로 포탈이 등장할 위치도 설정.
- 각 씬 GameScene1, 2 (3는 최종단계라 제외)마다 각 씬별로 목적지가 다른 포탈 프리팹을 개별 설정하여 독립적인 스테이지 전개 가능하도록 했어.
   1. 프리팹 관리: 모든 씬이 같은 프리팹을 공유할 때 목적지가 꼬이는 문제를 확인하고, 씬별 전용 포탈을 만들기 위해 포탈을 복사하고 이름을 변경해서 인스펙터 값을 개별 설정(Override.새롭게 재정의)하여 해결
   2. 1번 씬(No Obstacle) → 2번 씬(FireBall) → 3번 씬(All)으로 이어지는 흐름 구축

점수 UI밑에 ??/?? 방식으로 처치해야 몬스터 수를 텍스트로 표시

- 설계 관점: 스크립트의 비대화를 막기 위해 MonsterCountManager 스크립트를 분리해서 유지보수성을 높였고, 인터페이스(IsMissionComplete)를 통해 객체 간 협력 구조를 설계.
- 단순히 1분을 버티는 것뿐만 아니라, 지정된 수의 Normal, Strong, Elite 몬스터를 모두 잡아야 스테이지가 클리어되도록 로직을 고도화했어.(1분만 버티고 다음 스테이지로 넘어가면 몬스터를 처치하지 않고 도망만 치면 넘어가게 되니까)
- Enemy 스크립트에서 몬스터가 죽으면 if (MonsterCountManager.Instance != null) MonsterCountManager.Instance.DeathCount(this.enemyType); 으로 죽었다는 신호를 MonsterCountManager로 보내
- MonsterCountManager 스크립트의 public void DeathCount(Enemy.EnemyType type) 함수에서 처치한 횟수를 UpdateCounterUI 함수로 보내 처치 현황 UI에 보내.
- GameTimerUI 스크립트에선 시간(1분 이후)과 MonsterCountManager 스크립트의 몬스터 처치 처치 수를 확인하고 이 두가지 조건이 충족되면 차원문 등장.


- 코드 구조 개선 (SRP 및 캡슐화 적용):
   1. MonsterCountManager 추가(스크립트와 오브젝트 동일한 이름): 처치 수 카운트 및 미션 달성 여부 판단 로직을 전담시켜
   2. GameTimerUI 스크립트 역할 조정: 게임시간 측정과 포탈 소환 트리거 역할에 집중하게 하여 스크립트 간 의존성을 낮췄어

- UI 및 디테일 최적화:
   1. 화면의 점수 UI 밑에 Normal: 0/20 같은 형식으로 실시간 목표 달성률을 표시했어
   2. 목표 수치를 초과해도 숫자가 계속 올라가지 않게 Mathf.Min을 활용해 예외 처리를 완료
   3. UX 관점: "플레이어에게 '잡아야 할 몬스터 수'를 명확히 제시하여 게임의 목표 의식을 강화할 수 있지
